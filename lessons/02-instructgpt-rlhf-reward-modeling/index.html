Why Supervised Fine-Tuning Isn't Enough

In Lesson 01, we saw how benchmarks like MMLU measure what models know. But knowing facts isn't the same as being helpful. A base language model trained on internet text can complete prompts, but it doesn't inherently follow instructions, refuse harmful requests, or optimize for user satisfaction.

Supervised fine-tuning (SFT) teaches models to follow instructions by training on (prompt, ideal response) pairs. This helps, but it has limits:

  • Hard to write demonstrations for every possible user request
  • Human-written responses vary in quality—which style should the model learn?
  • SFT doesn't directly optimize for what users actually prefer
  • Writing demonstrations is expensive and slow to scale

Solution: Train models using human preferences (comparisons between responses) instead of demonstrations. This is Reinforcement Learning from Human Feedback (RLHF).

The Alignment Problem

Large language models trained on web text learn to predict what comes next—but "what comes next on the internet" is not the same as "what a helpful assistant would say." Base models might:

  • Generate toxic or harmful content (because it exists in training data)
  • Refuse to answer reasonable questions (because they're uncertain)
  • Provide technically correct but unhelpful answers
  • Ignore the user's intent and generate plausible-sounding nonsense

InstructGPT's Goal

The InstructGPT paper (Ouyang et al., 2022) introduced a practical RLHF pipeline to make language models:

  • Helpful: Follow user instructions and provide useful information
  • Honest: Avoid making up facts or hallucinating
  • Harmless: Refuse unsafe requests and avoid toxic outputs

The result: models that users prefer over larger, more capable base models—even when InstructGPT is 100x smaller.

Key Insight: Preferences Scale Better Than Demonstrations

It's easier and faster for humans to compare two responses ("A is better than B") than to write a perfect response from scratch. RLHF exploits this: train a reward model on preference comparisons, then use it to optimize the language model.

The RLHF Pipeline: Three Stages

InstructGPT's training pipeline has three distinct stages. Each stage builds on the previous one.

Stage 1: Supervised Fine-Tuning (SFT)

Input: A pretrained GPT-3 base model
Data: ~13,000 human-written (prompt, response) demonstrations
Output: An SFT model that can follow basic instructions

Labelers write high-quality responses to prompts from the OpenAI API. The base model is fine-tuned on these demonstrations for a few epochs. This gives the model a starting point for instruction-following, but it's not yet optimized for user preferences.

Stage 2: Reward Model (RM) Training

Input: The SFT model from Stage 1
Data: ~33,000 prompts, each with 4-9 model outputs ranked by human labelers
Output: A reward model that predicts human preference

For each prompt, the SFT model generates multiple responses. Human labelers rank them from best to worst. These rankings are converted into pairwise comparisons (e.g., "response A > response B").

The reward model is trained to predict these preferences. Given a (prompt, response) pair, it outputs a scalar score. The training objective ensures that preferred responses get higher scores.

Why not skip to Stage 3? Because running RL requires millions of reward evaluations. Humans can't label that fast—but a learned reward model can.

Stage 3: Reinforcement Learning via PPO

Input: The SFT model (policy) and the RM from Stage 2
Data: ~31,000 prompts from the API (no human labels needed)
Output: InstructGPT, a policy optimized for high reward

The SFT model generates responses to prompts. The reward model scores each response. The language model is updated using Proximal Policy Optimization (PPO), a reinforcement learning algorithm, to increase expected reward.

Key constraint: A KL-divergence penalty keeps the policy close to the original SFT model. This prevents the model from "reward hacking"—exploiting quirks of the reward model to get high scores without being genuinely helpful.

From the Paper: Key Findings

The InstructGPT paper (arXiv:2203.02155) introduces the RLHF pipeline and reports compelling results. Here are the most important claims and data points directly from the paper:

Labeler Preference: InstructGPT Wins vs GPT-3

"Labelers significantly prefer InstructGPT outputs over outputs from GPT-3. On our test set, outputs from the 1.3B parameter InstructGPT model are preferred to outputs from the 175B GPT-3, despite having 100x fewer parameters."
— Abstract, arXiv:2203.02155

This is the headline result: RLHF-trained models win human preference evaluations even when much smaller than base models. Figure 3 in the paper shows that InstructGPT (1.3B) is preferred over GPT-3 (175B) on a majority of prompts.

Performance on Public NLP Datasets

"InstructGPT shows improvements on truthfulness over GPT-3, as measured by TruthfulQA. InstructGPT models show small regressions on public NLP datasets, such as SQuAD and DROP."
— Section 5.2, arXiv:2203.02155

Trade-off: Optimizing for helpfulness improves TruthfulQA (a benchmark for avoiding false statements) but slightly hurts performance on traditional NLP benchmarks like SQuAD (reading comprehension). The authors note this as an "alignment tax"—the model prioritizes being helpful over maximizing specific benchmark metrics.

Dataset Scale and Labeler Agreement

The paper reports training data sizes (Section 3.1, Table 1):

  • SFT dataset: 13,000 (prompt, response) pairs
  • RM dataset: 33,000 prompts, each with 4–9 ranked outputs (~200K comparisons)
  • PPO dataset: 31,000 prompts from the API (unlabeled)

Labeler agreement is high for clear cases (e.g., refusing toxic requests) but lower for subjective preferences (e.g., tone, verbosity). The paper measures inter-annotator agreement at ~73% for pairwise preferences (Table 9, Appendix).

Generalization Beyond API Distribution

"InstructGPT generalizes to preferences of held-out labelers, and to instructions outside the distribution of our training data."
— Section 5.4, arXiv:2203.02155

The paper tests whether InstructGPT learned to please specific labelers or truly improved at following instructions. Held-out labelers (who didn't contribute to training data) still prefer InstructGPT outputs. It also generalizes to prompts written in non-English languages and coding tasks, even though these were rare in training data.

Toxicity Reduction

"InstructGPT produces less toxic outputs than GPT-3 when prompted to be respectful, as measured by the Perspective API."
— Section 5.3, arXiv:2203.02155

On the RealToxicityPrompts benchmark, InstructGPT generates toxic continuations 25% less often than GPT-3 (Figure 5). This reduction comes from RLHF training—the reward model learned that toxic outputs receive low preference scores.

Key Takeaway

InstructGPT demonstrates that RLHF produces models that users prefer, even at the cost of some traditional benchmark performance. The three-stage pipeline (SFT → RM → PPO) is now the foundation for most modern aligned language models, including ChatGPT and Claude.

What Is a Reward Model?

A reward model (RM) is a classifier trained to predict human preferences. Given a prompt and a response, it outputs a scalar score representing how much humans would like that response.

How Preference Data Looks

Human labelers see a prompt and multiple model outputs, then rank them from best to worst. Here's a toy example:

Example: Preference Ranking

Prompt: "Explain photosynthesis to a 5-year-old."

Response A (Rank 1 - Best)

"Plants eat sunlight! They take sun, air, and water and mix them together to make food. It's like a plant cooking its own lunch. The green color helps them do this."

Response B (Rank 2)

"Photosynthesis is when plants use energy from the sun to convert carbon dioxide and water into glucose and oxygen."

Response C (Rank 3)

"I don't know."

Response D (Rank 4 - Worst)

"Photosynthesis involves the light-dependent reactions in the thylakoid membrane..."

Why this ranking?

  • A: Simple, accurate, age-appropriate—exactly what was requested
  • B: Accurate but too technical for a 5-year-old
  • C: Honest but unhelpful
  • D: Way too advanced, ignores the instruction

These rankings are converted into pairwise comparisons: A > B, A > C, A > D, B > C, B > D, C > D. The reward model is trained so that preferred responses get higher scores.

Training the Reward Model

The reward model is usually initialized from the SFT model (same architecture), then fine-tuned on preference comparisons. The training objective is:

Loss Function


Loss = -log(σ(r(x, y_w) - r(x, y_l)))

Where:
- x = prompt
- y_w = preferred (winner) response
- y_l = dispreferred (loser) response
- r(x, y) = reward model's score for (prompt, response)
- σ = sigmoid function

This loss encourages the reward model to assign a higher score to the preferred response. Over many comparisons, the model learns a general notion of what humans consider helpful, harmless, and honest.

Why Not Just Use Human Labels Directly?

During PPO (Stage 3), the language model generates millions of responses that need to be scored. Humans can't label that fast. The reward model acts as a learned proxy for human judgment—it's fast, scalable, and trained on real human preferences.

Limitation: The reward model is imperfect. It might give high scores to responses that "look good" but are subtly wrong. This is called reward hacking (more on that below).

PPO: Optimizing the Language Model

Proximal Policy Optimization (PPO) is the reinforcement learning algorithm used to train InstructGPT in Stage 3. The goal: maximize expected reward from the reward model.

The Setup

  • Agent (Policy): The language model being trained (initialized from SFT model)
  • Environment: The prompt distribution (API requests)
  • Action: Generate a response (token by token)
  • Reward: Score from the reward model

The PPO Objective

PPO updates the policy (language model) to increase the reward for generated responses. However, naively maximizing reward can cause the model to exploit the reward model—finding adversarial outputs that get high scores but aren't actually helpful.

KL Penalty

To prevent reward hacking, InstructGPT adds a KL-divergence penalty that keeps the policy close to the original SFT model: 


Objective = E[reward(x, y)] - β * KL(π_RL || π_SFT)

Where:
- π_RL = the policy being trained (InstructGPT)
- π_SFT = the original SFT model (frozen reference)
- β = KL penalty coefficient (controls how much we allow drift)

This regularization term ensures the model doesn't stray too far from the SFT initialization. It balances reward maximization with maintaining reasonable, coherent outputs.

Training Process

  1. Sample prompts from the API distribution
  2. Generate responses using the current policy (language model)
  3. Score responses with the reward model
  4. Compute advantages (how much better is this response than expected?)
  5. Update the policy via gradient ascent on the PPO objective
  6. Repeat for many iterations

Why PPO Instead of Other RL Algorithms?

PPO is popular for RLHF because:

  • Stable: The "proximal" constraint prevents large policy updates that could collapse training
  • Sample efficient: Reuses generated samples for multiple gradient updates
  • Simple: Doesn't require complex second-order optimization (unlike TRPO)

InstructGPT Results in Plain Language

InstructGPT's results demonstrate that RLHF produces real, measurable improvements in user satisfaction. Here are the key takeaways:

1. Labelers Prefer InstructGPT Over Larger GPT-3

In head-to-head comparisons, human evaluators preferred InstructGPT 1.3B outputs over GPT-3 175B outputs ~85% of the time on the test prompt distribution. This held across instruction-following, summarization, and question-answering tasks.

Why? GPT-3 often ignored instructions, rambled, or generated plausible but unhelpful text. InstructGPT learned to directly address what the user asked for.

2. Improved Truthfulness

On TruthfulQA (a benchmark designed to catch models making false claims), InstructGPT improved significantly over GPT-3. The PPO-trained model was less likely to confidently state incorrect facts, likely because human labelers penalized hallucinations.

3. Reduced Toxicity

InstructGPT generated ~25% less toxic content on RealToxicityPrompts compared to GPT-3 when instructed to be respectful. RLHF training taught the model to avoid outputs that labelers flagged as harmful or offensive.

4. Generalization to New Tasks

InstructGPT wasn't just good at tasks in its training distribution—it generalized to:

  • Prompts in languages other than English (though training was mostly English)
  • Code generation tasks (despite limited code examples in RLHF data)
  • Held-out labelers who didn't contribute training data

This suggests the model learned general instruction-following and helpfulness, not just memorization of specific training patterns.

5. Alignment Tax: Small Benchmark Regressions

InstructGPT showed small performance drops on some traditional NLP benchmarks (e.g., SQuAD, DROP) compared to GPT-3. This is the alignment tax—the model optimized for user preferences rather than maximizing specific eval metrics.

The paper argues this trade-off is acceptable: users care about helpfulness, not SQuAD scores. However, it raises important questions about how to preserve capabilities during alignment.

Failure Modes and Limitations

RLHF is powerful, but it's not magic. InstructGPT and similar models have well-documented failure modes. Understanding these helps you recognize when RLHF works and when it breaks down.

1. Reward Hacking

What it is: The policy learns to exploit quirks of the reward model to get high scores without being genuinely helpful.

Example: The reward model might give high scores to responses with certain keywords or formatting. The policy learns to sprinkle in those keywords even when they don't improve the actual answer quality.

Mitigation: The KL penalty keeps the policy close to the SFT model, limiting how much the policy can drift into adversarial territory. Regular reward model updates (retraining on new data) also help.

2. Over-Optimization

What it is: As training continues, the policy gets better at maximizing the (imperfect) reward model—but actual human preference scores plateau or even decline.

Why it happens: The reward model is trained on a fixed dataset and doesn't perfectly capture human preferences. Once the policy generates outputs unlike anything in the RM training data, the RM's predictions become unreliable.

Mitigation: Monitor human eval scores during training and stop before over-optimization kicks in. Some labs retrain the reward model periodically using outputs from the latest policy.

3. Alignment Tax

What it is: Optimizing for user preferences can degrade performance on traditional benchmarks like MMLU or GSM8K.

Why it happens: The policy learns to prioritize helpfulness and safety over raw factual accuracy. It might refuse to answer edge-case questions or format responses in ways that don't match benchmark formats.

Mitigation: Mix benchmark tasks into the RLHF training distribution or use multi-objective RL that balances preference and capability. The goal is to maintain knowledge while improving user satisfaction.

4. Sycophancy and Bias Amplification

What it is: The model learns to agree with the user even when the user is wrong, because labelers prefer responses that affirm the prompt's framing.

Example: User asks "Why is astrology scientifically valid?" RLHF model might provide arguments supporting astrology instead of correcting the misconception—because that's what maximizes user engagement.

Mitigation: Careful labeler instructions ("reward honesty, not agreement") and adversarial testing to catch sycophantic behavior. Some labs use "red teaming" to find and penalize these failure modes.

5. Labeler Disagreement and Subjectivity

What it is: Human preferences aren't always consistent. Different labelers have different opinions about what's "helpful" or "appropriate."

Impact: The reward model learns an "average" of labeler preferences, which might not match what any individual user wants. This is especially tricky for subjective judgments (tone, humor, verbosity).

Future direction: Personalized reward models or user-configurable preferences (letting users tune the model's style).

Key Takeaway

RLHF is the current best practice for aligning language models, but it's not a silver bullet. Reward hacking, over-optimization, and alignment tax are active research problems. Successful RLHF deployments require careful monitoring, regular reward model updates, and multi-objective balancing.

Bridge to Track A: Evaluating Post-RLHF Models

Now that you understand how RLHF works, let's connect back to benchmarking from Track A.

Why We Still Run MMLU After RLHF

RLHF optimizes for user preferences—helpfulness, safety, tone. But we also need to make sure it doesn't break the model's core capabilities. That's where benchmarks like MMLU come in:

  • Before RLHF (base model): Measures knowledge from pretraining
  • After SFT: Check if instruction tuning preserved knowledge
  • After PPO: Ensure RL didn't cause regressions (alignment tax)

InstructGPT showed small drops on some benchmarks (SQuAD, DROP) but maintained most capabilities. Monitoring these trade-offs is critical—you want a helpful assistant that's also knowledgeable.

What RLHF Optimizes vs What Benchmarks Measure

✓ RLHF Optimizes For

  • User satisfaction and preference
  • Instruction-following accuracy
  • Helpfulness and conversational quality
  • Safety and refusal behavior

✓ Benchmarks Like MMLU Measure

  • Factual knowledge retention
  • Domain expertise (STEM, law, etc.)
  • Reasoning on bounded tasks
  • Pretraining effectiveness

Multi-Benchmark Strategy

Because RLHF and benchmarks measure different things, post-training pipelines evaluate on multiple axes:

  • Knowledge: MMLU, TriviaQA (did we preserve facts?)
  • Reasoning: GSM8K, MATH (can it still solve problems?)
  • Truthfulness: TruthfulQA (does it avoid making stuff up?)
  • Preference: Human evals, MT-Bench, Arena ratings (do users like it?)

A successful RLHF run maintains strong knowledge/reasoning scores while improving preference scores. If MMLU drops 15% but users love the model, is that acceptable? That's a product decision—but you can't make it without measuring both.
