From Kata to Firecracker: The Minimal VMM

In Lesson 03, you saw that Kata Containers can use Firecracker as its hypervisor. But what is Firecracker, and why did AWS build it?

Firecracker is a minimal Virtual Machine Monitor (VMM) written in Rust. It's designed for one thing: launching thousands of lightweight microVMs with sub-second boot times and minimal memory overhead. From the Firecracker SPECIFICATION.md:

"It takes <= 125 ms to go from receiving the Firecracker InstanceStart API call to the start of the Linux guest user-space /sbin/init process."

And the memory overhead per VM? Per the same spec:

"Firecracker's virtual machine manager threads have a memory overhead <= 5 MiB."

These targets—125ms boot, 5 MiB overhead—are enforced by CI tests (test_boottime.py, memory.py).

What You'll Learn

  • What a VMM is and how KVM provides the hypervisor primitives (ioctl interface)
  • Firecracker's minimal device model: virtio-net, virtio-block, vsock, serial, and a minimal i8042 keyboard controller
  • The process/thread model: API thread, VMM thread, and vCPU threads (one per guest core)
  • The REST API over a Unix socket: boot-source, drives, network-interfaces, machine-config, actions InstanceStart
  • The jailer: chroot, namespaces, cgroups, seccomp filters, and privilege drop—tying back to Lessons 01–02
  • TAP networking: how the host's tap device backs virtio-net inside the guest
  • Why E2B, Fly Machines, AWS Lambda (Firecracker powers Lambda), and others use microVMs for eval orchestration
  • Hands-on: boot a Firecracker VM from scratch with curl and measure boot time

⚠️ KVM Required

Firecracker requires Linux with KVM (/dev/kvm). This means:

  • Bare metal: Works out of the box if KVM is enabled
  • Cloud VMs: Only .metal instance types (AWS c5.metal, m5d.metal, etc.) or cloud providers with nested virtualization enabled (some GCP/Azure VM families)
  • Your laptop VM: Enable nested virtualization in your hypervisor settings

If you don't have KVM, you can read the code and understand the concepts, but you won't be able to run the exercise. The Firecracker getting-started guide recommends an EC2 c5.metal instance with Ubuntu 24.04.

VMM Fundamentals: What is a Virtual Machine Monitor?

A Virtual Machine Monitor (VMM), also called a hypervisor, is software that creates and runs virtual machines. It sits between the guest OS (the VM's kernel) and the host hardware.

Type 1 vs Type 2 Hypervisors

  • Type 1 (bare-metal): Runs directly on the hardware. Examples: VMware ESXi, Xen, Hyper-V (when running in the host kernel).
  • Type 2 (hosted): Runs as a process in a host OS. Examples: VirtualBox, VMware Workstation, QEMU, Firecracker.

Firecracker is a Type 2 hypervisor—it runs as a Linux process. But it delegates the heavy lifting to the KVM kernel module.

KVM: The Linux Hypervisor

KVM (Kernel-based Virtual Machine) is a Linux kernel module (loadable with modprobe kvm_intel or kvm_amd) that turns the kernel into a hypervisor. It provides:

  • /dev/kvm: A character device that user-space programs (like Firecracker) open to create VMs
  • ioctl API: The VMM sends ioctl(2) commands to /dev/kvm to:
    • Create a VM (KVM_CREATE_VM)
    • Allocate guest memory (KVM_SET_USER_MEMORY_REGION)
    • Create vCPUs (KVM_CREATE_VCPU)
    • Run a vCPU (KVM_RUN)—this blocks until the guest exits (e.g., I/O, hypercall, or timer)
  • Hardware virtualization extensions: KVM uses Intel VT-x or AMD-V to run guest code directly on the CPU with hardware isolation. VM exits (hypercalls, I/O) trap into the host kernel, which returns control to the VMM process.

Why this matters for evals: KVM provides hardware isolation between the guest kernel and the host kernel. The guest cannot directly access host memory or devices. Compare this to containers (Lesson 01) where the guest makes syscalls directly to the shared host kernel, or gVisor (Lesson 03) where the Sentry intercepts syscalls in user space. With KVM, the guest kernel runs in its own context, and only hypercalls (guest → host kernel transitions) expose the host to attack.

What the VMM Must Emulate

A guest OS expects to interact with hardware devices: disks, network cards, serial ports, etc. The VMM must emulate these devices in software. When the guest writes to a disk, the VMM intercepts the I/O and writes to a file on the host. When the guest sends a network packet, the VMM writes it to a TAP device on the host.

Traditional VMMs like QEMU emulate a full PC: BIOS, PCI bus, IDE/SATA disks, e1000 NICs, VGA graphics, USB controllers, audio, etc. This is why QEMU can run Windows or any x86 OS unmodified.

Firecracker's philosophy: Emulate the absolute minimum needed to boot a modern Linux kernel and run workloads. No BIOS, no PCI, no graphics, no USB, no audio. Just:

  • virtio-net: Paravirtualized network device
  • virtio-block: Paravirtualized block device
  • virtio-vsock: Virtual socket for host-guest communication
  • Serial console: A single UART (usually disabled in production for speed)
  • i8042 keyboard controller: Minimal emulation to satisfy Linux's legacy device expectations

What is virtio? A standard for paravirtualized I/O devices (Linux virtio docs). Instead of emulating legacy hardware (e.g., e1000 NIC register-level behavior), virtio defines a ring buffer interface where the guest driver and the host VMM share memory. This is much faster than trap-and-emulate.

Firecracker Architecture

Source: github.com/firecracker-microvm/firecracker
Key files: src/vmm/, src/firecracker/, src/jailer/
Design doc: docs/design.md

One Process, One microVM

From design.md:

"Each Firecracker process encapsulates one and only one microVM. The process runs the following threads: API, VMM and vCPU(s)."

This is a key architectural choice. Unlike QEMU (which can run multiple VMs in one process with -machine accel=kvm and threading), Firecracker is one process per VM. This simplifies security (kill the process, kill the VM) and resource accounting (cgroups naturally scope to one VM).

Thread Model

Continuing from design.md:

  • API thread: Runs the HTTP server that listens on a Unix socket. Handles configuration requests (PUT /boot-source, PUT /drives, etc.). Never in the fast path once the VM is running.
  • VMM thread: Runs the main event loop (epoll-based). Emulates devices (virtio-net, virtio-block, serial console). When a vCPU exits to handle I/O, the VMM thread processes it.
  • vCPU threads: One thread per guest CPU core. Each vCPU thread calls KVM_RUN in a loop. The guest code runs here. On VM exit (I/O, timer, hypercall), the vCPU thread notifies the VMM thread (via eventfd) and blocks until the I/O is handled.

Device Model

From the Firecracker NSDI 2020 paper (Agache et al.):

"Firecracker's device model is intentionally minimal, supporting only virtio block devices, virtio net devices, a serial console, a one-button keyboard, and a partial RTC."

The "one-button keyboard" is a minimal i8042 keyboard controller emulation, not a full keyboard. It's there because Linux expects it during boot. The "partial RTC" is enough to let the guest read the time.

No graphics, no PCI bus, no USB. If the guest tries to access unsupported devices, the VM exits with an error or the guest kernel ignores them. This minimalism is why Firecracker's boot is so fast: there's nothing to initialize except virtio devices.

Memory Footprint

Per SPECIFICATION.md, the VMM threads consume <= 5 MiB of host memory. This does not include:

  • The guest's own RAM (which you configure via PUT /machine-config: {"vcpu_count": 1, "mem_size_mib": 128})
  • The Firecracker binary itself (statically linked musl binary, ~2 MiB on disk, mapped into memory)
  • The guest kernel and rootfs (loaded into the guest's memory)

Total overhead per VM: ~7–10 MiB of host memory beyond the guest's configured RAM. Compare this to Kata (50–150 MiB per VM for guest kernel + kata-agent) or gVisor (variable, but the Sentry is a full Go process).

Performance Targets

From SPECIFICATION.md (vendor claims, enforced by Firecracker's CI):

  • Boot time: <= 125 ms from InstanceStart to guest /sbin/init start. Measured with serial console disabled and a minimal kernel + rootfs.
  • Mutation rate: "5 microVMs per host core per second" (e.g., 180 VMs/s on a 36-core host)
  • Network throughput: "up to 14.5 Gbps" using <= 80% of one host core for emulation; "up to 25 Gbps" at 100% core usage
  • Storage throughput: "up to 1 GiB/s" using <= 70% of one host core
  • CPU overhead: "The compute-only guest CPU performance is > 95% of the equivalent bare-metal performance"

These are best-case numbers on AWS M5D.metal and M6G.metal instances. Your mileage will vary, but the design goal is clear: near-native performance with minimal overhead.

The REST API: Configuring a microVM

Firecracker exposes a REST API over a Unix socket. The API is defined in src/firecracker/swagger/firecracker.yaml (OpenAPI spec).

Typical Workflow

  1. Start Firecracker: ./firecracker --api-sock /tmp/firecracker.socket. The process starts and listens on the socket. The API thread is ready, but no VM is configured yet.
  2. Configure the guest kernel: PUT /boot-source with JSON: 
    {
  "kernel_image_path": "/path/to/vmlinux",
  "boot_args": "console=ttyS0 reboot=k panic=1 pci=off"
}
  3. Configure the root filesystem: PUT /drives/rootfs with JSON: 
    {
  "drive_id": "rootfs",
  "path_on_host": "/path/to/rootfs.ext4",
  "is_root_device": true,
  "is_read_only": false
}
  4. Configure machine resources: PUT /machine-config with JSON: 
    {
  "vcpu_count": 1,
  "mem_size_mib": 128
}
  5. (Optional) Configure networking: PUT /network-interfaces/eth0 with JSON: 
    {
  "iface_id": "eth0",
  "guest_mac": "AA:FC:00:00:00:01",
  "host_dev_name": "tap0"
}
  6. Start the VM: PUT /actions with JSON: 
    {
  "action_type": "InstanceStart"
}
    This is the InstanceStart action. The VMM thread creates the VM via KVM, maps guest memory, loads the kernel, creates vCPU threads, and runs KVM_RUN. The 125ms timer starts here.

Example: curl Commands

The Unix socket speaks HTTP. You can use curl --unix-socket: 

# Set boot source
curl --unix-socket /tmp/firecracker.socket -X PUT \
  http://localhost/boot-source \
  -H "Content-Type: application/json" \
  -d '{
    "kernel_image_path": "/path/to/vmlinux",
    "boot_args": "console=ttyS0 reboot=k panic=1 pci=off"
  }'

# Set rootfs
curl --unix-socket /tmp/firecracker.socket -X PUT \
  http://localhost/drives/rootfs \
  -H "Content-Type: application/json" \
  -d '{
    "drive_id": "rootfs",
    "path_on_host": "/path/to/rootfs.ext4",
    "is_root_device": true,
    "is_read_only": false
  }'

# Set machine config
curl --unix-socket /tmp/firecracker.socket -X PUT \
  http://localhost/machine-config \
  -H "Content-Type: application/json" \
  -d '{
    "vcpu_count": 1,
    "mem_size_mib": 128
  }'

# Start the VM
curl --unix-socket /tmp/firecracker.socket -X PUT \
  http://localhost/actions \
  -H "Content-Type: application/json" \
  -d '{
    "action_type": "InstanceStart"
  }'

Other Actions

  • Pause: {"action_type": "SendCtrlAltDel"} — sends Ctrl+Alt+Del to the guest (triggers a clean shutdown)
  • CreateSnapshot: Snapshot the VM's memory and device state (see snapshot-support.md)
  • LoadSnapshot: Restore a VM from a snapshot

Why a REST API?

From the NSDI paper:

"Firecracker's control plane is a simple REST API, making it easy to integrate with existing orchestration systems. The API is stateless: each request is self-contained, and there is no session state. This simplifies retry logic and error handling."

The API also enforces immutability: once you call InstanceStart, you can't change the boot source or drives. You must stop the VM and start a new one. This simplifies the VMM's state machine.

The Jailer: Lessons 01–02 in Action

Source: src/jailer/
Documentation: docs/jailer.md

In production, you never run Firecracker directly. You run it via the jailer, a separate binary that sets up an execution jail before execing the Firecracker binary. From jailer.md:

"The jailer is a program designed to isolate the Firecracker process in order to enhance Firecracker's security posture."

What the Jailer Does

The jailer applies all the primitives you learned in Lessons 01 and 02:

  1. chroot jail: Creates a new root at /srv/jailer/firecracker/<id>/root (configurable with --chroot-base-dir). Copies the Firecracker binary into the jail. Uses pivot_root(2) to switch to the new root and chroot(2) to lock it in. The Firecracker process cannot access files outside the jail.
  2. Namespaces: Calls unshare(2) to enter new mount and (optionally) PID namespaces. Optionally joins a network namespace via --netns. (Lesson 01: namespaces isolate resources.)
  3. cgroups: Creates cgroup v1 or v2 hierarchies (Lesson 01: cgroups limit resources). You pass --cgroup cpuset.cpus=0 or --cgroup memory.max=134217728 to the jailer, and it writes these limits before starting Firecracker. The Firecracker process and its children inherit the cgroup.
  4. seccomp-bpf: Applies a strict seccomp filter (Lesson 02: syscall filtering). Firecracker's default seccomp filter allows only ~60 syscalls. See src/firecracker/src/seccomp.rs and the JSON filter definitions in resources/seccomp/. The filter is architecture-specific (x86_64, aarch64).
  5. Privilege drop: Calls setuid(2) and setgid(2) to drop to a non-root user (you specify --uid and --gid). This ensures Firecracker runs as an unprivileged user inside the jail.
  6. Resource limits: Calls setrlimit(2) to set RLIMIT_FSIZE (max file size) and RLIMIT_NOFILE (max open files). Default: no-file=2048.
  7. /dev/kvm and /dev/net/tun: Uses mknod(2) to create /dev/kvm and /dev/net/tun inside the jail, then chowns them to the target uid:gid. Firecracker can access these devices (read/write to /dev/kvm for KVM ioctls, read/write to /dev/net/tun for TAP networking) but nothing else.

Example Jailer Invocation

jailer \
  --id my-microvm-001 \
  --exec-file /usr/local/bin/firecracker \
  --uid 1000 \
  --gid 1000 \
  --cgroup-version 2 \
  --cgroup memory.max=134217728 \
  --cgroup cpu.max="50000 100000" \
  --netns /var/run/netns/my-netns \
  --resource-limit no-file=1024 \
  --new-pid-ns \
  -- --api-sock ./firecracker.socket

This invocation:

  • Creates a jail at /srv/jailer/firecracker/my-microvm-001/root
  • Copies /usr/local/bin/firecracker into the jail
  • Creates cgroup v2 limits: 128 MiB memory, 50% CPU (50ms per 100ms period)
  • Joins the network namespace /var/run/netns/my-netns
  • Drops to uid=1000, gid=1000
  • Applies seccomp filters
  • Execs firecracker --api-sock ./firecracker.socket (relative to the jail root)

How This Ties to Lessons 01–02

  • Lesson 01: The jailer uses unshare(2) for namespaces, writes to /sys/fs/cgroup/ for cgroups, and calls pivot_root(2) + chroot(2) for filesystem isolation. You built a minimal sandbox with these primitives; the jailer does the same for Firecracker.
  • Lesson 02: The jailer applies seccomp-bpf filters (allow ~60 syscalls, block the rest) and uses mknod(2) + chown(2) to create device nodes inside the jail. You learned how seccomp filters work; Firecracker's filters are production-grade examples you can study in resources/seccomp/*.json.

Defense in Depth

Even with hardware virtualization (KVM), Firecracker layers multiple defenses:

  1. Hardware isolation (KVM): The guest kernel runs in its own address space. Hypercalls are the only attack surface.
  2. Minimal device model: Fewer emulated devices = smaller attack surface. No graphics, no USB, no PCI bus.
  3. Seccomp: The Firecracker process itself can only make ~60 syscalls. Even if an attacker escapes the VM, they're still in a seccomp jail.
  4. chroot + namespaces: The process can't see the host filesystem or other network namespaces.
  5. cgroups: Resource exhaustion attacks are bounded by memory and CPU limits.
  6. Unprivileged user: The process runs as uid=1000 (or whatever you set), not root.

This is the model AWS uses for Lambda: thousands of tenants' functions run on shared hardware, isolated by Firecracker + the jailer.

TAP Networking: Connecting the Guest to the Host

Documentation: docs/network-setup.md

Firecracker emulates a virtio-net device inside the guest. The guest's virtio-net driver sends packets to the VMM via a ring buffer (shared memory). The VMM writes these packets to a TAP device on the host.

What is a TAP Device?

A TAP device (tap0, tap1, etc.) is a virtual Ethernet interface. It looks like a normal NIC to the kernel, but packets written to it go to a user-space program (in this case, Firecracker) instead of physical hardware.

  • TUN: Layer 3 (IP packets)
  • TAP: Layer 2 (Ethernet frames)

Firecracker uses TAP because virtio-net is a layer-2 device (Ethernet). The guest sends Ethernet frames, and Firecracker writes them to tap0.

Setting Up TAP Networking

From network-setup.md: 

# Create the tap device
sudo ip tuntap add tap0 mode tap

# Assign it an IP and bring it up
sudo ip addr add 172.16.0.1/30 dev tap0
sudo ip link set tap0 up

# Enable IPv4 forwarding
echo 1 | sudo tee /proc/sys/net/ipv4/ip_forward

# Set up NAT (using nftables)
sudo nft add table firecracker
sudo nft 'add chain firecracker postrouting { type nat hook postrouting priority srcnat; policy accept; }'
sudo nft 'add chain firecracker filter { type filter hook forward priority filter; policy accept; }'

# Masquerade packets from the guest (172.16.0.2) as if they came from the host
sudo nft add rule firecracker postrouting ip saddr 172.16.0.2 oifname eth0 counter masquerade

# Forward packets from tap0 to eth0
sudo nft add rule firecracker filter iifname tap0 oifname eth0 accept
sudo nft add rule firecracker filter iifname eth0 oifname tap0 ct state related,established accept

What this does:

  • The guest will configure itself with IP 172.16.0.2 and gateway 172.16.0.1 (the TAP IP).
  • When the guest sends a packet to the Internet, it goes to tap0.
  • The host's nftables rules masquerade the packet (change source IP from 172.16.0.2 to the host's IP) and forward it to eth0.
  • Return packets (marked established by conntrack) are forwarded back to tap0.

Guest Network Configuration

Inside the guest, you configure the network manually or via a startup script: 

# Inside the guest
ip addr add 172.16.0.2/30 dev eth0
ip link set eth0 up
ip route add default via 172.16.0.1

# Test connectivity
ping 8.8.8.8

Networking in Multi-Tenant Environments

For production eval orchestration:

  • One TAP per VM: Each Firecracker VM gets its own tap0, tap1, etc.
  • Network namespaces (Lesson 01): You can put each TAP in a separate netns to isolate VMs from each other. The jailer's --netns flag joins that namespace.
  • Egress filtering: Use nftables or iptables to block outbound traffic by default, then allowlist specific domains (E2B, Modal, Daytona all do this). See E2B's nftables config in e2b-dev/infra.
  • No ingress by default: The guest has a private IP (172.16.0.2) and is NATed. External traffic can't reach it unless you set up port forwarding (which you typically don't for sandboxes).

Eval Orchestration Context: Why microVMs?

Now that you understand Firecracker's architecture, why do eval systems use it?

Who Uses Firecracker for Evals/Sandboxes

  • AWS Lambda: All Lambda functions run in Firecracker microVMs. From the NSDI paper: "Firecracker [...] is the foundation of AWS Lambda and AWS Fargate." Lambda's cold-start time includes Firecracker boot.
  • E2B (e2b-dev/runtime): Uses Firecracker directly for agent sandboxes. Supports snapshot/restore and fork (one VM to step k, then fork N children). See the e2b-dev/infra repo for their Terraform + nftables setup.
  • Fly Machines: Fly.io's compute product uses Firecracker. From Fly Machines docs: "Fly Machines are Firecracker microVMs." They support fast stop/start (pause/resume) and per-second billing.
  • Kata Containers: Can use Firecracker as its hypervisor (Lesson 03). E.g., kata-runtime --hypervisor firecracker.
  • Northflank: CPU sandboxes run on Kata (Lesson 03), which may use Firecracker or Cloud Hypervisor under the hood.

Why microVMs over Containers?

From Lesson 03, you know the isolation trade-off:

  • runc (containers): Shared kernel. One kernel vuln = escape. Fast but risky for untrusted code.
  • gVisor: Userspace kernel (Sentry) intercepts syscalls. Safer than runc, but overhead on I/O and syscall-heavy workloads. Great for GPU (nvproxy).
  • Firecracker (microVMs): Hardware isolation via KVM. Strongest isolation. Overhead is boot time (~125ms) and per-VM memory (~7–10 MiB). No GPU support (unlike gVisor or Kata+QEMU).

When to use Firecracker for evals:

  • Multi-tenant, untrusted code: You're running code from different users on shared hardware. Lambda's threat model.
  • Fast warm pools via snapshots: Boot a VM to a base state, snapshot it, restore N copies. E2B does this for agent environments.
  • Fork-on-demand: Run an agent to step k, snapshot, fork N children with different sampling (GRPO, tree search). E2B's fork API.
  • No GPU needed: If your eval doesn't need GPU inside the sandbox, Firecracker is a good fit. If you need GPU, use gVisor or Kata+QEMU.
  • Pause/resume billing: Firecracker's snapshot/restore lets you pause a VM (save its state) and resume later. Fly Machines does this for per-second billing.

The Snapshot/Fork Workflow (Preview of Lesson 05)

This is a teaser; Lesson 05 covers it in depth. The workflow:

  1. Boot a base VM: Firecracker + rootfs + dependencies preloaded.
  2. Snapshot it: PUT /actions {"action_type": "CreateSnapshot"}. Firecracker writes guest memory to a file and device state to a JSON file.
  3. For each new eval: PUT /actions {"action_type": "LoadSnapshot"} to restore the snapshot. Boot time drops from ~125ms to ~10ms (memory is already paged in).
  4. For forking: Run the agent to step k, snapshot, restore N times with different RNG seeds or policies. Handle clone hazards: reseed RNGs, update MAC addresses, bump VMGenID (guest VM generation counter).

Why this is faster than containers: A container image pull takes seconds (hundreds of MB). A Firecracker snapshot is already in memory. Restoring it is a memory copy + KVM VM creation, which takes milliseconds.

Build It Yourself: Boot Firecracker by Hand

In this exercise, you'll download Firecracker, get a guest kernel and rootfs, boot a VM via the REST API, set up TAP networking, and measure the boot time. You'll see the 125ms target in action.

⚠️ Prerequisites

  • Linux host with KVM: Check ls -l /dev/kvm. You need read/write access. See getting-started.md for setup.
  • Bare metal or nested virt: Cloud VMs need .metal instance types or nested virt enabled.
  • curl, jq, Python 3: For API calls and scripting.

If you don't have KVM, you can read the code and understand the workflow, but you won't be able to run it.

Step 1: Download Firecracker and Resources

We'll use the official CI kernel and rootfs from the getting-started guide. Create setup_firecracker.sh: 

#!/bin/bash
set -euo pipefail

# Create a working directory
mkdir -p firecracker-demo
cd firecracker-demo

# Detect architecture
ARCH=$(uname -m)
echo "Architecture: $ARCH"

# Download Firecracker binary (latest release)
FC_VERSION="v1.9.1"  # Update to latest stable version
FC_URL="https://github.com/firecracker-microvm/firecracker/releases/download/${FC_VERSION}/firecracker-${FC_VERSION}-${ARCH}.tgz"

echo "Downloading Firecracker $FC_VERSION..."
curl -L "$FC_URL" -o firecracker.tgz
tar -xzf firecracker.tgz
mv release-${FC_VERSION}-${ARCH}/firecracker-${FC_VERSION}-${ARCH} firecracker
chmod +x firecracker

# Download guest kernel (from Firecracker CI artifacts)
# These are minimal kernels built for fast boot
KERNEL_URL="https://s3.amazonaws.com/spec.ccfc.min/firecracker-ci/v1.9/${ARCH}/vmlinux-5.10.217"
echo "Downloading guest kernel..."
curl -L "$KERNEL_URL" -o vmlinux

# Download rootfs (Ubuntu 22.04, minimal)
ROOTFS_URL="https://s3.amazonaws.com/spec.ccfc.min/firecracker-ci/v1.9/${ARCH}/ubuntu-22.04.ext4"
echo "Downloading rootfs..."
curl -L "$ROOTFS_URL" -o rootfs.ext4

echo "Setup complete!"
echo "Files:"
ls -lh firecracker vmlinux rootfs.ext4

Run it: 

chmod +x setup_firecracker.sh
./setup_firecracker.sh

Note: The kernel and rootfs URLs are from Firecracker's CI. They're minimal and not intended for production, but they're perfect for testing. If the URLs break, check the getting-started.md for updated links.

Step 2: Boot Script with curl

Create boot_firecracker.sh: 

#!/bin/bash
set -euo pipefail

cd firecracker-demo

# Start Firecracker in the background
# API socket at ./firecracker.socket
rm -f firecracker.socket
./firecracker --api-sock firecracker.socket &
FC_PID=$!
echo "Started Firecracker (PID $FC_PID)"

# Wait for the socket to be ready
echo "Waiting for API socket..."
for i in {1..10}; do
    if [ -S firecracker.socket ]; then
        break
    fi
    sleep 0.1
done

if [ ! -S firecracker.socket ]; then
    echo "ERROR: API socket not ready"
    kill $FC_PID 2>/dev/null || true
    exit 1
fi

# Function to call the API
api_call() {
    local method=$1
    local path=$2
    local data=$3
    curl --unix-socket firecracker.socket \
        -X "$method" \
        "http://localhost$path" \
        -H "Content-Type: application/json" \
        -d "$data"
    echo ""
}

# Configure boot source
echo "Configuring boot source..."
api_call PUT /boot-source '{
  "kernel_image_path": "'$(pwd)'/vmlinux",
  "boot_args": "console=ttyS0 reboot=k panic=1 pci=off"
}'

# Configure rootfs
echo "Configuring rootfs..."
api_call PUT /drives/rootfs '{
  "drive_id": "rootfs",
  "path_on_host": "'$(pwd)'/rootfs.ext4",
  "is_root_device": true,
  "is_read_only": false
}'

# Configure machine (1 vCPU, 128 MiB RAM)
echo "Configuring machine..."
api_call PUT /machine-config '{
  "vcpu_count": 1,
  "mem_size_mib": 128
}'

# Start the VM
echo "Starting VM..."
START_TIME=$(date +%s%3N)  # milliseconds
api_call PUT /actions '{
  "action_type": "InstanceStart"
}'
END_TIME=$(date +%s%3N)

BOOT_TIME=$((END_TIME - START_TIME))
echo "InstanceStart call took: ${BOOT_TIME}ms"

# The VM is now running. The Firecracker process is still alive.
# To interact with the guest, you'd need a serial console or network.
# For this demo, we'll just measure the boot time and stop.

echo ""
echo "VM is running. Firecracker PID: $FC_PID"
echo "To stop: kill $FC_PID"
echo ""
echo "Boot time from InstanceStart call: ${BOOT_TIME}ms"
echo "(Note: This is the API call latency, not the full guest boot time.)"
echo "The SPECIFICATION.md target is <= 125ms from InstanceStart to /sbin/init."

Run it: 

chmod +x boot_firecracker.sh
./boot_firecracker.sh

Step 3: Measuring Full Boot Time

The script above measures the InstanceStart API call latency, not the full guest boot time. To measure the full time to /sbin/init, you'd need to instrument the guest (e.g., add a systemd unit that writes to the serial console when init starts, then capture that in the host). Firecracker's CI does this in test_boottime.py.

For this exercise, we'll trust the spec's claim: <= 125ms from InstanceStart to /sbin/init start. You can verify this by reading the CI test.

Step 4 (Optional): Add TAP Networking

If you want to add networking, create a TAP device first: 

sudo ip tuntap add tap0 mode tap
sudo ip addr add 172.16.0.1/30 dev tap0
sudo ip link set tap0 up

Then add this API call before InstanceStart: 

api_call PUT /network-interfaces/eth0 '{
  "iface_id": "eth0",
  "guest_mac": "AA:FC:00:00:00:01",
  "host_dev_name": "tap0"
}'

Inside the guest, you'd configure the network manually (you'd need to attach to the serial console or use a startup script in the rootfs).

Step 5: Python Client (Alternative)

If you prefer Python, here's a minimal client using http.client with a Unix socket: 

#!/usr/bin/env python3
"""
Minimal Firecracker API client using Unix socket.
"""
import http.client
import json
import socket
import time


class FirecrackerClient:
    def __init__(self, socket_path):
        self.socket_path = socket_path
    
    def _call(self, method, path, data=None):
        # http.client doesn't support Unix sockets directly, so we use socket
        sock = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
        sock.connect(self.socket_path)
        
        body = json.dumps(data) if data else ""
        body_bytes = body.encode('utf-8')
        
        request = (
            f"{method} {path} HTTP/1.1\r\n"
            f"Host: localhost\r\n"
            f"Content-Type: application/json\r\n"
            f"Content-Length: {len(body_bytes)}\r\n"
            f"\r\n"
        ).encode('utf-8')
        
        sock.sendall(request + body_bytes)
        
        # Read response (simple parser; production would use http.client.HTTPResponse)
        response = b""
        while True:
            chunk = sock.recv(4096)
            if not chunk:
                break
            response += chunk
            if b"\r\n\r\n" in response:
                break
        
        sock.close()
        
        # Parse status line
        status_line = response.split(b"\r\n")[0].decode('utf-8')
        status_code = int(status_line.split()[1])
        
        return status_code, response
    
    def put(self, path, data):
        return self._call("PUT", path, data)


def main():
    import sys
    import os
    import subprocess
    
    os.chdir("firecracker-demo")
    
    # Start Firecracker
    if os.path.exists("firecracker.socket"):
        os.remove("firecracker.socket")
    
    fc_proc = subprocess.Popen(
        ["./firecracker", "--api-sock", "firecracker.socket"],
        stdout=subprocess.DEVNULL,
        stderr=subprocess.DEVNULL
    )
    print(f"Started Firecracker (PID {fc_proc.pid})")
    
    # Wait for socket
    for _ in range(50):
        if os.path.exists("firecracker.socket"):
            break
        time.sleep(0.1)
    else:
        print("ERROR: Socket not ready")
        fc_proc.kill()
        return
    
    client = FirecrackerClient("firecracker.socket")
    
    # Configure
    print("Configuring boot source...")
    client.put("/boot-source", {
        "kernel_image_path": f"{os.getcwd()}/vmlinux",
        "boot_args": "console=ttyS0 reboot=k panic=1 pci=off"
    })
    
    print("Configuring rootfs...")
    client.put("/drives/rootfs", {
        "drive_id": "rootfs",
        "path_on_host": f"{os.getcwd()}/rootfs.ext4",
        "is_root_device": True,
        "is_read_only": False
    })
    
    print("Configuring machine...")
    client.put("/machine-config", {
        "vcpu_count": 1,
        "mem_size_mib": 128
    })
    
    # Start
    print("Starting VM...")
    start_ms = int(time.time() * 1000)
    client.put("/actions", {"action_type": "InstanceStart"})
    end_ms = int(time.time() * 1000)
    
    boot_time = end_ms - start_ms
    print(f"InstanceStart call took: {boot_time}ms")
    print(f"VM is running. Firecracker PID: {fc_proc.pid}")
    print("To stop: kill", fc_proc.pid)


if __name__ == "__main__":
    main()

Expected Results

  • InstanceStart API call latency: 10–50ms (depends on your CPU and I/O). This is not the full boot time; it's how long the API call takes to return.
  • Full boot time (InstanceStart → /sbin/init): <= 125ms per the spec. You'd need to instrument the guest to measure this precisely (see Firecracker's CI test).
  • Memory overhead: Check ps aux | grep firecracker. The VSZ will be large (guest RAM + host overhead), but the RSS should be small (~5–10 MiB for the VMM threads, plus 128 MiB for the guest's RAM).
