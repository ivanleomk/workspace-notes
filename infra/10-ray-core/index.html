From Single-Machine Sandboxes to Distributed Orchestration

In Lessons 01–09, you mastered the isolation layer: containers (runc), microVMs (Firecracker), userspace kernels (gVisor), and sandbox platforms (E2B, Modal, Daytona). You know how to create, pause, resume, and fork individual sandboxes. But when you need to run 10,000 evals across 100 machines, or orchestrate RL rollouts with 1,000 concurrent actors collecting experience while 8×H100 GPUs train a policy, you need a distributed runtime that handles scheduling, data movement, failure recovery, and coordination.

Ray (github.com/ray-project/ray, Apache-2.0) is that distributed runtime. Developed at UC Berkeley's RISELab and maintained by Anyscale, Ray provides three core abstractions: tasks (stateless remote functions), actors (stateful workers), and ObjectRefs (distributed futures). Tasks and actors run on a cluster of workers, share data via a distributed object store, and are coordinated by the Global Control Service (GCS).

What You'll Learn

  • Why you need a distributed runtime for eval/rollout orchestration (beyond asyncio on one machine)
  • Ray's cluster architecture: head node (GCS), worker nodes (raylet + object store + workers)

  • Actors: stateful workers, async actors, max_concurrency, concurrency groups

  • How real systems use Ray for RL (verl, OpenRLHF) and when plain asyncio beats Ray
  • Hands-on: Build an async actor pool for fake-sandbox evals with streaming results, retries, and object-store broadcast

Ray Cluster Architecture

From the Ray 2.0 Architecture Whitepaper:

"A Ray cluster consists of one or more worker nodes, each of which consists of the following physical processes: (1) One or more worker processes, responsible for task submission and execution. [...] (2) A raylet. The raylet manages shared resources on each node. [...] One of the worker nodes is designated as the head node. In addition to the above processes, the head node also hosts: (1) The Global Control Service (GCS). [...] (2) The driver process(es). [...] (3) Other cluster-level services that handle job submission, autoscaling, etc."

Head Node

The head node hosts:

  • Global Control Service (GCS): The cluster control plane. Manages cluster-level metadata (actor locations, node membership, placement groups), stored as key-value pairs. In Ray 2.0+, GCS can be fault-tolerant with Redis-backed persistence (whitepaper). Source: src/ray/gcs/gcs_server/.
  • Driver process: A special worker that executes __main__, submits tasks, but cannot execute tasks itself. Drivers can run on any node but usually run on the head node.
  • Cluster services: Job submission API, autoscaler, dashboard (port 8265).

Worker Nodes

Each worker node (including the head node) runs:

  • Worker processes: Python/Java/C++ processes that execute tasks and actor methods. Each worker stores: (a) An ownership table (system metadata for objects the worker has a reference to, e.g., ref counts and object locations), (b) An in-process store (for small objects, inlined return values). Default: one worker per CPU core. Source: src/ray/core_worker/core_worker.h.
  • Raylet: One per node, manages resources and object store. Has two main components:
    • Scheduler: Resource management, task placement, and fulfilling task arguments from the object store. Raylets coordinate to form the distributed scheduler.
    • Shared-memory object store: Also known as the Plasma Object Store. Stores, transfers, and spills large objects. Multiple object stores across nodes form the distributed object store.
    Source: src/ray/raylet/.

How Components Communicate

From Ray 2.0 Architecture Whitepaper:

"Each worker process and raylet is assigned a unique 28-byte identifier and an IP address and port. [...] Worker processes fate-share with their local raylet process."

Workers and raylets communicate via gRPC. The GCS uses Redis (or in-memory storage for non-HA setups) to store cluster metadata. Object transfers between nodes use the raylet's object manager (source: src/ray/object_manager/).

Tasks: Stateless Remote Functions

Tasks are Ray's unit of work: a stateless function that runs on a worker, returns a result, and can be retried if it fails. You define a task with @ray.remote and invoke it with .remote(...), which immediately returns an ObjectRef (a distributed future).

Basic Task Example

import ray

ray.init()  # Start a local Ray cluster

@ray.remote
def square(x):
    return x * x

# Submit tasks
futures = [square.remote(i) for i in range(5)]
# futures = [ObjectRef(...), ObjectRef(...), ...]

# Get results (blocking until tasks complete)
results = ray.get(futures)
print(results)  # [0, 1, 4, 9, 16]

Task Lifecycle

From Ray docs: Task Lifecycle (written for a newer Ray; Ray 2.40.0 uses the same basic flow):

  1. Submission: Driver calls task.remote(...). CoreWorker creates a task spec, assigns an ObjectRef for the return value, and sends a RequestWorkerLease RPC to a raylet (local or remote based on locality).
  2. Scheduling: The raylet's scheduler picks a worker based on resource availability (CPU, GPU, memory, custom resources). If the task needs objects not present locally, the raylet fetches them from other nodes' object stores.
  3. Execution: The owner sends a PushTask RPC directly to the leased worker. The worker deserializes the task spec, runs the function, serializes the return value, and stores it in the object store (or inlines it if small).
  4. Completion: The worker notifies the owner (the worker that created the ObjectRef) that the object is ready. The owner updates its ownership table with the object's location.

ObjectRefs and ray.get / ray.wait

An ObjectRef is a reference to a Ray object (task return value or ray.put object). It encodes a 28-byte object ID (per the whitepaper: "A unique 28-byte identifier ... The address of the object's owner"). From Ownership paper (NSDI 2021):

"a distributed future is a reference whose eventual value may be stored on a remote node"

and "the caller of a task is the owner of the returned future and all related metadata."

ray.get(object_refs): Blocks until objects are available, then returns their values. If an object is not on the local node, Ray fetches it from the owning node. Source: python/ray/_private/worker.py, line ~2755 (invokes C++ CoreWorker get_objects).

ray.wait(object_refs, num_returns=1, timeout=None): Returns (ready, remaining) tuples. Non-blocking if timeout=0. Use this to stream results as tasks complete (pseudocode; slow_task is not defined): 

pending = [slow_task.remote(i) for i in range(100)]

while pending:
    ready, pending = ray.wait(pending, num_returns=1, timeout=None)
    result = ray.get(ready[0])
    print(f"Task {result['id']} completed")
    # Process result immediately, don't wait for all 100 tasks

Task Options

Tasks can specify resource requirements: 

@ray.remote(num_cpus=2, num_gpus=0.5, memory=4*1024*1024*1024)  # 4 GiB
def heavy_task(data):
    return process(data)

# Or per-call:
future = heavy_task.options(num_cpus=4).remote(large_data)

Resource requirements are tracked by the raylet scheduler. A task with num_gpus=1 will only run on a node with available GPU resources.

Actors: Stateful Workers

Actors are stateful workers: a long-running process with mutable state. Unlike tasks (which are stateless and can run on any worker), an actor is a dedicated worker that executes methods in order (by default) and preserves state across method calls.

Basic Actor Example

@ray.remote
class Counter:
    def __init__(self, start=0):
        self.value = start
    
    def increment(self):
        self.value += 1
        return self.value
    
    def get_value(self):
        return self.value

# Create actor (GCS places it on a worker node)
counter = Counter.remote(start=10)

# Call methods (returns ObjectRefs)
futures = [counter.increment.remote() for _ in range(5)]
values = ray.get(futures)
print(values)  # [11, 12, 13, 14, 15]

final = ray.get(counter.get_value.remote())
print(final)  # 15

Actor Lifecycle

From Ray 2.0 Architecture Whitepaper:

From the whitepaper, the actor creation process:

"When an actor is created in Python, the creating worker builds a special task known as an actor creation task ... the creating worker asynchronously registers the actor with the GCS. The GCS then creates the actor by scheduling the actor creation task."

and "the Python call to create the actor immediately returns an 'actor handle'". The handle returns immediately, before the actor creation completes on a worker node.

Actor methods are submitted to the actor's mailbox (a queue on the actor worker). By default, methods execute sequentially (one at a time). If the actor dies, Ray can restart it (up to max_restarts times) and replay pending methods (replaying also requires max_task_retries to be set; default is 0).

Async Actors and max_concurrency

For I/O-bound workloads (e.g., calling sandbox APIs, database queries), use async actors with max_concurrency to run multiple methods concurrently: 

@ray.remote
class AsyncSandboxPool:
    def __init__(self, max_concurrency=10):
        self.max_concurrency = max_concurrency
        self.completed = 0
    
    async def exec_sandbox(self, item_id):
        # Simulate I/O-bound sandbox exec
        await asyncio.sleep(0.5)
        self.completed += 1
        return {"item_id": item_id, "status": "success"}

# Create async actor with concurrency limit
pool = AsyncSandboxPool.options(max_concurrency=10).remote()

# Submit 100 items; up to 10 execute concurrently in the actor
futures = [pool.exec_sandbox.remote(i) for i in range(100)]
results = ray.get(futures)

From Ray docs: AsyncIO / Concurrency for Actors, for async actors: "By default, 1000 tasks can be running concurrently." From Concurrency Groups:

"there is always a default concurrency group for actors, which has a default concurrency of 1000 AsyncIO actors and 1 otherwise."

Source: Actor task scheduling and concurrency logic live in src/ray/core_worker/transport/ (actor scheduling queues, concurrency group manager).

Concurrency Groups

You can partition actor methods into concurrency groups, each with its own concurrency limit. From Ray docs: Limiting Concurrency Per-Method with Concurrency Groups: 

@ray.remote(concurrency_groups={"io": 5, "compute": 2})
class EvalActor:
    @ray.method(concurrency_group="io")
    async def fetch_data(self, url):
        # Up to 5 fetch_data calls run concurrently
        ...
    
    @ray.method(concurrency_group="compute")
    def process(self, data):
        # Up to 2 process calls run concurrently
        ...
    
    async def health_check(self):
        # Default group (max_concurrency=1000 for async actors)
        ...

actor = EvalActor.options(max_concurrency=10).remote()  # Sets default group to 10

Use concurrency groups to prioritize health checks (high concurrency) while rate-limiting expensive operations (low concurrency).

The Distributed Object Store

Ray's distributed object store is where task return values, ray.put objects, and actor state are stored. It consists of:

  • Per-node shared-memory store: Derived from Apache Arrow Plasma, stores large objects (>100 KB) in /dev/shm on Linux. Workers on the same node share objects via zero-copy memory-mapped files.
  • In-process store: Each worker has an in-process store for small objects (≤100 KB). These are inlined in task RPCs and stored in the owner's heap.
  • Spilling to disk: When the shared-memory store is full, Ray automatically spills objects to local disk (or S3). No application changes needed.

Small vs Large Objects

From src/ray/common/ray_config_def.h, lines 197-199: 

// The max allowed size in bytes of a return object from direct actor calls.
// Objects larger than this size will be spilled/promoted to plasma.
RAY_CONFIG(int64_t, max_direct_call_object_size, 100 * 1024)

100 KB threshold: Objects ≤100 KB are inlined (stored in the owner's in-process store). Objects >100 KB go to the shared-memory Plasma store. This default can be changed at ray.init() with _system_config={"max_direct_call_object_size": ...}.

Why the threshold? Small objects have low serialization cost and fit in gRPC messages (avoiding shared-memory coordination). Large objects benefit from zero-copy shared memory: multiple workers can read the same object without copying.

Shared-Memory Store (Plasma)

From Ray docs: Memory Management:

"By default, when starting an instance, Ray reserves 30% of available memory. The size of the object store can be controlled by --object-store-memory."

On Linux, Ray allocates Plasma in /dev/shm. On macOS, it uses /tmp (on disk, slower). Default object store size: 30% of total RAM, capped at 2 GB on macOS (per ray_constants.py: "Mac with 16GB memory has degraded performance when the object store size is greater than 2GB").

Source: src/ray/object_manager/plasma/store.cc (Plasma store implementation).

Object Spilling to Disk

When the Plasma store is full, Ray automatically spills objects to external storage (local disk by default, or S3). From Ray docs: Object Spilling (this page targets a newer Ray than 2.40.0; the mechanism is the same):

"When memory pressure is detected, when pinned objects are automatically spilled from shared memory to external storage (local disk or S3). When a spilled object is needed again, it is transparently restored back into Plasma. [...] Object spilling is fully abstracted away to user applications. No application-level code changes are needed."

Configure spill directory (per Ray 2.40.0 docs): 

import json
ray.init(_system_config={
    "object_spilling_config": json.dumps({
        "type": "filesystem",
        "params": {"directory_path": "/tmp/spill"}
    })
})

When does spilling happen? The raylet's LocalObjectManager triggers spilling when Plasma allocation fails. It identifies spillable objects (objects with ref count == 1, meaning only the owner holds a reference), writes them to disk, and frees Plasma memory. Source: src/ray/raylet/local_object_manager.cc.

Broadcast Pattern: ray.put Once, Share Everywhere

For eval orchestration, you often have large shared inputs (test datasets, reference data, model weights). Use ray.put to store the object once, then pass the ObjectRef to all tasks (pseudocode; helpers not defined): 

# Put once
dataset = load_test_cases()  # 1 GB
dataset_ref = ray.put(dataset)

# Share across 1,000 tasks; Ray stores dataset once per node
@ray.remote
def eval_task(test_case, dataset):
    # dataset is the actual data, resolved from dataset_ref
    return run_eval(test_case, dataset)

futures = [eval_task.remote(tc, dataset_ref) for tc in test_cases[:1000]]
results = ray.get(futures)

Benefit: Ray transfers the dataset to each node once, stores it in Plasma, and all workers on that node share it via zero-copy access. Without ray.put, you'd serialize the dataset 1,000 times (once per task), wasting memory and network bandwidth.

The Ownership Model: Distributed Reference Counting

How does Ray know when to delete an object? In a single-machine Python runtime, the garbage collector tracks reference counts and frees objects when their count hits zero. In a distributed system with thousands of workers, centralized reference counting would be a bottleneck. Ray uses a decentralized ownership model.

Owner, Borrowers, and Distributed Reference Counting

From Ownership: A Distributed Futures System for Fine-Grained Tasks (NSDI 2021):

Each object has an owner (the caller of the task that created it) and borrowers (other workers that hold references). The owner stores metadata and coordinates scheduling and garbage collection. From the paper:

"Each borrower stores a local reference count for the DFut on behalf of the owner (Table 2) and notifies the owner when the local reference count reaches zero. The owner decides when the object is safe to reclaim."

Hierarchical Reference Counting

Ray uses hierarchical distributed reference counting:

  1. Local ref count: Each borrower maintains a local count of how many times the ObjectRef is referenced in its process (e.g., stored in a list, passed to another task).
  2. Owner ref count: The owner tracks how many borrowers have nonzero local counts, plus its own local references.
  3. Notify on zero: When a borrower's local count reaches zero, it reports to the owner via WaitForRefRemoved / WORKER_REF_REMOVED_CHANNEL pub/sub. The owner decrements its borrower count.
  4. Reclaim when no refs: When the owner's local count and borrower count are both zero, and no pending tasks depend on the object, the owner tells the raylet to delete the object from Plasma.

Source: src/ray/core_worker/reference_count.cc (distributed reference counting implementation).

Lineage Reconstruction for Fault Tolerance

What if a node fails and loses objects? Ray uses lineage reconstruction: the owner stores the task spec (function, arguments, dependencies) for each object. If an object is lost (node failure, eviction), Ray re-executes the task to reconstruct the object.

From Ownership paper (NSDI 2021):

"We choose a minimal approach that guarantees progress, at the potential cost of additional re-execution on a failure: we fate share the object and any reference holders with the owner, then use lineage reconstruction to recover the object and any of the owner's fate-shared children tasks (Section 4.3)."

Fate-sharing: If the owner dies, all objects it owns and all borrowers are lost. Ray re-executes the owner's task and downstream tasks to reconstruct the lost objects. This adds minimal runtime overhead (no checkpointing) but may cause re-execution on failure.

Lineage limit: From src/ray/common/ray_config_def.h, lines 145-151: 

/// Maximum amount of lineage to keep in bytes. [...] If we reach this limit,
/// 50% of the current lineage will be evicted and objects that are still in
/// scope will no longer be reconstructed if lost.
RAY_CONFIG(int64_t, max_lineage_bytes, 1024 * 1024 * 1024)  // 1 GiB

Once lineage exceeds 1 GiB, Ray evicts old lineage. Objects without lineage cannot be reconstructed if lost.

Global Control Service (GCS): The Cluster Control Plane

The Global Control Service (GCS) is Ray's centralized metadata store and control plane. It runs on the head node (or multiple nodes with fault tolerance) and manages cluster-wide state.

What the GCS Stores

From Ray 2.0 Architecture Whitepaper:

"The GCS is a server that manages cluster-level metadata, such as the locations of actors, stored as key-value pairs that may be cached locally by workers. The GCS also manages a handful of cluster-level operations, including scheduling for placement groups and actors and determining cluster node membership. In general, the GCS manages metadata that is less frequently accessed but likely to be used by most or all workers in the cluster."

GCS stores:

  • Actor directory: Mapping from ActorID to node address. When you call an actor method, Ray looks up the actor's location in GCS.
  • Node membership: Which nodes are alive, their resources (CPU, GPU, memory, custom), and their raylet addresses.
  • Placement groups: Reservations of resources across multiple nodes (used for gang-scheduling, e.g., multi-GPU training). Covered in Lesson 11.
  • Job table: Active jobs and their drivers.

What the GCS does NOT store: Task metadata (stored by task owners), object locations (stored in ownership tables by object owners), object data (stored in Plasma).

Source: src/ray/gcs/gcs_server/ (GCS server, actor manager, node manager, placement group manager).

GCS Fault Tolerance

In Ray 2.0+, GCS can be fault-tolerant with Redis-backed persistence. From Redis in Ray: Past and future (Anyscale blog):

"Cluster metadata is stored inside GCS by default instead of Redis. We implemented a GCS internal key-value store, and a common interface for Redis and GCS key-value stores, to facilitate the migration of the default storage."

Without GCS FT (default for ray.init() local clusters), GCS failure means the entire cluster fails (see below). With GCS FT enabled, GCS can recover and reload its state from Redis.

Lesson 12 (KubeRay, Autoscaling, and GCS Fault Tolerance) covers GCS HA setup and failure modes in detail.

What Happens When GCS Fails (Without FT)

From Ray 2.40.0 docs: GCS Fault Tolerance:

"By default, the GCS is not fault tolerant ... its failure means that the entire Ray cluster fails."

Raylets exit after 60 seconds (gcs_rpc_server_reconnect_timeout_s) when they cannot reach the GCS. The cluster is unrecoverable without GCS FT: you must restart all nodes and all jobs.

With GCS FT enabled (Redis-backed persistence), during GCS recovery:

  • Available: "running Ray tasks and actors remain alive and any existing objects will continue to be available" (docs).
  • Unavailable: Actor creation/deletion/reconstruction, placement group operations, resource management, node registration, worker process creation.

GCS FT setup: Not supported in local ray.init() clusters. Per docs, enable with RAY_REDIS_ADDRESS=redis_ip:port ray start --head --redis-password PASSWORD. Officially supported only on KubeRay.

Ray for Eval Orchestration: When to Use It and When to Skip It

You've seen the mechanics: tasks, actors, object store, ownership, GCS. Now, when should you use Ray for eval orchestration, and when is plain asyncio (or another tool) better?

When Ray Helps

  • Multi-machine scale: You're running 10,000+ evals across 50+ machines. Ray handles scheduling, data transfer, and failure recovery. You don't have to write a custom scheduler.
  • Heterogeneous resources: Some tasks need GPUs (vLLM inference), some need CPUs (sandbox exec), some need lots of memory (dataset loading). Ray's resource-aware scheduler places tasks on appropriate nodes.
  • Stateful workers: You have async actors that hold sandbox clients, database connections, or pre-loaded models. Ray actors persist state across method calls and can run 1,000s of tasks without tearing down/recreating workers.
  • Large shared data: You broadcast a 10 GB dataset to 1,000 tasks. Ray stores it once per node in Plasma, avoiding 1,000× serialization overhead.
  • RL rollouts: You have 1,000 actors collecting experience, 8×H100 training a policy, and periodic syncs of model weights. Ray's placement groups (Lesson 11) gang-schedule GPU workers, and Ray actors coordinate rollout/training loops (verl, OpenRLHF examples in Lesson 13).

When Ray is Overkill (Use Plain Asyncio or Simpler Tools)

  • Single machine: If you're running 200 evals on one laptop or a single beefy VM, asyncio (or a simple process pool) is simpler. Ray's overhead (GCS, raylet, object store) adds latency and memory for the runtime.
  • Tiny tasks: Tasks that run <1ms. Ray's ~1 ms latency per task (from NSDI 2021 paper) dominates. For millions of 100µs tasks, use a lower-level runtime (Dask, native multiprocessing).
  • No shared data: If every task has unique inputs and outputs, and you're not reusing data, Ray's object store is wasted. Just spawn tasks and collect results.
  • Tight coupling: If tasks constantly communicate (e.g., MPI-style all-reduce every iteration), Ray's async task model is a poor fit. Use MPI or a collective-communication framework.

Real Systems: verl, OpenRLHF, SkyRL

Lesson 13 (Ray in Production RL) covers how real RL frameworks use Ray:

  • verl (Volcengine RL): HybridFlow architecture: vLLM actors for generation (GPU-heavy), Megatron actors for training (multi-GPU), CPU actors for reward computation. Ray placement groups reserve multi-GPU resources for training.
  • OpenRLHF: Ray schedules generation on vLLM actors (GPU), training on DeepSpeed actors (multi-GPU), and syncs weights via object store.
  • SkyRL-OpenHands: Ray actors coordinate many Docker containers. Each actor holds N sandbox clients (aiodocker), fans out code-editing tasks, uses ray.wait to stream results.

Takeaway: Ray shines when you have heterogeneous resources, stateful workers, and multi-machine scale. For single-machine or homogeneous workloads, simpler tools (asyncio, multiprocessing, Celery) may suffice.

Async Actors vs Tasks for Sandbox Exec

For I/O-bound eval workloads (each eval = 30 seconds of LLM API calls + sandbox exec), use async actors with max_concurrency (pseudocode; SandboxClient and save_results not defined): 

@ray.remote
class SandboxPoolActor:
    def __init__(self, sandbox_api_url):
        self.client = SandboxClient(sandbox_api_url)
        self.completed = 0
    
    async def run_eval(self, item_id):
        result = await self.client.exec(item_id)  # I/O-bound
        self.completed += 1
        return result

# Create 10 actors, each with concurrency=10 → 100 concurrent evals
pools = [SandboxPoolActor.options(max_concurrency=10).remote(url) for _ in range(10)]

# Fan out 10,000 items
futures = [pools[i % 10].run_eval.remote(i) for i in range(10000)]

# Stream results with ray.wait
while futures:
    ready, futures = ray.wait(futures, num_returns=10, timeout=None)
    results = ray.get(ready)
    save_results(results)

Why actors, not tasks? Tasks are stateless: each task would create a new SandboxClient, authenticate, and tear down. Actors persist the client across 10,000 calls, avoiding setup overhead. Async actors handle I/O concurrency (10 concurrent exec calls per actor) without blocking.

When the Object Store Becomes a Bottleneck

The object store is great for large shared inputs (broadcast once, read many times). But it can be a bottleneck if:

  • Many small objects: Creating 1 million 1 KB objects fills Plasma metadata. For small results, return them inline (they'll be ≤100 KB and stored in-process).
  • Head node hotspot: If all tasks return results to the driver (head node), and you're returning 1 TB of data, the driver's object store and network become a bottleneck. Instead, write results directly to S3 or a database from workers.
  • Object store full: If your working set exceeds object store size (30% of RAM by default), Ray spills to disk. From Ray docs, spilling comes "at the cost of I/O latency" (docs recommend SSD over HDD). Either increase object store size (ray.init(object_store_memory=...)) or reduce working set (process results in smaller batches, delete ObjectRefs sooner).

Build It Yourself: Async Actor Pool for Eval Orchestration

Let's build a Ray-based eval orchestrator with async actors, streaming results, retries, and object store broadcast. This simulates a real eval harness: 200 items, fake-sandbox exec (asyncio.sleep with random latency and 20% failure rate), 4 async actor pools with concurrency=10 each (40 total concurrency).

Exercise Code

#!/usr/bin/env python3
"""
Ray Eval Orchestrator Exercise: Async Actor Pool for Sandbox Execution

Demonstrates:
- Async actors as a pool of sandbox clients for I/O-bound work
- ray.wait to stream completions
- Retry logic for failed items
- Object store for broadcasting shared data
"""
import ray
import asyncio
import random
import time
from typing import Dict, List
from dataclasses import dataclass

@dataclass
class EvalResult:
    item_id: int
    status: str  # 'success' or 'failed'
    duration: float
    retries: int
    error: str = None

@ray.remote
class AsyncSandboxPool:
    """
    Async actor that holds N concurrent sandbox exec calls.
    
    Uses asyncio for concurrency within a single actor, which is more efficient
    for I/O-bound work than spawning N separate Ray tasks.
    """
    
    def __init__(self, pool_id: int, max_concurrency: int = 5):
        self.pool_id = pool_id
        self.max_concurrency = max_concurrency
        self.semaphore = asyncio.Semaphore(max_concurrency)
        self.completed_count = 0
        self.failed_count = 0
    
    async def exec_item(self, item_id: int, attempt: int = 1) -> EvalResult:
        """
        Simulate sandbox exec: random latency, 20% failure rate on first attempt
        """
        async with self.semaphore:
            # Simulate I/O-bound sandbox exec (network call to sandbox API)
            duration = random.uniform(0.1, 0.5)
            await asyncio.sleep(duration)
            
            # Simulate failure with lower probability on retries
            failure_prob = 0.2 / attempt
            if random.random() < failure_prob:
                self.failed_count += 1
                return EvalResult(
                    item_id=item_id,
                    status='failed',
                    duration=duration,
                    retries=attempt,
                    error=f"Sandbox timeout (simulated, attempt {attempt})"
                )
            
            self.completed_count += 1
            return EvalResult(
                item_id=item_id,
                status='success',
                duration=duration,
                retries=attempt
            )
    
    def get_stats(self) -> Dict:
        return {
            "pool_id": self.pool_id,
            "completed": self.completed_count,
            "failed": self.failed_count,
            "total": self.completed_count + self.failed_count
        }

def run_eval_orchestrator(num_items: int = 200, num_pools: int = 4, max_concurrency: int = 10):
    """
    Main orchestrator: fans out eval items across async actor pools,
    uses ray.wait to stream completions, retries failed items.
    """
    print(f"Starting eval orchestrator:")
    print(f"  Items: {num_items}")
    print(f"  Pools: {num_pools}")
    print(f"  Concurrency per pool: {max_concurrency}")
    print(f"  Total concurrency: {num_pools * max_concurrency}")
    print()
    
    # Create async actor pool with max_concurrency option
    pools = [
        AsyncSandboxPool.options(max_concurrency=max_concurrency).remote(i, max_concurrency) 
        for i in range(num_pools)
    ]
    
    # Submit all items, distributed across pools
    pending_refs = []
    for item_id in range(num_items):
        pool = pools[item_id % num_pools]
        ref = pool.exec_item.remote(item_id, attempt=1)
        pending_refs.append(ref)
    
    # Stream results as they complete, retry failures
    completed_results: List[EvalResult] = []
    failed_items = []
    
    start_time = time.time()
    last_report = start_time
    
    print("Processing items (streaming results with ray.wait):")
    while pending_refs:
        # Wait for at least 1 task to complete, timeout after 1 second to report progress
        ready, pending_refs = ray.wait(pending_refs, num_returns=1, timeout=1.0)
        
        # Process completed tasks
        for ref in ready:
            result: EvalResult = ray.get(ref)
            
            if result.status == 'success':
                completed_results.append(result)
            else:
                # Retry failed items (up to 3 attempts)
                if result.retries < 3:
                    pool = pools[result.item_id % num_pools]
                    retry_ref = pool.exec_item.remote(result.item_id, attempt=result.retries + 1)
                    pending_refs.append(retry_ref)
                else:
                    failed_items.append(result)
        
        # Report progress every 2 seconds
        now = time.time()
        if now - last_report >= 2.0:
            total_processed = len(completed_results) + len(failed_items)
            elapsed = now - start_time
            throughput = total_processed / elapsed if elapsed > 0 else 0
            print(f"  [{elapsed:.1f}s] Completed: {len(completed_results)}, "
                  f"Failed: {len(failed_items)}, "
                  f"Pending: {len(pending_refs)}, "
                  f"Throughput: {throughput:.1f} items/s")
            last_report = now
    
    elapsed = time.time() - start_time
    
    # Final stats
    print(f"\n{'=' * 60}")
    print("FINAL RESULTS")
    print(f"{'=' * 60}")
    print(f"Total items: {num_items}")
    print(f"Successful: {len(completed_results)}")
    print(f"Failed (after retries): {len(failed_items)}")
    print(f"Success rate: {len(completed_results) / num_items * 100:.1f}%")
    print(f"Total time: {elapsed:.2f}s")
    print(f"Throughput: {num_items / elapsed:.1f} items/s")
    print()
    
    # Per-pool stats
    print("Per-pool statistics:")
    pool_stats = ray.get([pool.get_stats.remote() for pool in pools])
    for stats in pool_stats:
        print(f"  Pool {stats['pool_id']}: "
              f"{stats['completed']} completed, "
              f"{stats['failed']} failed "
              f"(total: {stats['total']} execs including retries)")
    print()
    
    # Duration statistics
    durations = [r.duration for r in completed_results]
    if durations:
        print(f"Latency statistics (successful items):")
        print(f"  Min: {min(durations):.3f}s")
        print(f"  Max: {max(durations):.3f}s")
        print(f"  Avg: {sum(durations) / len(durations):.3f}s")
    
    # Retry statistics
    retry_counts = [r.retries for r in completed_results + failed_items]
    retried = sum(1 for r in retry_counts if r > 1)
    print(f"\nRetry statistics:")
    print(f"  Items that needed retry: {retried} ({retried / num_items * 100:.1f}%)")
    print(f"  Permanently failed: {len(failed_items)} ({len(failed_items) / num_items * 100:.1f}%)")

def demo_object_store_broadcast():
    """
    Demonstrate object store for broadcasting large shared inputs
    """
    print(f"\n{'=' * 60}")
    print("DEMO: Object Store for Broadcast")
    print(f"{'=' * 60}")
    
    # Create a large dataset (e.g., test cases, reference data)
    dataset = {
        "test_cases": [f"test_{i}" for i in range(10000)],
        "reference_data": list(range(100000))
    }
    
    print(f"Dataset size: {len(str(dataset))} bytes (approximate)")
    
    # Put once in object store
    start = time.time()
    dataset_ref = ray.put(dataset)
    put_time = time.time() - start
    print(f"ray.put() time: {put_time * 1000:.2f}ms")
    print(f"ObjectRef: {dataset_ref}")
    
    @ray.remote
    def use_dataset(data, worker_id):
        # Ray automatically resolves the ObjectRef passed as argument
        return {
            "worker_id": worker_id,
            "num_test_cases": len(data["test_cases"]),
            "data_sum": sum(data["reference_data"][:100])
        }
    
    # Fan out to many tasks - dataset is shared in memory, not copied
    start = time.time()
    refs = [use_dataset.remote(dataset_ref, i) for i in range(20)]
    results = ray.get(refs)
    fanout_time = time.time() - start
    
    print(f"\n20 tasks used shared dataset:")
    print(f"  Total time: {fanout_time:.3f}s")
    print(f"  First result: {results[0]}")
    print(f"  All got same data: {all(r['num_test_cases'] == 10000 for r in results)}")
    print(f"\nBenefit: Dataset stored once in object store, shared by all workers")
    print(f"without copying. Alternative (passing as argument without ray.put)")
    print(f"would serialize the dataset for each task, wasting memory and bandwidth.")

if __name__ == "__main__":
    random.seed(42)
    ray.init(ignore_reinit_error=True)
    
    try:
        # Main exercise: async actor pool for eval orchestration
        run_eval_orchestrator(num_items=200, num_pools=4, max_concurrency=10)
        
        # Bonus: demonstrate object store broadcast
        demo_object_store_broadcast()
        
    finally:
        ray.shutdown()
    
    print(f"\n{'=' * 60}")
    print("✓ Exercise completed successfully!")
    print(f"{'=' * 60}")

What You Learned

  • Async actors with max_concurrency: Each pool runs up to 10 concurrent exec_item calls (I/O-bound work), avoiding the overhead of spawning 200 separate workers.
  • ray.wait for streaming: Instead of blocking on all 200 tasks with ray.get(all_futures), we process results as they complete, enabling progress reporting and early failure detection.
  • Retry logic: Failed items (20% failure rate on first attempt) are retried up to 3 times. Ray makes this easy: just submit a new actor method call with incremented attempt count.
  • Object store broadcast: ray.put stores the dataset once; all tasks share it via zero-copy access. Without ray.put, each task would serialize the dataset, wasting 20× the memory and bandwidth.
