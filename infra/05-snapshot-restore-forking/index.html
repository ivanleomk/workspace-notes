From Cold Boot to Warm Resume: The Throughput Lever

In Lesson 04, you booted Firecracker from scratch and measured the ≤125ms target from InstanceStart to guest /sbin/init. But what if you need to run 10,000 eval episodes? Or train an RL policy where every episode boots a fresh sandbox?

Cold boot doesn't scale. Even at 125ms per boot, 10,000 boots = 21 minutes of pure boot time, ignoring the actual eval work. And that's with a minimal kernel and rootfs. Add real dependencies (Python packages, git clones, pip install), and your "boot" becomes multi-second setup per instance.

Enter Snapshot/Restore

Snapshot/restore is the lever that transforms eval throughput. The idea:

  1. Boot once. Start a Firecracker VM, install dependencies, warm up the environment, and get to a ready state.
  2. Snapshot. Capture the full guest memory (RAM contents) and device state (virtio ring buffers, CPU registers, etc.) to files on the host.
  3. Restore N times. For each eval, restore the snapshot instead of cold-booting. The VM resumes exactly where it left off, with all packages installed and caches warm.

From Firecracker's snapshot-support.md:

"A snapshot can be used to restore a microVM to the exact state captured at snapshot time."

Why this is faster than cold boot:

  • No kernel decompression or device initialization. The guest kernel and virtio devices are already initialized in the snapshot.
  • No userspace init. /sbin/init, systemd, and startup scripts already ran. The snapshot captures a running system.
  • Dependencies pre-installed. pip install, git clone, and cache warming happened once, before the snapshot. Every restore inherits that state.

Why Snapshot/Restore Beats Cold Create

The Setup Tax

Real eval workloads don't run on minimal kernels. They need:

  • Dependencies: pip install transformers torch can take 10–30 seconds, even with fast mirrors and local caches.
  • Repository clones: git clone https://github.com/large-repo transfers MBs or GBs.
  • Warm-up: First import of a large library (PyTorch, TensorFlow) is slow; subsequent imports are faster thanks to __pycache__ and system caches.
  • Per-task setup: SWE-bench instances install per-repo environments and check out specific commits.

Problem: If you cold-boot for every eval episode, you pay this tax N times. For 10,000 episodes, that's 10,000× the setup cost.

The Snapshot Solution

With snapshot/restore:

  1. Template creation: Boot a VM, run all setup (pip install, git clone, warm imports), then snapshot it. This is now your template.
  2. Per-eval restore: For each eval, restore the template snapshot. The VM starts with all packages installed, repos cloned, and caches warm. Setup cost: zero.

Key Takeaway

Snapshot/restore is a time-shift: you move all setup cost from per-eval time to per-template time. Boot once, snapshot, restore N times. This is why E2B's "create" API call actually resumes a snapshot—cold boot would be too slow.

Firecracker Snapshot Mechanics

Documentation: snapshot-support.md

What a Snapshot Contains

A Firecracker snapshot consists of:

  1. Memory file: The raw contents of guest RAM. This is the guest kernel, running processes, page cache, etc. For a VM with 1 GiB of RAM, this file is 1 GiB (uncompressed). You can optionally compress it with zstd or similar.
  2. State file (JSON): Device state (virtio-net/block/vsock ring buffer positions, vCPU registers, serial console state, etc.). This is small (tens of KB).
  3. (Optional) Diff memory file: For diff snapshots (developer preview), only the dirty pages since the base snapshot are saved. This shrinks the memory file when changes are small.

Creating a Snapshot

Via the Firecracker API: 

curl --unix-socket /tmp/firecracker.socket -X PUT \
  http://localhost/actions \
  -H "Content-Type: application/json" \
  -d '{
    "action_type": "CreateSnapshot",
    "payload": {
      "snapshot_type": "Full",
      "snapshot_path": "/path/to/snapshot_state.json",
      "mem_file_path": "/path/to/snapshot_memory.bin"
    }
  }'

This pauses the VM, writes the memory and state files, and then you can stop Firecracker. The VM is frozen at the moment of snapshot.

Restoring a Snapshot

You start a new Firecracker process and tell it to load a snapshot: 

curl --unix-socket /tmp/firecracker2.socket -X PUT \
  http://localhost/snapshot/load \
  -H "Content-Type: application/json" \
  -d '{
    "snapshot_path": "/path/to/snapshot_state.json",
    "mem_backend": {
      "backend_type": "File",
      "backend_path": "/path/to/snapshot_memory.bin"
    },
    "enable_diff_snapshots": false,
    "resume_vm": true
  }'

What happens:

  1. Firecracker mmaps the memory file. The guest's RAM is backed by this file.
  2. It deserializes the device state from the JSON.
  3. It creates a new KVM VM (KVM_CREATE_VM), maps the memory, restores vCPU registers, and calls KVM_RUN.
  4. The guest resumes execution exactly where it left off when the snapshot was taken. No reboot, no init—just continuation.

Full vs Diff Snapshots

From snapshot-support.md:

"Diff snapshots (developer preview) capture only the dirty memory pages since the last snapshot."
  • Full snapshot: Captures all guest memory. Size = guest RAM size. Always works.
  • Diff snapshot: Captures only pages modified since a base snapshot. Much smaller if changes are small (e.g., an agent ran for 10 seconds, touching ~50 MB). Still developer preview as of Firecracker v1.9; test before production use.

Use case for diff snapshots: You run an agent to step k, take a diff snapshot, fork N children. Each child's diff is small (only the RNG state and per-child data changed). Storage cost for N children is much lower than N full snapshots.

Important: Snapshots Are Not Portable Across Kernel Versions

From snapshot-support.md: "Snapshot compatibility is ensured only for snapshots taken with the same Firecracker binary version and on hosts with the same kernel version." If you snapshot on kernel 5.10 and restore on 6.1, KVM internal state may have changed. For production, pin your host kernel version or test carefully.

userfaultfd: Lazy Memory on Restore

Documentation: handling-page-faults-on-snapshot-resume.md

The Problem: Waiting for 1 GiB Transfers

Imagine you store snapshots in S3 or object storage (as E2B does). A 1 GiB memory file takes time to download over the network. If you wait for the full file before resuming the VM, your "fast" snapshot restore becomes slow.

userfaultfd solves this.

What is userfaultfd?

From the Linux man page (userfaultfd(2)) and Firecracker's doc:

"userfaultfd is a Linux kernel feature that allows a userspace process to handle page faults."

Normally, when a process accesses unmapped memory, the kernel handles the page fault (allocates a page, zeros it or loads it from disk, maps it). With userfaultfd, the kernel sends a notification to a userspace handler, which can:

  • Load the page from a file, network, or object storage
  • Decompress it
  • Map it into the faulting process

This is lazy loading: the VM starts running with no memory pages mapped. As the guest touches pages (code, data, stack), Firecracker's userfaultfd handler loads them on demand.

How Firecracker Uses userfaultfd

From handling-page-faults-on-snapshot-resume.md:

"Firecracker… can configure guest memory to be handled by a userspace page fault handler."

The workflow:

  1. Firecracker creates a userfaultfd descriptor via the userfaultfd(2) syscall.
  2. It registers the guest memory range with the userfaultfd.
  3. On snapshot restore, Firecracker mmaps the guest memory range but does not immediately read the snapshot file into it.
  4. When the guest accesses a page (e.g., executing code at address 0x400000), the kernel sends a userfaultfd event to Firecracker's handler thread.
  5. The handler reads that 4 KiB page from the snapshot file (or object storage) and calls UFFDIO_COPY to map it.
  6. The guest resumes. The page fault is transparent to the guest.

Figure 3: userfaultfd lazy page-in. The guest's first access to a page triggers a fault; Firecracker's handler fetches it from storage and maps it.

Why This Is Fast

Hot pages load first, cold pages load on demand (or never).

  • The guest's first instructions (kernel code, init process) are in the first few MB of memory. Those pages fault immediately and are loaded.
  • Large allocations that the guest never touches (e.g., a 512 MiB buffer allocated but not yet written) never fault, so those pages are never transferred.
  • Total transfer time is proportional to the working set (pages actually accessed), not the full memory size.

E2B reports (vendor claim, E2B persistence docs):

"Resume takes approximately 1 second."

This is for a ~1 GiB snapshot with userfaultfd from object storage. Without userfaultfd, you'd wait for the full 1 GiB download.

Prefetching Hot Pages

E2B's runtime ( e2b-dev/runtime) includes a prefetcher:

"A final optimize pass 'records which pages a boot actually touches'."

This means: during template creation, E2B tracks which pages are accessed during a typical boot. On restore, it prefetches those pages before the VM starts, so the first faults are instant. Cold pages still fault on demand.

Clone Hazards: Why Restoring N Times Breaks Things

You take a snapshot and restore it 10 times. Now you have 10 VMs. But they're clones—they started from identical memory. This causes problems.

Hazard 1: Shared RNG State (Breaks Determinism)

Documentation: random-for-clones.md

From random-for-clones.md:

"When you restore a snapshot… the guest OS entropy pool is in the exact same state… Clones of a snapshot produce the same sequence of random numbers."

What this means for evals:

  • All 10 clones call /dev/urandom and get identical bytes.
  • Python's random.random() (seeded from /dev/urandom at startup) produces identical values across all 10 clones.
  • If you're sampling from an LLM with temperature=0.8, all 10 rollouts produce identical samples—not independent samples.

This is a determinism hazard: for GRPO-style forking (run to step k, fork N children, sample differently), you need independent RNG state per child. Without reseeding, your N rollouts are copies, not independent trials.

Fixing RNG Clones

From random-for-clones.md, Firecracker recommends two mitigations:

  1. VMGenID (VM Generation Counter): Firecracker exposes a device that increments a counter on every restore. The guest kernel's RNG can read this and reseed. Requires guest kernel support (CONFIG_VMGENID=y, available in Linux 5.18+).
  2. Manual reseed: After restore, write entropy to /dev/urandom from the host or a startup script. Example: 
    # Inside the guest, after restore
dd if=/dev/random of=/dev/urandom bs=32 count=1
    Or, if you control the workload: 
    import random
import os

# After fork, reseed Python's RNG with OS entropy
random.seed(os.urandom(32))

Hazard 2: Shared MAC Addresses (Breaks Networking)

Documentation: network-for-clones.md

From network-for-clones.md:

"Restored microVMs… share the same MAC and IP addresses."

If all 10 clones use MAC AA:FC:00:00:00:01 and IP 172.16.0.2, they collide on the host network. Packets meant for clone 1 might arrive at clone 5. This breaks connectivity.

Fixing Network Clones

From network-for-clones.md:

"Each clone should be placed in its own network namespace."

The workflow:

  1. Create a network namespace per clone: 
    ip netns add clone-1
ip netns add clone-2
  2. Create a unique TAP device per clone: 
    ip tuntap add tap1 mode tap
ip tuntap add tap2 mode tap
  3. Assign each TAP a unique IP (e.g., 172.16.0.1 for tap1, 172.16.1.1 for tap2).
  4. When restoring, configure Firecracker to use the per-clone TAP and MAC.
  5. Inside the guest, reconfigure the network after restore (assign the per-clone IP).

Alternative: Disable networking entirely for evals that don't need it (safer and simpler).

Hazard 3: Time Skew

The snapshot captures the guest's wall clock. If you snapshot at time T and restore 10 minutes later, the guest's clock is 10 minutes behind. Some applications (certificate validation, TTL checks) break.

Fix: Sync the guest clock after restore. If the guest has virtio-rtc or NTP, it will auto-sync. For quick restores, this may not matter (the guest runs for seconds, not hours).

⚠️ Clone Hazards Are Correctness Bugs, Not Just Performance Issues

Shared RNG state means your N "independent" rollouts are actually identical. This breaks GRPO, tree search, and any algorithm that assumes independent sampling. Always reseed after restore.

GRPO-Style Forking: Run to Step k, Fork N Children

The GRPO Use Case

GRPO (Group Relative Policy Optimization) is an RL algorithm where, at each training step, you sample G rollouts from the same state and compare them. The idea: run the agent to a decision point, then sample G different continuations.

Naive approach: Run the agent to step k, save the state, then replay from that state G times. Problem: you pay the cost of steps 0 to k G times.

Forking approach: Run the agent to step k once, snapshot, then fork G clones from the snapshot. Each clone continues from step k with different sampling. You pay the prefix cost once, not G times.

Why This Requires Snapshot/Fork

Without snapshots: To replay from step k, you need to serialize the entire environment state (filesystem, process memory, open sockets, etc.). This is hard and brittle. Some things (kernel state, device buffers) can't be serialized from userspace.

With Firecracker snapshots: The VM is the environment. Snapshot = entire environment state. Restore = perfect replay. No serialization logic needed.

The Forking Workflow

  1. Boot template: Start a VM with dependencies pre-installed (restored from a base template snapshot).
  2. Run prefix: Execute the agent's policy for steps 0 to k. The agent interacts with the environment (runs code, edits files, etc.).
  3. Snapshot at decision point: When you reach step k (a decision point where you want G samples), call Firecracker's CreateSnapshot. This captures the VM mid-flight.
  4. Fork G children: Restore the snapshot G times (either on the same host or across hosts). Each child is a clone of the step-k VM.
  5. Reseed RNGs: After restore, write unique entropy to each child's /dev/urandom or reseed the application's RNG. This ensures independent sampling.
  6. Sample differently: Each child runs the policy from step k with different sampling (temperature, top-k, seed). They produce G independent rollouts.
  7. Collect outcomes: Each child writes its trajectory and outcome to object storage (or returns it via an API).
  8. GRPO update: Compare the G outcomes and compute the policy gradient update.

Real Systems That Use Forking

  • E2B: Supports a fork API. From the docs: "With the SDKs and the CLI you can request up to 20 forks at once." (E2B fork docs)
  • Morph: branch(count=n) API. From the docs: "snapshot, branch, and restore entire computational environments in under 250ms" (vendor claim). (Morph developers page; the branch API itself is at branch docs)
  • Daytona: VM class supports "pause / resume, fork, and hot snapshots." (Daytona isolation docs)
  • Modal: Supports memory snapshots (experimental) for debugging. Filesystem snapshots (images) are the standard way to share setup across sandboxes. (Modal snapshots docs)

CRIU: Process-Level Checkpoint/Restore

CRIU (Checkpoint/Restore In Userspace) is an alternative to VM snapshots. It checkpoints process trees (not entire VMs) from userspace.

Homepage: github.com/checkpoint-restore/criu

How CRIU Works

CRIU uses ptrace(2) and /proc to capture:

  • Process memory (heap, stack, mmap regions)
  • Open file descriptors and their positions
  • Process IDs, parent/child relationships
  • Namespaces (mount, network, pid, etc.)
  • cgroup membership
  • Signal handlers, timers, etc.

On restore, CRIU reconstructs the process tree: creates processes with the same PIDs, maps memory, reopens files, and resumes execution.

CRIU vs Firecracker Snapshots

Aspect CRIU Firecracker Snapshots
Scope Process tree (userspace only) Entire VM (kernel + userspace)
Kernel state Not captured (relies on host kernel) Fully captured (guest kernel is part of the snapshot)
Portability Fragile: host kernel version/config must match Requires same Firecracker version + kernel version (still fragile, but VM boundary helps)
Overhead No VM overhead ~7–10 MiB per VM (Firecracker VMM)
Isolation Container-level (shared kernel) Hardware-level (KVM)
Restore speed Fast (no VM boot) Fast (VM resume, no boot)
Integration Docker (docker checkpoint), LXC, OpenVZ Firecracker (native), E2B, Morph, Daytona

When to Use CRIU

Use CRIU when:

  • You're checkpointing simple process trees (single-process or parent+children).
  • You control the host kernel version (so checkpoints are portable).
  • You don't need VM-level isolation (container-level is OK).

Use Firecracker snapshots when:

  • You need to capture the entire environment (kernel + userspace).
  • The guest does complex things (kernel modules, device interactions).
  • You want hardware isolation (KVM).
  • You're already using Firecracker for other reasons.

gVisor Checkpoint/Restore

gVisor (Lesson 03) also supports checkpoint/restore via runsc checkpoint and runsc restore. Because the Sentry is the kernel, gVisor serializes the entire kernel state without needing kernel cooperation. This is more robust than CRIU (which depends on the host kernel's checkpoint interface) but still lighter than a full VM snapshot. gVisor's checkpoint/restore supports lazy loading (--background) and GPU state (cuda-checkpoint). (gVisor checkpoint docs)

How Real Systems Use Snapshot/Restore

E2B Runtime

Repository: e2b-dev/runtime (formerly e2b-dev/infra)
Documentation: ARCHITECTURE.md

From ARCHITECTURE.md:

"Fresh creates, resumes after a pause, and forks all take the same path."

What this means:

  • A template is a pre-booted Firecracker VM snapshot. Templates are built in layers (each layer is hashed), and a final optimize pass records which pages a boot touches.
  • Create resumes a template snapshot via userfaultfd (lazy memory) and an NBD-served copy-on-write rootfs.
  • Pause diffs memory and disk against the template and uploads the diff to object storage.
  • Resume prefers the node that still has the diff cached. If not, it fetches from object storage.
  • Fork checkpoints the original in place and spreads children across nodes.

E2B's architecture includes:

  • Control plane: API + Postgres + Redis + ClickHouse. Handles placement and quotas.
  • Data plane: Per-node orchestrator that drives Firecracker. Sandbox traffic goes directly to the node (never through the API).
  • Per-node mechanisms:
    • uffd/: userfaultfd lazy memory, with optional prefetcher for known-hot pages
    • nbd/ and rootfs/: copy-on-write rootfs served by an in-process NBD server
    • network/: netns + veth "slots"
    • cgroup CPU quotas applied before the guest runs

Idempotency: E2B's API offers opt-in request idempotency with a TTL (default 86,400s per ARCHITECTURE.md). Use this in your orchestrator for retry safety.

Morph Cloud (Infinibranch)

Documentation: Morph developers page | branch API docs

From the developers page:

"snapshot, branch, and restore entire computational environments in under 250ms" (vendor claim)

Morph's API is shaped around VMs. A snapshot carries vcpus, memory, and disk_size. The branch API (POST /api/instance/:id/branch with count) saves a hidden synchronous snapshot and starts count children.

Content-addressed snapshots: The snapshot digest field gives you hash(setup) → snapshot, so you can cache and reuse snapshots for identical setup steps.

Daytona

Documentation: Daytona isolation docs

Daytona has two sandbox classes:

  • Container: "dedicated namespaces and enforced resource limits" (shared kernel, no snapshots)
  • VM: "full virtual machine with its own kernel," which enables "pause / resume, fork, and hot snapshots"

Note: Daytona's public repo (AGPL-3.0) is no longer maintained; the README (as of June 2026) says "core development has moved to a private codebase." Self-hosting means maintaining a fork of legacy code.

Modal Sandboxes

Documentation: Modal sandbox snapshots

Modal supports three kinds of snapshots:

  1. Filesystem snapshots (images): Standard Modal images (e.g., built with Image.build(...).publish). Any number of sandboxes can start from one image. This is the recommended way to share setup.
  2. Directory snapshots: Snapshot a specific directory (e.g., /workspace) and restore it into another sandbox. TTL default: 30 days.
  3. Memory snapshots (experimental): Snapshot a running sandbox's memory. TTL: 7 days. Sharp edges: taking a memory snapshot terminates the sandbox; you cannot snapshot while an exec is running; restore requires the same instance type; no GPU support.

For forking: Use filesystem snapshots (images) to share setup. Memory snapshots are better for debugging than production forking.

Fly Machines

Documentation: Fly Machines overview

Fly Machines are built on Firecracker microVMs. Fly supports fast stop/start (pause/resume). A stopped machine stays assembled, so start is "usually… well under a second" (vendor claim). Fly also offers clone (fork) and volumes (persistent storage).

Build It Yourself: Warm-Pool Simulator and GRPO Forking

In this exercise, you'll build a minimal Python warm-pool and fork simulator that demonstrates the speedup of "prefix once, fork N" vs "replay N times." This runs on any laptop (no KVM required).

Then, for those with Linux + KVM access, we provide a real Firecracker snapshot + fork example (clearly marked optional).

Exercise Goals

  • Model a warm pool: pre-create M "sandboxes" (simulated as Python objects), measure acquire/release latency
  • Model GRPO forking: run prefix once (simulated expensive setup), "snapshot" state, "fork" N children with different RNG seeds, measure total time vs N full replays
  • Demonstrate RNG clone hazard: fork without reseeding → identical samples

Part 1: Warm-Pool Simulator (Python, runs anywhere)

Create warm_pool_sim.py: 

#!/usr/bin/env python3
"""
Warm-pool simulator: pre-create sandboxes, measure acquire latency.
"""
import asyncio
import time
from typing import List, Dict
import random


class Sandbox:
    """Simulated sandbox."""
    def __init__(self, sid: str):
        self.sid = sid
        self.state = {}  # Simulated state
    
    async def setup(self):
        """Simulate expensive setup (pip install, git clone)."""
        await asyncio.sleep(0.1)  # 100ms setup
        self.state["setup_done"] = True
    
    def exec_command(self, cmd: str) -> str:
        """Simulate command execution."""
        return f"Sandbox {self.sid}: ran {cmd}"
    
    def snapshot(self) -> Dict:
        """Simulate taking a snapshot."""
        return self.state.copy()
    
    def restore(self, snapshot: Dict):
        """Simulate restoring from snapshot."""
        self.state = snapshot.copy()


class WarmPool:
    """Warm pool manager."""
    def __init__(self, size: int):
        self.size = size
        self.pool: List[Sandbox] = []
        self.available: asyncio.Queue = asyncio.Queue()
    
    async def initialize(self):
        """Pre-create and warm up sandboxes."""
        print(f"Initializing warm pool with {self.size} sandboxes...")
        start = time.time()
        
        # Create sandboxes concurrently
        tasks = [self._create_and_warm(i) for i in range(self.size)]
        self.pool = await asyncio.gather(*tasks)
        
        for sb in self.pool:
            await self.available.put(sb)
        
        elapsed = time.time() - start
        print(f"Warm pool initialized in {elapsed:.2f}s ({elapsed/self.size:.3f}s per sandbox)")
    
    async def _create_and_warm(self, idx: int) -> Sandbox:
        """Create a sandbox and run setup."""
        sb = Sandbox(f"sb-{idx:03d}")
        await sb.setup()
        return sb
    
    async def acquire(self) -> Sandbox:
        """Acquire a sandbox from the pool."""
        return await self.available.get()
    
    async def release(self, sb: Sandbox):
        """Return a sandbox to the pool."""
        await self.available.put(sb)


async def benchmark_cold_vs_warm():
    """Compare cold create vs warm pool acquire."""
    
    # Cold create
    print("\n=== Cold Create ===")
    cold_times = []
    for i in range(10):
        start = time.time()
        sb = Sandbox(f"cold-{i}")
        await sb.setup()
        elapsed = time.time() - start
        cold_times.append(elapsed)
    
    print(f"Cold create (10 runs): mean={sum(cold_times)/len(cold_times)*1000:.1f}ms")
    
    # Warm pool
    print("\n=== Warm Pool ===")
    pool = WarmPool(size=5)
    await pool.initialize()
    
    warm_times = []
    for i in range(10):
        start = time.time()
        sb = await pool.acquire()
        elapsed = time.time() - start
        warm_times.append(elapsed)
        # Use sandbox
        sb.exec_command(f"echo test-{i}")
        # Release
        await pool.release(sb)
    
    print(f"Warm acquire (10 runs): mean={sum(warm_times)/len(warm_times)*1000:.1f}ms")
    print(f"Speedup: {sum(cold_times)/sum(warm_times):.1f}x")


async def main():
    await benchmark_cold_vs_warm()


if __name__ == "__main__":
    asyncio.run(main())

Part 2: GRPO Fork Simulator (Python)

Create grpo_fork_sim.py: 

#!/usr/bin/env python3
"""
GRPO fork simulator: run prefix once, fork N, sample differently.
Demonstrates RNG clone hazard if you forget to reseed.
"""
import asyncio
import time
import random
import copy


class Agent:
    """Simulated agent with RNG state."""
    def __init__(self, agent_id: str):
        self.agent_id = agent_id
        self.rng = random.Random()
        self.rng.seed(42)  # Shared initial seed
        self.trajectory = []
    
    async def run_prefix(self, k: int):
        """Run steps 0 to k (expensive prefix)."""
        for step in range(k):
            await asyncio.sleep(0.01)  # Simulate step cost
            action = self.rng.randint(0, 10)
            self.trajectory.append((step, action))
    
    def snapshot(self) -> dict:
        """Snapshot agent state (trajectory + RNG state)."""
        return {
            "trajectory": copy.deepcopy(self.trajectory),
            "rng_state": self.rng.getstate()
        }
    
    def restore(self, snapshot: dict):
        """Restore from snapshot."""
        self.trajectory = copy.deepcopy(snapshot["trajectory"])
        self.rng.setstate(snapshot["rng_state"])
    
    def reseed(self, seed: int):
        """Reseed RNG (fixes clone hazard)."""
        self.rng.seed(seed)
    
    def sample_action(self) -> int:
        """Sample next action."""
        return self.rng.randint(0, 100)


async def grpo_naive(k: int, g: int):
    """Naive GRPO: replay prefix G times."""
    print(f"\n=== Naive GRPO (replay prefix {g} times) ===")
    start = time.time()
    
    rollouts = []
    for i in range(g):
        agent = Agent(f"naive-{i}")
        await agent.run_prefix(k)  # Run prefix from scratch
        action = agent.sample_action()
        rollouts.append(action)
    
    elapsed = time.time() - start
    print(f"Rollouts: {rollouts}")
    print(f"Time: {elapsed:.2f}s")
    return rollouts, elapsed


async def grpo_fork_no_reseed(k: int, g: int):
    """GRPO with fork, but NO reseed (demonstrates RNG hazard)."""
    print(f"\n=== GRPO Fork (NO reseed - demonstrates hazard) ===")
    start = time.time()
    
    # Run prefix once
    base_agent = Agent("base")
    await base_agent.run_prefix(k)
    snapshot = base_agent.snapshot()
    
    # Fork G children
    rollouts = []
    for i in range(g):
        agent = Agent(f"fork-no-reseed-{i}")
        agent.restore(snapshot)  # Clone without reseed
        action = agent.sample_action()
        rollouts.append(action)
    
    elapsed = time.time() - start
    print(f"Rollouts: {rollouts}")
    print(f"Time: {elapsed:.2f}s")
    print(f"⚠️  All rollouts identical? {len(set(rollouts)) == 1}")
    return rollouts, elapsed


async def grpo_fork_with_reseed(k: int, g: int):
    """GRPO with fork AND reseed (correct)."""
    print(f"\n=== GRPO Fork (WITH reseed - correct) ===")
    start = time.time()
    
    # Run prefix once
    base_agent = Agent("base")
    await base_agent.run_prefix(k)
    snapshot = base_agent.snapshot()
    
    # Fork G children with unique seeds
    rollouts = []
    for i in range(g):
        agent = Agent(f"fork-reseed-{i}")
        agent.restore(snapshot)
        agent.reseed(42 + i)  # Unique seed per child
        action = agent.sample_action()
        rollouts.append(action)
    
    elapsed = time.time() - start
    print(f"Rollouts: {rollouts}")
    print(f"Time: {elapsed:.2f}s")
    print(f"Speedup vs naive: {time_naive / elapsed:.1f}x")
    print(f"✓ Rollouts are independent? {len(set(rollouts)) > 1}")
    return rollouts, elapsed


async def main():
    k = 10  # Prefix length
    g = 8   # Number of rollouts
    
    global time_naive
    _, time_naive = await grpo_naive(k, g)
    _, time_no_reseed = await grpo_fork_no_reseed(k, g)
    _, time_reseed = await grpo_fork_with_reseed(k, g)
    
    print(f"\n=== Summary ===")
    print(f"Naive (replay {g}x): {time_naive:.2f}s")
    print(f"Fork no reseed: {time_no_reseed:.2f}s (but WRONG: identical samples)")
    print(f"Fork with reseed: {time_reseed:.2f}s (correct)")


if __name__ == "__main__":
    asyncio.run(main())

Run it: 

python3 grpo_fork_sim.py

Expected output:

  • Naive: Replays prefix 8 times. Time: ~0.8s (10 steps × 0.01s × 8 rollouts).
  • Fork no reseed: Prefix runs once (~0.1s), forks 8 times. BUT all 8 rollouts produce identical actions because RNG state is cloned.
  • Fork with reseed: Prefix runs once, forks 8 times with unique seeds. Rollouts are independent. Time: ~0.1s. Speedup: ~8x vs naive.

⚠️ Key Lesson

Without reseeding, forked rollouts are identical, not independent. This breaks GRPO and any algorithm that assumes independent samples. Always reseed after fork/restore.
