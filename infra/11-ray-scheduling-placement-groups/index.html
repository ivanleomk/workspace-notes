Ray's Resource Model: Logical Resources and Allocation

Ray tracks logical resources on each node. When you submit a task or create an actor with resource requirements, Ray's scheduler finds a node with available resources.

Built-in Resource Types

From Ray 2.40.0 Docs: Specifying Task and Actor Resources:

"For convenience, Ray has native support for CPU, GPU, and memory resource types; CPU, GPU and memory are called pre-defined resources."
  • CPU: Logical CPUs. By default set to the number of CPUs of the machine/container at ray start or ray.init(). Override with --num-cpus or num_cpus=.
  • GPU: GPU devices (NVIDIA, AMD, etc.). Ray auto-detects via CUDA_VISIBLE_DEVICES. Override with --num-gpus or num_gpus=.
  • memory: Bytes of RAM. By default Ray sets this to 70% of available memory at startup. Override with --memory.
  • object_store_memory: Bytes for Plasma object store (not a logical resource; cannot be used for scheduling). By default Ray sets this to 30% of available memory at startup. Override with --object-store-memory.

Custom Resources

You can define custom resources for specialized hardware or logical constraints. From Ray docs:

"Besides pre-defined resources, you can also specify a Ray node's custom resources and request them in your tasks or actors." 
ray.init(resources={"tpu": 4, "fpga": 2})

@ray.remote(resources={"tpu": 1})
def train_on_tpu():
    # This task will only run on a node with available "tpu" resources
    return "trained on TPU"

Use case: Label nodes with custom resources (e.g., high_memory_node, spot_instance) to control placement without tying to physical hardware.

Fractional Resources

Tasks and actors can request fractional resources. From Ray docs:

"Ray supports fractional resource requirements. For example, if your task or actor is IO bound and has low CPU usage, you can specify fractional CPU num_cpus=0.5 or even zero CPU num_cpus=0."
"It's your responsibility to make sure tasks or actors use no more resources than specified via resource requirements." 
# 4 tasks can share 1 GPU
@ray.remote(num_gpus=0.25)
def light_gpu_task():
    # Use only 1/4 of GPU memory/compute
    return "light GPU work"

# Spawn 8 tasks; they'll be scheduled on 2 GPUs (4 per GPU)
futures = [light_gpu_task.remote() for _ in range(8)]

When to use: Multiple small models fitting on one GPU (e.g., 4×1.5B models on one A100), or IO-bound tasks with low CPU usage.

Warning: Ray does NOT enforce resource limits at runtime. If you request num_gpus=0.25 but use 80% of GPU memory, you'll cause OOM for other tasks on that GPU. Ray sets CUDA_VISIBLE_DEVICES itself (device-level isolation only); to cap per-task GPU memory use framework settings (e.g., vLLM gpu_memory_utilization, torch.cuda.set_per_process_memory_fraction) or MPS/MIG.

Default Resource Allocations: Tasks vs Actors

From Ray 2.40.0 docs:

"By default, Ray tasks use 1 logical CPU resource and Ray actors use 1 logical CPU for scheduling, and 0 logical CPU for running. (This means, by default, actors cannot get scheduled on a zero-cpu node, but an infinite number of them can run on any non-zero cpu node. ... If resources are specified explicitly, they are required both at schedule time and at execution time.)"

Tasks: Default num_cpus=1. A task without explicit resource requirements reserves 1 CPU. 

@ray.remote  # Implicitly num_cpus=1
def default_task():
    return "uses 1 CPU"

Actors: More nuanced. By default, actors use 1 CPU for scheduling (to be placed on the cluster) and then hold 0 CPUs while running.

Example: 

@ray.remote  # Default actor: needs 1 free CPU to be scheduled, then holds 0 CPUs for its lifetime
class MyActor:
    def method(self):
        return "actor method uses the actor's process"

# Actor creation needs 1 CPU free to be scheduled, then releases it
actor = MyActor.remote()
# Actor method calls do not acquire CPUs; they run on the actor's process
ray.get(actor.method.remote())

To reserve CPUs for the actor's lifetime (useful for actors that hold expensive state like GPU models): 

@ray.remote(num_cpus=4, num_gpus=1)
class GPUModelActor:
    def __init__(self):
        # Load model onto GPU; reserves 4 CPUs + 1 GPU for lifetime
        pass
    
    def infer(self, data):
        return "inference"

If you set num_cpus (or any resource) explicitly, it is held for the actor's lifetime, both at scheduling and execution time.

Why the difference? Per the Ray docs, the actor default "was chosen for historical reasons. It's recommended to always explicitly set num_cpus for actors to avoid any surprises."

How Ray's Scheduler Works: Hybrid Two-Level Scheduling

Ray uses a hybrid two-level scheduler: GCS schedules actors (centralized), raylets schedule tasks (distributed). From the Ray 2.0 Architecture Whitepaper:

"The GCS also manages a handful of cluster-level operations, including scheduling for placement groups and actors and determining cluster node membership. In general, the GCS manages metadata that is less frequently accessed but likely to be used by most or all workers in the cluster."

From the whitepaper: "A task caller schedules a task by first sending a resource request to the preferred raylet for that request. ... 3. By default, the local raylet."

Actor Placement (GCS)

When you call Actor.remote(), the driver sends an actor creation request to the GCS. The GCS picks a node with available resources and tells a raylet to create the actor. From the whitepaper:

"the GCS then creates the actor by scheduling the actor creation task"

The GCS uses a default hybrid policy (source: src/ray/gcs/gcs_server/gcs_actor_scheduler.h):

By default (gcs_actor_scheduling_enabled=false), the GCS forwards the actor creation lease request to the raylet on the owner's node (or a random node). That raylet applies the normal hybrid policy and may spill back to another raylet, exactly as for tasks: "as if the GCS were the actor creation task's caller" (whitepaper). If no node is feasible, the actor stays PENDING.

Task Placement (Raylet)

When you call task.remote(), the driver's local raylet (CoreWorker → raylet communication) checks resources. From the whitepaper:

"When a resource request (i.e RequestWorkerLease PRC) is received by the raylet, it will go through the above state machine"

The raylet uses a local-first policy:

  1. Local placement: If the local node has resources, schedule the task locally.
  2. Spillback: If not, the raylet replies to the caller (owner) with the address of a remote raylet chosen from its eventually-consistent cluster view, and the caller retries the lease request there. The GCS is not on this path. If no node has resources, the task is queued (status: PENDING).

Why local-first? Minimizes data transfer. If a task depends on objects created by the driver or previous tasks on the same node, those objects are already in the local object store (zero-copy access).

Pending Tasks and Actors: Resource Exhaustion

If no node has available resources, tasks and actors remain PENDING until resources free up. From Ray 2.40.0 docs:

"If there are feasible nodes, Ray will either choose an available node or wait until a unavailable node to become available depending on other factors discussed below. If all nodes are infeasible, the task or actor cannot be scheduled until feasible nodes are added to the cluster."

You can inspect pending tasks/actors in the Ray dashboard (:8265) or with ray status (CLI). For placement groups (next section), use ray.util.placement_group_table() to see PENDING groups.

Scheduling Strategies: DEFAULT, SPREAD, Node Affinity

Ray provides scheduling strategies to control where tasks and actors run. From Ray 2.40.0 Docs: Scheduling:

"Tasks or actors support a scheduling_strategy option to specify the strategy used to decide the best node among feasible nodes."

DEFAULT: Hybrid (pack until 50% utilization, then spread)

The default strategy (if you don't specify one) is "DEFAULT". Nodes whose critical-resource utilization is below RAY_scheduler_spread_threshold (default 0.5) score 0 and are preferred, with the local/preferred node favoured for locality; above the threshold the score is the utilization itself. Ray picks randomly among the top k lowest-score nodes, where k = max(RAY_scheduler_top_k_fraction (0.2) × nodes, RAY_scheduler_top_k_absolute (1)). 

@ray.remote
def task():
    return "default strategy"

# Implicitly uses DEFAULT strategy
future = task.remote()

SPREAD: Anti-Affinity Across Nodes

"SPREAD" strategy distributes tasks/actors across nodes, avoiding concentration on one node. From Ray docs:

"\"SPREAD\" strategy will try to spread the tasks or actors among available nodes." 
@ray.remote(scheduling_strategy="SPREAD")
def task():
    return "spread across nodes"

# Create 100 actors; Ray will distribute them across all nodes
actors = [MyActor.options(scheduling_strategy="SPREAD").remote() for _ in range(100)]

Use case: Load balancing, avoiding hotspots. For example, spread 100 I/O-bound sandbox actors across 10 nodes (10 per node) instead of packing them all on the head node.

NodeAffinitySchedulingStrategy: Soft and Hard Affinity

Target a specific node by node ID. From Ray docs, first sentence:

"NodeAffinitySchedulingStrategy is a low-level strategy that allows a task or actor to be scheduled onto a particular node specified by its node id." 
from ray.util.scheduling_strategies import NodeAffinitySchedulingStrategy

# Get node ID
import ray
nodes = ray.nodes()
node_id = nodes[0]["NodeID"]

# soft=True: fall back elsewhere only if node dies/is infeasible
@ray.remote(scheduling_strategy=NodeAffinitySchedulingStrategy(
    node_id=node_id,
    soft=True
))
def task_soft():
    return "prefer node, but can spill"

# soft=False: fail with *UnschedulableError if node dies/is infeasible
@ray.remote(scheduling_strategy=NodeAffinitySchedulingStrategy(
    node_id=node_id,
    soft=False
))
def task_hard():
    return "must run on node"

Soft (soft=True): runs only on the target node while it is alive and feasible (waiting if it is busy); falls back to another feasible node only if the target is dead or infeasible.

Hard (soft=False): same while the node is alive and feasible; if the node is dead or infeasible, the task/actor fails with TaskUnschedulableError / ActorUnschedulableError.

Use case: Pin tasks to nodes with specific hardware (e.g., high-memory node for dataset loading, GPU node for inference).

PlacementGroupSchedulingStrategy: Gang Scheduling

Schedule tasks/actors within a placement group (next section). This is the most important strategy for RL and multi-GPU workloads. 

from ray.util.placement_group import placement_group
from ray.util.scheduling_strategies import PlacementGroupSchedulingStrategy

pg = placement_group([{"CPU": 2, "GPU": 1}] * 4, strategy="STRICT_PACK")
ray.get(pg.ready())

@ray.remote(num_cpus=2, num_gpus=1)
class Worker:
    pass

# Schedule actor in bundle 0 of the placement group
worker = Worker.options(
    scheduling_strategy=PlacementGroupSchedulingStrategy(
        placement_group=pg,
        placement_group_bundle_index=0
    )
).remote()

Placement Groups: Gang Scheduling and Resource Reservation

Placement groups are Ray's mechanism for gang scheduling: reserving a set of resources (bundles) atomically across multiple nodes. From Ray 2.40.0 Docs: Placement Groups:

"Placement groups allow users to atomically reserve groups of resources across multiple nodes (i.e., gang scheduling)."

Why Placement Groups?

Problem: You want to start 8 actors, each needing 1 GPU. You submit them with Actor.remote(). Ray schedules the first 4 actors on Node A (which has 4 GPUs). The cluster has 8 total GPUs but they're split: 4 on Node A, 4 on Node B. Actors 5–8 are placed on Node B. Now your actors are split across nodes, and inter-node communication is slow.

Solution: Use a placement group with STRICT_PACK strategy to reserve 8×(1 GPU) on the same node. If no single node has 8 GPUs, the placement group remains PENDING until autoscaling adds capacity or other jobs finish.

Placement Group Basics: Bundles

A placement group consists of bundles: resource specifications. From Ray docs:

"A **bundle** is a collection of "resources". It could be a single resource, ``{"CPU": 1}``, or a group of resources, ``{"CPU": 1, "GPU": 4}``."
"Ray supports four placement group strategies. The default scheduling policy is ``PACK``." 
from ray.util.placement_group import placement_group

# Reserve 4 bundles: each bundle has 2 CPUs and 1 GPU
pg = placement_group(
    bundles=[
        {"CPU": 2, "GPU": 1},
        {"CPU": 2, "GPU": 1},
        {"CPU": 2, "GPU": 1},
        {"CPU": 2, "GPU": 1}
    ],
    strategy="PACK"
)

# Wait for placement group to be created (resources reserved)
ray.get(pg.ready())

# Now schedule tasks/actors in the placement group
# (see PlacementGroupSchedulingStrategy above)

Shorthand: Use [{"CPU": 2, "GPU": 1}] * 4 to create 4 identical bundles.

Placement Group Strategies

From Ray docs:

PACK: Prefer Same Node

From Ray docs:

"**PACK** All provided bundles are packed onto a single node on a best-effort basis. If strict packing is not feasible (i.e., some bundles do not fit on the node), bundles can be placed onto other nodes."

Use case: Multi-GPU training where all GPUs should be on the same node (fast NVLink communication). If one node doesn't have enough resources, Ray will split across nodes.

STRICT_PACK: All on Same Node

From Ray docs:

"**STRICT_PACK** All bundles must be placed into a single node on the cluster. Use this strategy when you want to maximize the locality."

If no single node has enough resources, the placement group remains PENDING.

SPREAD: Prefer Separate Nodes (best-effort)

From Ray docs:

"**SPREAD** Each bundle is spread onto separate nodes on a best-effort basis. If strict spreading is not feasible, bundles can be placed on overlapping nodes."

Use case: Distributed training where you want one worker per node (to maximize cross-node bandwidth usage and avoid intra-node contention).

STRICT_SPREAD: Exactly One Bundle Per Node

From Ray docs:

"**STRICT_SPREAD** Each bundle must be scheduled in a separate node."

If the cluster has fewer nodes than bundles, the placement group stays PENDING (infeasible); it does not fail.

Two-Phase Commit: Atomic Reservation

Placement groups use two-phase commit to reserve resources atomically. From the Ray 2.0 Architecture Whitepaper:

"Since resource groups may involve resources across multiple nodes, Ray uses a two phase commit protocol across the raylets to ensure atomicity. The protocol is coordinated by the GCS. If any raylet dies in the middle of the protocol, the placement group creation is rolled back and the GCS queues the request again."

Phase 1 (Prepare): GCS asks raylets on selected nodes: "Can you reserve these resources?" Raylets check and respond yes/no.

Phase 2 (Commit): If all raylets say yes, GCS sends "Commit" and raylets mark resources as reserved. If any raylet says no, GCS sends "Abort" and tries a different set of nodes.

This ensures all-or-nothing: either all bundles are reserved, or none are. No partial placement groups.

Placement Group Lifecycle

  1. Creation: Call placement_group(...). Returns a PlacementGroup handle immediately. The group is in PENDING state.
  2. Scheduling: GCS tries to find nodes with resources. Uses two-phase commit to reserve bundles.
  3. Ready: When all bundles are reserved, the group enters CREATED state. pg.ready() resolves.
  4. Usage: Schedule tasks/actors in the group with PlacementGroupSchedulingStrategy.
  5. Removal: Call ray.util.remove_placement_group(pg). Resources are freed. If lifetime="detached", the group persists until explicit removal or cluster shutdown.
from ray.util.placement_group import placement_group, remove_placement_group
from ray.util.scheduling_strategies import PlacementGroupSchedulingStrategy

pg = placement_group([{"CPU": 2}] * 4, strategy="PACK", lifetime="detached", name="my_pg")
ray.get(pg.ready())  # Wait for CREATED state

# Use it
@ray.remote(num_cpus=2)
def task():
    return "in placement group"

future = task.options(
    scheduling_strategy=PlacementGroupSchedulingStrategy(placement_group=pg)
).remote()

ray.get(future)

# Remove when done
remove_placement_group(pg)

placement_group_capture_child_tasks: Automatic Placement

From Ray docs:

"By default, child actors and tasks don't share the same placement group that the parent uses. To automatically schedule child actors or tasks to the same placement group, set ``placement_group_capture_child_tasks`` to True." 
from ray.util.scheduling_strategies import PlacementGroupSchedulingStrategy

pg = placement_group([{"CPU": 4}], strategy="PACK")
ray.get(pg.ready())

@ray.remote
def parent():
    # This child task will also be scheduled in the placement group
    @ray.remote
    def child():
        return "child task"
    return ray.get(child.remote())

# parent.remote() uses the placement group with capture_child_tasks, child.remote() does too
future = parent.options(
    scheduling_strategy=PlacementGroupSchedulingStrategy(
        placement_group=pg,
        placement_group_capture_child_tasks=True
    )
).remote()

ray.get(future)  # "child task"

Use case: Nested parallelism (e.g., a rollout actor spawns per-episode sandbox tasks). Without placement_group_capture_child_tasks, child tasks might spill to other nodes; with it, they stay in the placement group.

What Happens When a Node Fails?

From Ray docs:

"If nodes that contain some bundles of a placement group die, all the bundles are rescheduled on different nodes by GCS (i.e., we try reserving resources again). This means that the initial creation of placement group is "atomic", but once it is created, there could be partial placement groups. Rescheduling bundles have higher scheduling priority than other placement group scheduling."
"Actors and tasks that use the bundle (reserved resources) are rescheduled based on their fault tolerant policy once the bundle is recovered."

Rescheduling: GCS tries to find replacement nodes with resources. If actors were running in the failed bundles, they are rescheduled per their fault-tolerance policy (e.g., max_restarts) once the bundle is recovered.

Manual removal: If you don't want automatic rescheduling, call remove_placement_group(pg) and create a new one.

Placement Groups in Production RL: verl and OpenRLHF

How do real RL frameworks use placement groups for multi-GPU training and rollout orchestration?

verl: Volcano Engine Reinforcement Learning

verl (github.com/verl-project/verl, Apache-2.0) is Volcano Engine's RL framework for RLHF. From the README:

"verl is a flexible, efficient and production-ready RL training library for large language models (LLMs)."

verl uses Ray placement groups to gang-schedule multi-GPU workers. From verl/single_controller/ray/base.py (RayResourcePool.get_placement_groups, main, excerpt): 

# Real verl code (verl/single_controller/ray/base.py):
def get_placement_groups(self, strategy="STRICT_PACK", ...):
    bundle = {"CPU": self.max_colocate_count}
    bundle[device_name] = 1
    placement_group(bundles=bundles, strategy=strategy, name=pg_name_prefix + str(idx), lifetime=lifetime)
    
# RayWorkerGroup uses bin_pack: bool = True → strategy = "STRICT_PACK"

verl's architecture:

  • verl maps roles (actor/rollout, critic, reference, reward model) to resource pools; each pool creates one placement group per node, using STRICT_PACK by default (RayWorkerGroup bin_pack=True), and the actor and rollout engines are colocated in the same workers (HybridFlow hybrid engine).

OpenRLHF: Open-Source RLHF Framework

OpenRLHF (github.com/OpenRLHF/OpenRLHF, Apache-2.0) is an open-source RLHF framework supporting Ray + vLLM + DeepSpeed. From the README:

"OpenRLHF is **the first** high-performance, production-ready open-source RLHF framework that combines **Ray + vLLM distributed architecture** with a **unified agent-based design paradigm** for scalable and extensible reinforcement learning from human feedback."

OpenRLHF uses placement groups for vLLM inference. From openrlhf/trainer/ray/vllm_engine.py (main branch, L248-251): 

# Create a big placement group to ensure that all engines are packed
bundles = [{"GPU": 1, "CPU": 1} for _ in range(num_engines * tensor_parallel_size)]
shared_pg = placement_group(bundles, strategy="PACK")
ray.get(shared_pg.ready())

OpenRLHF's hybrid engine uses:

  • vLLM actors in placement groups: Generation on GPUs (tensor-parallel across multiple GPUs on the same node).
  • DeepSpeed training actors: placed in a PACK placement group (launcher.py) with one {"GPU": 1, "CPU": 1} bundle per GPU.

From OpenRLHF's README (vendor claim):

"RLHF training spends **80% of the time on sample generation**. Powered by vLLM with Auto Tensor Parallelism (AutoTP) and Pipeline Parallelism (PP), OpenRLHF delivers high-throughput, memory-efficient generation."

Lesson 13 (Ray in Production RL) covers verl and OpenRLHF in more detail, including how they coordinate generation/training loops and handle placement group failures.

    pg_spread = placement_group(
        name="pg_spread",
        bundles=[{"CPU": 1, "simulated_gpu": 1}] * 2,
        strategy="SPREAD"
    )
    ray.get(pg_spread.ready())
    print(f"✓ SPREAD placement group created")
    print(f"  Bundles will be spread across nodes")
    
    # STRICT_PACK: all on same node
    print("\n--- Strategy: STRICT_PACK ---")
    pg_strict_pack = placement_group(
        name="pg_strict_pack",
        bundles=[{"CPU": 1, "simulated_gpu": 1}] * 2,
        strategy="STRICT_PACK"
    )
    ray.get(pg_strict_pack.ready(), timeout=5)
    print(f"✓ STRICT_PACK placement group created")
    print(f"  All bundles MUST be on the same node")
    
    # Show placement group table
    print("\n--- Placement Group Table ---")
    table = placement_group_table()
    for pg_id, pg_info in table.items():
        print(f"{pg_info['name']}:")
        print(f"  State: {pg_info['state']}")
        print(f"  Strategy: {pg_info['strategy']}")
        print(f"  Bundles: {len(pg_info['bundles'])}")
    
    # Cleanup
    remove_placement_group(pg_pack)
    remove_placement_group(pg_spread)
    remove_placement_group(pg_strict_pack)
    
    ray.shutdown()
    print("\n✓ Demo 1 complete")

def demo_gang_scheduling():
    """
    Demonstrate gang-scheduling actors for RL rollout simulation
    """
    print("\n" + "="*60)
    print("DEMO 2: Gang Scheduling GPU Workers")
    print("="*60)
    
    # Simulate 4 "GPUs"
    ray.init(
        num_cpus=8,
        resources={"simulated_gpu": 4},
        ignore_reinit_error=True
    )
    
    print("\nSimulating RL rollout with 4 GPU workers")
    print("Creating placement group with STRICT_PACK (all GPUs on same node)")
    
    # Create placement group for 4 GPU workers
    pg = placement_group(
        bundles=[{"CPU": 1, "simulated_gpu": 1}] * 4,
        strategy="STRICT_PACK",
        name="rl_gpu_workers"
    )
    
    # Wait for placement group to be ready
    start = time.time()
    ray.get(pg.ready())
    elapsed = time.time() - start
    print(f"✓ Placement group ready in {elapsed:.3f}s")
    
    # Define GPU worker actor
    @ray.remote(num_cpus=1, resources={"simulated_gpu": 1})
    class GPUWorker:
        def __init__(self, worker_id):
            self.worker_id = worker_id
            self.episodes_completed = 0
        
        def run_episode(self, episode_id):
            # Simulate GPU rollout
            self.episodes_completed += 1
            return {
                "worker_id": self.worker_id,
                "episode_id": episode_id,
                "status": "success"
            }
        
        def get_stats(self):
            return {
                "worker_id": self.worker_id,
                "episodes_completed": self.episodes_completed
            }
    
    # Create 4 workers in the placement group (one per bundle)
    print("\nCreating 4 GPU workers in placement group...")
    workers: List[ray.actor.ActorHandle] = []
    for i in range(4):
        worker = GPUWorker.options(
            scheduling_strategy=PlacementGroupSchedulingStrategy(
                placement_group=pg,
                placement_group_bundle_index=i
            )
        ).remote(i)
        workers.append(worker)
    
    print("✓ All workers created")
    
    # Run episodes across all workers
    print("\nRunning 20 episodes across 4 workers...")
    futures = []
    for episode_id in range(20):
        worker = workers[episode_id % 4]
        future = worker.run_episode.remote(episode_id)
        futures.append(future)
    
    # Wait for all episodes
    results = ray.get(futures)
    print(f"✓ All episodes completed: {len(results)} results")
    
    # Get worker stats
    print("\n--- Worker Statistics ---")
    stats = ray.get([worker.get_stats.remote() for worker in workers])
    for stat in stats:
        print(f"Worker {stat['worker_id']}: {stat['episodes_completed']} episodes")
    
    # Cleanup
    remove_placement_group(pg)
    ray.shutdown()
    print("\n✓ Demo 2 complete")

def demo_resource_exhaustion():
    """
    Demonstrate what happens when resources are insufficient
    """
    print("\n" + "="*60)
    print("DEMO 3: Resource Exhaustion and Pending Placement Groups")
    print("="*60)
    
    # Small cluster: only 4 CPUs, 2 "GPUs"
    ray.init(
        num_cpus=4,
        resources={"simulated_gpu": 2},
        ignore_reinit_error=True
    )
    
    print(f"\nCluster has only 4 CPUs and 2 simulated_gpu")
    print(f"Resources: {ray.cluster_resources()}")
    
    # Try to create a placement group requiring 4 GPUs (more than available)
    print("\nAttempting to create placement group requiring 4 GPUs (STRICT_PACK)...")
    pg_large = placement_group(
        bundles=[{"CPU": 1, "simulated_gpu": 1}] * 4,
        strategy="STRICT_PACK",
        name="pg_too_large"
    )
    
    # Check status without blocking
    print("Placement group created (not yet scheduled)")
    
    # Check placement group table
    time.sleep(1)  # Give GCS time to schedule
    pg_info = placement_group_table(pg_large)
    
    print(f"\nPlacement group state: {pg_info['state']}")
    if pg_info['state'] == 'PENDING':
        print("✓ As expected, placement group is PENDING (insufficient resources)")
        print("  STRICT_PACK requires all 4 bundles on one node, but cluster has only 2 GPUs")
    else:
        print(f"  State: {pg_info['state']}")
    
    # Try to use the placement group (will fail or timeout)
    print("\nTrying to schedule an actor in the pending placement group...")
    
    @ray.remote(num_cpus=1, resources={"simulated_gpu": 1})
    class Worker:
        def ping(self):
            return "alive"
    
    worker = Worker.options(
        scheduling_strategy=PlacementGroupSchedulingStrategy(
            placement_group=pg_large,
            placement_group_bundle_index=0
        )
    ).remote()
    
    # Try to call method with short timeout
    try:
        result = ray.get(worker.ping.remote(), timeout=3)
        print(f"Unexpected: actor responded: {result}")
    except ray.exceptions.GetTimeoutError:
        print("✓ Actor method timed out (expected: actor can't be created until PG is ready)")
    
    # Show how to detect pending placement groups
    print("\n--- Detecting Pending Placement Groups ---")
    table = placement_group_table()
    pending_pgs = [
        (pg_id, info['name'], info['state'])
        for pg_id, info in table.items()
        if info['state'] == 'PENDING'
    ]
    
    if pending_pgs:
        print(f"Found {len(pending_pgs)} pending placement group(s):")
        for pg_id, name, state in pending_pgs:
            print(f"  - {name}: {state}")
    else:
        print("No pending placement groups")
    
    # Cleanup
    remove_placement_group(pg_large)
    ray.shutdown()
    print("\n✓ Demo 3 complete")

def demo_capture_child_tasks():
    """
    Demonstrate capture_child_tasks flag
    """
    print("\n" + "="*60)
    print("DEMO 4: capture_child_tasks Flag")
    print("="*60)
    
    ray.init(num_cpus=8, ignore_reinit_error=True)
    
    # Create placement group with placement_group_capture_child_tasks
    pg = placement_group(
        bundles=[{"CPU": 4}],
        strategy="PACK",
        name="pg_with_capture"
    )
    ray.get(pg.ready())
    print("✓ Placement group created")
    
    @ray.remote
    def parent_task():
        # Child task will also be scheduled in the placement group
        @ray.remote
        def child_task():
            return "child executed in placement group"
        
        return ray.get(child_task.remote())
    
    # Schedule parent in placement group with placement_group_capture_child_tasks=True
    result = ray.get(parent_task.options(
        scheduling_strategy=PlacementGroupSchedulingStrategy(
            placement_group=pg,
            placement_group_capture_child_tasks=True
        )
    ).remote())
    
    print(f"✓ Parent task spawned child task: {result}")
    print("  Child was automatically scheduled in the same placement group")
    
    remove_placement_group(pg)
    ray.shutdown()
    print("\n✓ Demo 4 complete")

What You'll Learn

  • Placement group strategies: See how PACK, SPREAD, and STRICT_PACK differ.
