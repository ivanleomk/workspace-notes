Why Runtime Choice Matters for Evals

In Lessons 01 and 02, you learned the primitives: namespaces, cgroups, seccomp-bpf, and overlayfs. Now we'll see how three major container runtimes combine these primitives—or go beyond them—to provide different isolation guarantees.

The fundamental trade-off: Security vs Performance vs Compatibility.

  • runc (and crun): Shared kernel. Highest performance, largest attack surface.
  • gVisor (runsc): Userspace kernel. Syscalls hit the Sentry, not the host. Overhead on syscall-heavy and I/O-heavy workloads.
  • Kata Containers: Hardware virtualization. Each pod gets a guest kernel. VM boot cost, per-VM memory, and requires bare metal or nested virt.

What You'll Learn

  • The OCI runtime spec and how containerd shim v2 plugs in runc/runsc/kata-runtime
  • How runc builds on lessons 01–02 (namespaces, cgroups, seccomp)
  • gVisor's Sentry + Gofer architecture and platform choices (systrap/ptrace/KVM)
  • Kata's lightweight VM model with guest kernel, kata-agent, and virtio-fs
  • Which runtime production systems use (Modal, UK AISI, Northflank, SkyRL)
  • A decision guide: which runtime for which eval workload
  • Hands-on: benchmark syscall, I/O, and CPU workloads under runc vs runsc

⚠️ The Isolation Ladder

Every step up the ladder shrinks the attack surface but adds overhead:

  1. Plain containers (runc): Shared kernel. One vuln = escape.
  2. gVisor: Syscalls hit a userspace kernel (the Sentry). Host kernel exposure is drastically reduced.
  3. microVMs (Firecracker/Kata): Hardware isolation. Each guest has its own kernel behind KVM.

For untrusted code—RL policies exploring for reward hacks, adversarial submissions—runc alone is not enough. This is why Modal uses gVisor, and why Northflank runs Kata for CPU sandboxes.

The OCI Runtime Spec: What Runtimes Must Do

The Open Container Initiative (OCI) runtime specification defines a standard interface for low-level container runtimes. A runtime takes:

  • A bundle: a directory with a config.json (the container config) and a rootfs
  • Commands: create, start, kill, delete, state

The config.json specifies:

  • Process args, env, cwd, user
  • Namespaces to create (pid, network, mount, etc.)
  • Mounts (the rootfs plus any bind mounts)
  • Linux-specific: cgroups path and resources (memory.max, cpu.max, pids.max), seccomp profile, capabilities, AppArmor/SELinux labels

Key insight: The spec defines what to isolate, not how. runc, runsc, and kata-runtime all implement this spec but use completely different isolation mechanisms underneath.

containerd shim v2: How Runtimes Plug In

In Kubernetes (and Docker via containerd), the containerd shim v2 is the integration point (containerd runtime v2 README). Each runtime provides a shim binary:

  • runc: containerd-shim-runc-v2
  • gVisor (runsc): containerd-shim-runsc-v1 (from gVisor containerd quick start)
  • Kata: containerd-shim-kata-v2 (from Kata containerd guide)

The shim starts the container and manages its lifecycle. containerd talks to the shim, which talks to the low-level runtime (runc/runsc/kata-runtime).

Kubernetes RuntimeClass

From Kubernetes RuntimeClass:

"RuntimeClass is a feature for selecting the container runtime configuration. The container runtime configuration is used to run a Pod's containers."

You define a RuntimeClass (e.g., gvisor, kata) that points to a shim, then set spec.runtimeClassName in your pod spec. Example from UK AISI's Inspect k8s provider, which uses gVisor: 

apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc

Pods with runtimeClassName: gvisor run under runsc instead of runc.

runc: The Reference OCI Runtime

Source: github.com/opencontainers/runc

runc is the reference implementation of the OCI runtime spec. It's written in Go and powers Docker, containerd, CRI-O, and most Kubernetes clusters by default.

How runc Works: Lessons 01–02 in Action

runc's core is libcontainer/ (libcontainer code), which implements:

  1. Namespace creation (libcontainer/nsenter): Calls unshare(2) and setns(2) to enter the new namespaces (mnt, pid, net, uts, ipc, user, cgroup, time).
  2. cgroups setup (libcontainer/cgroups): Creates a cgroup v2 (or v1) hierarchy and writes limits (memory.max, cpu.max, pids.max, io.max).
  3. seccomp-bpf (libcontainer/seccomp): Applies a BPF filter. Docker's default profile disables "around 44 system calls out of 300+" (Docker seccomp docs).
  4. overlayfs mount: Layers the read-only image and a writable upper layer.
  5. pivot_root: Changes the root filesystem to the container's rootfs, isolating it from the host.
  6. Drop capabilities: Removes dangerous capabilities (e.g., CAP_SYS_ADMIN, CAP_NET_ADMIN unless needed).
  7. Exec the entrypoint: Finally, execve(2) the container's init process.

Where syscalls go: Directly to the host kernel. This is the highest performance path (no interception), but every syscall the workload makes is a potential attack vector.

Performance Characteristics

  • Near-native: Syscall, I/O, and CPU overhead is negligible (typically <1%).
  • Density: Thousands of containers per host. SkyRL-OpenHands reports "80–100 containers per replica on nodes with just 16 CPUs" (vendor claim) using crun (a lighter C implementation of runc).
  • Cold start: Container creation is ~1–10ms (mostly cgroup setup and namespace entry). Image pull dominates cold start.

Who Uses runc

  • SWE-bench: Default Docker runtime (SWE-bench repo).
  • SWE-Gym: Pre-built per-instance images on Docker Hub (SWE-Gym repo).
  • OpenHands: Agent-server runs in runc containers (OpenHands repo).
  • SkyRL-OpenHands: crun + aiodocker for density (SkyRL-OpenHands).
  • DeepSWE: Started with Docker (runc), moved to Kubernetes when dockerd crashed under load (DeepSWE blog).

⚠️ Security Implication

From gVisor README:

"While using a single, shared kernel allows for efficiency and performance gains, it also means that container escape is possible with a single vulnerability."

runc is appropriate for:

  • Trusted code: Your own test suites, known open-source test harnesses
  • Single-tenant: One user per node (no multi-tenancy)
  • Defense in depth: Network isolation, seccomp allowlists, read-only rootfs

For adversarial evals or multi-tenant environments, use gVisor or microVMs.

gVisor: A Userspace Kernel for Containers

Source: github.com/google/gvisor
Documentation: gvisor.dev/docs

gVisor is not a container runtime in the traditional sense. It's a userspace kernel—an "application kernel"—that intercepts syscalls before they reach the host kernel.

Architecture: Sentry + Gofer

From gVisor Architecture Guide:

  • Sentry: The userspace kernel, written in Go. It implements ~280 Linux syscalls (per compatibility docs). The workload's syscalls are intercepted by a platform (see below) and handled by the Sentry.
  • Gofer: A per-sandbox file proxy. The Sentry itself has no direct filesystem access; it sends file I/O requests to the Gofer over a UNIX socket (9P protocol). The Gofer does the actual open(2), read(2), write(2) on the host.

Why this matters: The Sentry never directly opens host files or makes unfiltered syscalls. Its own syscall surface to the host is tiny and heavily filtered. From gVisor security docs:

"The Sentry's own access to the host is restricted by seccomp, namespaces, and capabilities. The host kernel attack surface is drastically reduced."

Platforms: How Syscalls Are Intercepted

From gVisor Platforms:

  • systrap (default since mid-2023): Uses SECCOMP_RET_TRAP to trap syscalls (the same mechanism you learned in Lesson 02). When the workload makes a syscall, the seccomp filter returns SECCOMP_RET_TRAP, which sends a SIGSYS signal. The Sentry's signal handler catches it and emulates the syscall. Fast on modern kernels; no KVM required.
  • KVM: Runs the workload in a VM-like context (using KVM but without a guest kernel). Syscalls trigger VM exits, which the Sentry handles. Best performance on bare metal with KVM. Not available in nested virt or on cloud VMs without nested virt.
  • ptrace: Uses ptrace(2) to intercept syscalls. Slower and deprecated; kept for compatibility.

Performance note: systrap is now the default because it works everywhere (no KVM needed) and is much faster than ptrace. On bare metal with KVM, the KVM platform is slightly faster.

Performance Characteristics

From gVisor Performance Guide:

  • Syscall overhead: Each syscall intercepted by the platform has overhead (typically a few hundred nanoseconds to a few microseconds, depending on the platform). For syscall-heavy workloads (e.g., getpid() in a tight loop), this adds up.
  • File I/O overhead: File operations go through the Sentry → Gofer → host kernel path. This adds latency, especially for many small reads/writes. The Sentry caches file data and metadata, but cold I/O is slower than native.
  • CPU-bound workloads: Once a workload is running CPU-bound code (tight loops, computation), there's little overhead because no syscalls are being made.

Real-world numbers: The gVisor team's own benchmarks are in the performance guide, but they don't publish hard percentages. For eval workloads:

  • HumanEval-style unit tests: Mostly CPU-bound after imports. Overhead is minimal (few percent).
  • SWE-bench-style builds: pip install, pytest discovery, and git operations are syscall-heavy and I/O-heavy. Expect 10–30% slowdown (measure on your workload).

Checkpoint/Restore

From gVisor Checkpoint/Restore:

Because the Sentry is the kernel, gVisor can checkpoint and restore the entire kernel state without needing kernel cooperation (unlike CRIU, which has to serialize host-kernel state). Features:

  • Lazy restore: runsc restore --background pages memory in lazily.
  • Application-driven checkpoint: Write to /proc/gvisor/checkpoint from inside the sandbox to trigger a checkpoint.
  • GPU support: cuda-checkpoint tool for checkpointing GPU state (see checkpoint docs).

Who Uses gVisor

  • Modal: "GPU Sandboxes are only supported with runtime="gvisor"" (Modal sandbox docs). Default runtime for most sandboxes.
  • Northflank: GPU sandboxes run on gVisor; CPU sandboxes run on Kata (Northflank docs).
  • UK AISI Inspect k8s provider: Uses gVisor RuntimeClass (inspect_k8s_sandbox).
  • Google Cloud Run, App Engine: gVisor powers Google's own multi-tenant container platforms (mentioned in gvisor.dev home).

When to Use gVisor

  • Multi-tenant or untrusted code: Strong isolation without VM overhead
  • GPU inside the sandbox: gVisor supports GPU passthrough (nvproxy); Kata+Firecracker does not (Kata hypervisors table)
  • Fast snapshot/restore: gVisor's checkpoint/restore is more robust than CRIU
  • No KVM available: systrap platform works on cloud VMs without nested virt

Kata Containers: Lightweight VMs as Pods

Source: github.com/kata-containers/kata-containers
Documentation: Kata architecture

Kata Containers is an OCI runtime that launches each pod (or container) in a lightweight VM with its own guest kernel. The workload never directly touches the host kernel—it only sees the guest kernel.

Architecture: VMM + kata-agent

From Kata architecture docs:

  • kata-runtime: The OCI-compatible frontend. It receives OCI commands and orchestrates VM creation.
  • VMM (Virtual Machine Monitor): The hypervisor. Kata supports multiple VMMs (see hypervisors.md):
    • QEMU: Full-featured, mature. Supports GPU passthrough, hotplug, live migration.
    • Cloud Hypervisor: Rust VMM, built for modern cloud workloads. Supports CPU/memory/PCI hotplug, live migration.
    • Firecracker: Minimal Rust VMM from AWS. Fast boot, low memory overhead. No GPU support (per the hypervisors table).
    • Dragonball, StratoVirt: Alternative lightweight VMMs.
  • kata-agent: Runs inside the guest VM. The runtime talks to the agent over vsock (a virtual socket) to execute commands, manage processes, and handle I/O.
  • virtio-fs: A shared filesystem between host and guest. The container rootfs is mounted via virtio-fs, so file I/O goes through the hypervisor but doesn't require copying the whole rootfs into the VM.

Performance Characteristics

  • Boot overhead: VM boot adds latency. With Firecracker, the spec target is ≤125ms from InstanceStart to guest init (Firecracker SPECIFICATION.md). With QEMU, boot can be hundreds of milliseconds.
  • Memory overhead: Each VM needs memory for the guest kernel and kata-agent (typically 50–150 MB, depending on the VMM and kernel config).
  • Syscall overhead: Once inside the VM, syscalls are native (to the guest kernel). Hypercalls (guest kernel → host kernel) are fast with KVM.
  • I/O overhead: virtio-fs adds some overhead vs native filesystem access, but it's much faster than gVisor's Gofer for large files.
  • Density: Lower than runc or gVisor, because each VM has per-VM memory. Northflank documents boot "in under a second" for Kata (vendor claim, Northflank docs).

Who Uses Kata

  • Northflank: CPU sandboxes run on Kata; GPU sandboxes run on gVisor (Northflank docs).
  • Azure Kubernetes Service (AKS): Offers Kata as a RuntimeClass for untrusted workloads (AKS pod sandboxing docs).
  • IBM Cloud: Uses Kata for its Kubernetes service (mentioned in Kata README).

Snapshot/Restore Support

Snapshot/restore depends on the VMM. Firecracker has full and diff snapshots (Firecracker snapshot docs). Cloud Hypervisor supports snapshots and live migration. QEMU supports snapshots but Kata's integration is less mature than E2B's direct Firecracker orchestration. For production snapshot/fork workflows, most platforms use Firecracker directly (E2B, Fly Machines) or gVisor (Modal).

When to Use Kata

  • Strongest isolation: Hardware virtualization, guest kernel, no shared kernel attack surface
  • Docker-in-sandbox or nested containers: The guest kernel supports full Docker/K8s inside. Modal sends these to runtime="vm" (which may be Kata or Firecracker; Modal's docs don't specify the VMM).
  • Custom kernel: You control the guest kernel and can add custom patches or modules
  • Regulatory compliance: Some compliance regimes require VM-level isolation

Avoid Kata for:

  • GPU workloads: Firecracker has no GPU support; QEMU/Cloud Hypervisor do, but gVisor is the more common GPU sandbox path
  • Extreme density: VM memory overhead limits density vs runc/gVisor
  • Fast snapshot/fork: gVisor's checkpoint/restore or E2B's direct Firecracker orchestration is more mature

Attack Surface Comparison

The fundamental question: What can an attacker compromise if they fully control the workload?

Runtime Boundary Attack Surface Escape Scenario
runc Host kernel syscall surface, filtered by seccomp ~300 syscalls minus ~44 blocked by Docker's default profile = ~256 syscalls exposed A kernel vulnerability in one of the allowed syscalls. The attacker can exploit it directly because the workload makes syscalls to the host kernel.
gVisor Sentry (userspace kernel) + Sentry's own filtered syscalls to host The Sentry's ~280 implemented syscalls (in Go) + the Sentry's own restricted syscall surface to the host (much smaller, ~20–30 syscalls per gVisor security docs, though exact count varies). 1) Exploit the Sentry itself (a bug in the Go syscall implementation), or 2) Exploit a vulnerability in one of the few syscalls the Sentry makes to the host. Much harder than runc because the Sentry is a smaller, more auditable codebase than Linux, and its host syscall surface is tiny.
Kata Hypervisor (KVM + VMM) + virtio devices The guest kernel's syscall surface (internal to the VM, not host), plus the VMM's device emulation (virtio net/block/vsock). KVM itself is a small attack surface (~50k lines vs 30M lines in Linux). 1) Exploit the guest kernel (only gives you control of the VM, not the host), then 2) exploit a hypervisor or virtio device vulnerability to escape to the host. This is a much higher bar than runc or gVisor. Hardware-level isolation (Intel VT-x/AMD-V) enforces the boundary.

Real-World Escapes

Container escapes (runc): Multiple CVEs in runc and the kernel have allowed container escape. Notable examples:

  • CVE-2019-5736 (runc): Overwriting the runc binary on the host by exploiting /proc/self/exe. Patched in runc 1.0-rc7.
  • Dirty Cow (CVE-2016-5195): Kernel race condition allowing write access to read-only memory mappings. Could be exploited from containers to write to host files.

gVisor: No known in-the-wild escapes to date. The Sentry has had bugs, but they typically result in Sentry crashes (denial of service inside the sandbox) rather than host compromise.

Kata/VM escapes: KVM and hypervisor escapes exist (e.g., Spectre/Meltdown side channels, specific QEMU device emulation bugs), but they are rare and typically require chaining multiple vulnerabilities.

Key Insight: Defense in Depth

No isolation mechanism is perfect. Production systems layer multiple defenses:

  • Network isolation: No network by default (Inspect AI), or strict egress filtering (E2B nftables, Modal, Daytona allowlists)
  • Read-only rootfs: Prevent writes to system directories
  • Seccomp allowlists: Even with gVisor or Kata, apply seccomp to reduce the available syscall set
  • Resource limits: cgroups to prevent DoS by exhaustion
  • Monitoring: Detect anomalous syscalls, process trees, or network activity

Decision Guide: Which Runtime for Your Eval Workload

Choose based on threat model, performance requirements, and infrastructure constraints.

Workload Type Recommended Runtime Rationale
Pure-Python unit tests
(HumanEval, MBPP)		 runc or crun CPU-bound after imports. Threat model: trusted code from known datasets. Highest density (hundreds per host). Use seccomp, no network, cgroup limits, read-only rootfs.
SWE-bench-style builds
(pip install, pytest, git clone)		 runc for trusted, gVisor for multi-tenant or untrusted Syscall-heavy and I/O-heavy. runc is fastest (SWE-bench, DeepSWE use it). gVisor adds 10–30% overhead but much stronger isolation. Kata is overkill unless you need nested containers or a custom kernel.
RL policy rollouts
(agentic evals, multi-turn)		 gVisor (or microVMs if you need snapshot/fork) Policies explore for reward hacks. Some hacks look like escape attempts. gVisor's Sentry significantly reduces attack surface. If you need fork-on-demand for GRPO/tree search, use gVisor checkpoint/restore or E2B's Firecracker fork.
GPU jobs
(inference, training inside sandbox)		 gVisor Modal: "GPU Sandboxes are only supported with runtime=gvisor". Northflank also uses gVisor for GPU. Kata+Firecracker has no GPU support. Kata+QEMU/Cloud Hypervisor can do GPU passthrough but is less common.
Docker-in-sandbox
(nested containers, FUSE, custom kernel modules)		 Kata (or direct Firecracker/Cloud Hypervisor) Needs a full guest kernel. Modal sends these to runtime="vm". gVisor's Sentry doesn't fully support nested containers or FUSE.
Multi-tenant SaaS
(different customers' code on same host)		 gVisor or Kata runc is insufficient for untrusted multi-tenant workloads. gVisor is lower overhead and works on cloud VMs; Kata needs bare metal or nested virt.
Regulated environments
(FedRAMP, PCI-DSS, HIPAA)		 Kata Some compliance frameworks require VM-level isolation. Check your specific requirements.

Infrastructure Constraints

  • No KVM (cloud VM without nested virt): Use runc or gVisor (systrap platform). Kata requires KVM.
  • Bare metal with KVM: All options available. gVisor KVM platform is fastest; Kata provides strongest isolation.
  • Kubernetes: Use RuntimeClass to select. runc is default; install gVisor or Kata via their respective K8s integrations.
  • Extreme density (1000+ sandboxes per host): runc or gVisor. Kata's per-VM memory limits density.

Build It Yourself: Benchmark runc vs gVisor

In this exercise, you'll measure the overhead of gVisor vs runc on three workload types: syscall-heavy, I/O-heavy, and CPU-bound. You'll run the same Python script under Docker with --runtime=runc and --runtime=runsc, then compare the timings.

Prerequisites

  • Docker installed (any recent version)
  • gVisor (runsc) installed and registered as a Docker runtime (see gVisor install guide)
  • Python 3.7+ (inside the Docker images; we'll use python:3.11-slim)

Step 1: Install gVisor and Register runsc as a Docker Runtime

Follow the official gVisor install guide. On Ubuntu/Debian: 

# Add the gVisor repository and install runsc
(
  set -e
  ARCH=$(uname -m)
  URL=https://storage.googleapis.com/gvisor/releases/release/latest/${ARCH}
  wget ${URL}/runsc ${URL}/runsc.sha512 \
    ${URL}/containerd-shim-runsc-v1 ${URL}/containerd-shim-runsc-v1.sha512
  sha512sum -c runsc.sha512 \
    -c containerd-shim-runsc-v1.sha512
  rm -f *.sha512
  chmod a+rx runsc containerd-shim-runsc-v1
  sudo mv runsc containerd-shim-runsc-v1 /usr/local/bin
)

Step 2: The Benchmark Script

Create benchmark.py: 

#!/usr/bin/env python3
"""
Benchmark script comparing syscall-heavy, I/O-heavy, and CPU-bound workloads.

This script times three types of work:
1. Syscall-heavy: many getpid() calls
2. I/O-heavy: many small file writes and reads
3. CPU-bound: computing primes

Run this under runc and runsc to measure overhead.
"""

import os
import sys
import time
import tempfile


def benchmark_syscalls(n=1_000_000):
    """
    Syscall-heavy: call getpid() in a tight loop.
    This measures syscall interception overhead.
    """
    start = time.perf_counter()
    for _ in range(n):
        os.getpid()
    elapsed = time.perf_counter() - start
    return elapsed


def benchmark_io(n=10_000):
    """
    I/O-heavy: write and read many small files.
    This measures file I/O overhead (Gofer path in gVisor).
    """
    with tempfile.TemporaryDirectory() as tmpdir:
        start = time.perf_counter()
        
        # Write phase
        for i in range(n):
            path = os.path.join(tmpdir, f"file_{i}.txt")
            with open(path, "w") as f:
                f.write(f"data {i}\n")
        
        # Read phase
        for i in range(n):
            path = os.path.join(tmpdir, f"file_{i}.txt")
            with open(path, "r") as f:
                _ = f.read()
        
        elapsed = time.perf_counter() - start
    return elapsed


def is_prime(n):
    if n < 2:
        return False
    for i in range(2, int(n**0.5) + 1):
        if n % i == 0:
            return False
    return True


def benchmark_cpu(limit=100_000):
    """
    CPU-bound: count primes up to limit.
    This should show minimal overhead once running (no syscalls in the hot loop).
    """
    start = time.perf_counter()
    count = sum(1 for i in range(2, limit) if is_prime(i))
    elapsed = time.perf_counter() - start
    return elapsed, count


def main():
    print("=== Container Runtime Benchmark ===")
    print(f"Python {sys.version}")
    print(f"PID: {os.getpid()}")
    print()
    
    print("1. Syscall-heavy (1M getpid calls)...")
    syscall_time = benchmark_syscalls(1_000_000)
    print(f"   Time: {syscall_time:.4f} seconds")
    print(f"   Per-call: {syscall_time / 1_000_000 * 1e6:.2f} microseconds")
    print()
    
    print("2. I/O-heavy (10K small file write+read)...")
    io_time = benchmark_io(10_000)
    print(f"   Time: {io_time:.4f} seconds")
    print(f"   Per-operation: {io_time / 10_000 * 1000:.2f} milliseconds")
    print()
    
    print("3. CPU-bound (count primes up to 100K)...")
    cpu_time, prime_count = benchmark_cpu(100_000)
    print(f"   Time: {cpu_time:.4f} seconds")
    print(f"   Primes found: {prime_count}")
    print()
    
    print("=== Summary ===")
    print(f"Syscall:  {syscall_time:.4f}s")
    print(f"I/O:      {io_time:.4f}s")
    print(f"CPU:      {cpu_time:.4f}s")
    print()
    print("(Measure on your own machine; do not fabricate data.)")


if __name__ == "__main__":
    main()

Step 3: Run the Benchmark

Run under runc: 

docker run --rm --runtime=runc -v "$(pwd)/benchmark.py:/benchmark.py" \
  python:3.11-slim python /benchmark.py

Run under runsc (gVisor): 

docker run --rm --runtime=runsc -v "$(pwd)/benchmark.py:/benchmark.py" \
  python:3.11-slim python /benchmark.py

Note the timings from both runs. Run each a few times and take the median to reduce noise.

Expected Observations

  • Syscall-heavy: runsc will be slower. Each getpid() is intercepted by the platform and handled by the Sentry. Expect 2–10× overhead (varies by CPU and platform).
  • I/O-heavy: runsc will be slower due to the Gofer path. Expect 1.5–3× overhead for small-file I/O.
  • CPU-bound: runsc should be close to runc (within 10%) because the hot loop makes no syscalls. The overhead is only during startup and the final print.

Step 5 (Optional): Add Kata if KVM is Available

If you have KVM and Kata installed, register it as a Docker runtime and run the same benchmark with --runtime=kata. Kata's syscall overhead should be minimal (native to the guest kernel), but you'll see VM boot overhead if you measure cold start.

Important: Measure Honestly

Do not fabricate results. The actual overhead depends on your CPU, kernel version, gVisor platform (systrap vs KVM), and workload. Your numbers will differ from others. The goal is to understand the trade-off, not to match a specific number.
