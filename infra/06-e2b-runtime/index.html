From First Principles to Production: E2B's Runtime

In Lessons 04 and 05, you booted Firecracker by hand, created snapshots via curl commands, and simulated GRPO-style forking in Python. Now you'll see how a production system orchestrates thousands of these workflows at scale.

E2B Runtime ( e2b-dev/runtime, Apache-2.0 license, formerly e2b-dev/infra) is the complete open-source backend that powers E2B Cloud. It provides isolated sandboxes—Firecracker microVMs that resume from snapshots, run agent code, and pause when idle—along with the API, orchestration, networking, storage, and template building needed to run them in production.

What You'll Learn

  • Why production sandbox systems separate control plane (API + placement) from data plane (Firecracker + orchestrator)
  • How E2B's architecture maps requests: SDK → REST API → placement → orchestrator → Firecracker → envd
  • Template building: Docker image → ext4 rootfs → Firecracker boot → snapshot → object storage
  • How pause/resume/fork work end-to-end: userfaultfd lazy memory, NBD copy-on-write rootfs, and diff storage
  • Where snapshots and memory files live, and how they are loaded lazily to minimize restore latency
  • How envd (the in-VM daemon) exposes process/filesystem APIs over Connect RPC and REST (port 49983)
  • Hands-on: deploy E2B Embed locally and create/pause/resume/fork a sandbox, measuring latency at each step

⚠️ Scope and Source Verification

Repository correction: The curriculum originally referenced e2b-dev/runtime as the main OSS repo, which is correct. This lesson uses e2b-dev/runtime (formerly e2b-dev/infra) as the authoritative source.

"E2B Embed" is the single-node deployment bundle (Docker Compose, Terraform, or Kubernetes) described in runtime/embed/. The hands-on exercise walks through local Embed deployment.

All performance numbers and architecture claims cite primary sources (E2B's ARCHITECTURE.md, source code, official docs, or labeled as vendor claims when self-reported).

Architecture Overview: Control Plane vs Data Plane

From E2B's ARCHITECTURE.md:

"Two ideas drive the design:
1. A sandbox is a resumed snapshot. Templates are pre-booted VM snapshots (memory + disk + VM state) stored in object storage. 'Creating' a sandbox means restoring a snapshot, which is why startup is fast.
2. Control plane and data plane are separate. The API decides where a sandbox runs and tracks that it runs (Postgres/Redis); the orchestrator on each node owns how it runs (Firecracker, networking, storage). Sandbox traffic never passes through the API."

Why Separate Control and Data Planes?

Scalability: The API can be horizontally scaled (stateless, load-balanced) independently of orchestrator nodes (which are stateful: each owns its running VMs).

Latency: Sandbox traffic (exec commands, file reads/writes) goes directly from the SDK to the orchestrator node's proxy, then to envd inside the VM. It never hops through the central API, avoiding an extra network round-trip.

Blast radius: An API restart or deploy doesn't kill running sandboxes. The orchestrator keeps them alive and reconnects to the API when it returns.

Control Plane: API, Placement, and Client Proxy

API Service (packages/api)

The control plane entry point, written in Go (Gin framework), port 80 (REST) and 5009/5109 (gRPC). OpenAPI spec: GET /openapi.json.

Key responsibilities:

  • Authentication: Team API keys (X-API-Key, e2b_ prefix), OIDC JWTs, admin tokens. Backed by Postgres + Redis team cache.
  • Sandbox lifecycle: Create, list, kill, pause, resume, connect, metrics, logs. Writes running sandbox records to Redis (source of truth for running sandboxes). Persistent entities (templates, builds, snapshots, teams) live in Postgres.
  • Placement: Keeps a live map of orchestrator nodes (discovered via Nomad, Kubernetes, or static list). Uses a best-of-K algorithm: sample K ready nodes, score by CPU load and hugepage-pool load, pick lowest. Retry with backoff on ResourceExhausted.
  • Rate limiting: Per-team, per-operation-group budgets enforced via Redis (distributed rate limiter). Returns HTTP 429 with Retry-After when exhausted.
  • Secrets: /secrets API for customer secret management. Secrets are stored as markers; orchestrator resolves markers to values at sandbox egress (envd never sees the secret value).

Placement: Best-of-K with Overcommit

From ARCHITECTURE.md (internal/orchestrator/placement/):

"Sample K ready nodes, score by the higher of CPU load and hugepage-pool load, pick the lowest; retry on exhausted nodes."

Why best-of-K instead of global min? Sampling K nodes (e.g., K=3) is cheaper than querying all nodes. It converges to the least-loaded node with high probability when the fleet is large, and it avoids a single coordination bottleneck.

Hugepage scoring: Enabled by default (BEST_OF_K_HUGEPAGE_MEMORY). E2B uses hugepages for guest memory to reduce TLB misses. A node with exhausted hugepage pools scores high, steering placement away from it.

Client Proxy (packages/client-proxy)

Runs on control-plane nodes (port 3002). Routes sandbox URLs ( https://{port}-{sandboxID}.domain) to the correct orchestrator node. Queries Redis for sandbox:routing:{id} (written by the orchestrator), then forwards HTTP/gRPC traffic to the node's proxy (:5007), which forwards to envd (:49983).

Auto-resume: If the sandbox is paused, the client proxy calls the API's gRPC ResumeSandbox endpoint (:5109), which tells the orchestrator to resume the snapshot. The request waits until the sandbox is running, then the proxy forwards the original request.

Data Plane: Orchestrator and envd

Orchestrator (packages/orchestrator)

A single Go binary running on every sandbox node (as root, since it manages Firecracker/KVM). Ports: gRPC :5008 (lifecycle), HTTP :5007 (proxy to envd). Source: pkg/, almost all Linux-only.

gRPC services:

  • SandboxService: Create, Update, List, Delete, Pause, Checkpoint. Update callbacks are serialized per sandbox (for timeout/network updates).
  • TemplateService: TemplateCreate, TemplateBuildStatus, TemplateBuildDelete (template-manager role only).
  • InfoService: Node identity, roles, capacity, health (/health returns HTTP 200 with status ready, draining, or shutting_down).

How the Orchestrator Drives Firecracker

From ARCHITECTURE.md (pkg/sandbox/):

  • Firecracker (fc/): Each sandbox is one Firecracker process in its own cgroup and network namespace. The FC HTTP API (Unix socket) configures machine, drives, network, and snapshots. Guest metadata (sandbox ID, envd access token hash) is passed via MMDS (Metadata Micro-Service, a virtio-MMDS device).
  • userfaultfd lazy memory (uffd/): The orchestrator runs a userfaultfd handler thread. When the guest touches a memory page, the handler fetches it from object storage and calls UFFDIO_COPY to map it. Prefetching: During template builds, E2B records which pages are accessed during boot. On resume, it prefetches those pages before starting the VM, so the first faults are instant.
  • Copy-on-write rootfs (rootfs/, nbd/, block/): The template rootfs stays read-only. Writes go to a per-sandbox CoW cache. The cache is exposed to Firecracker as an NBD (Network Block Device) block device, served by an in-process userspace NBD server. On pause, dirty blocks are exported as a diff.
  • Networking (network/): Each sandbox gets its own network namespace with a TAP device. The orchestrator creates veth pairs and bridges them. nftables rules provide egress filtering (allow/deny domains). Ingress is blocked by default (no port forwarding unless explicitly configured).
  • Snapshots (snapshots/): On Pause, the orchestrator calls Firecracker's CreateSnapshot API, which writes the memory file (guest RAM) and state file (device state JSON). These are uploaded to object storage as diffs against the template (only modified pages/blocks). On Resume, the orchestrator downloads the diff, applies it to the template snapshot, and restores via LoadSnapshot.

envd: The In-VM Agent (packages/envd)

envd is a daemon that runs inside every Firecracker VM (port 49983). It's the data-plane API that SDKs talk to for execution and file operations. From ARCHITECTURE.md:

"envd exposes processes, PTYs, filesystem operations, file watchers, and port forwarding over Connect RPC and REST. It is what the SDKs talk to when they 'run code'."

Protocols:

  • Connect RPC / HTTP/2: High-performance streaming for Filesystem and Process services. Defined in spec/envd/*.proto. SDKs use custom HTTP/2 clients with connection pooling to avoid concurrency bottlenecks.
  • REST: Defined in spec/envd/envd.yaml (OpenAPI). Endpoints:
    • GET /health: Probes service health (returns 204 when healthy)
    • GET /metrics: Resource usage metrics
    • POST /init: Internal endpoint (x-internal: true) for setting environment variables, volume mounts, initial user, working directory, CA certs. Called by the orchestrator after snapshot restore, before the sandbox is marked ready.
    • POST /freeze, POST /unfreeze: Internal endpoints (x-internal: true) that freeze/unfreeze user/PTY cgroups before pausing. This ensures processes don't write during snapshot capture.

Live upgrade: envd can be upgraded inside a running sandbox without dropping the workload. The orchestrator sends a new envd binary over vsock, envd execs the new binary, and the new process inherits the open sockets and running PTYs. (Implementation: packages/envd/, not detailed in public docs.)

Why envd Is Inside the VM

Isolation: Process and file APIs are served by envd, which runs inside the guest kernel's address space. If the orchestrator served these APIs from the host, a malicious guest could exploit the orchestrator and escape to the host. With envd inside the VM, the blast radius is contained: a compromised envd can only affect its own sandbox, not other sandboxes or the host.

Live upgrade: Because envd is just a user-space daemon inside the guest, it can be upgraded without rebooting the guest kernel or stopping Firecracker. The orchestrator pushes a new binary, envd execs it, and the sandbox continues running. Compare this to upgrading the Firecracker binary or the guest kernel, both of which require a full stop/start cycle.

Template Building: Docker Image → Snapshot

From E2B docs: How it works and ARCHITECTURE.md (packages/orchestrator/pkg/template/build):

"Every time you are building a sandbox template, we create a container based on the definition. We extract the container's filesystem, do provisioning and configuration (e.g. installing required dependencies), run layers commands and start a sandbox. Then, these steps happen:
  1. We take the running sandbox.
  2. (Only if you specified the start command) Execute the start command.
  3. Wait for readiness (by default 20 seconds if start command is specified, otherwise immediately ready). Readiness check can be configured using ready command.
  4. Snapshot the sandbox and make it ready for you to spawn it with the SDK.

The Template Build Workflow (Detailed)

From packages/orchestrator/pkg/template/build godoc:

  1. Get Docker image from the remote repository (e.g., Docker Hub).
  2. Inject new file layers with the required setup for hostname, DNS, envd service configuration, basic provisioning script that runs before most VM services.
  3. Extract ext4 filesystem from the layered OCI image. The orchestrator converts the OCI image layers (tar.gz) into a single ext4 block device image that Firecracker can mount as a virtio-blk drive.
  4. Start FC VM with BusyBox init that runs just the provisioning script. This installs systemd (which is used for proper VM boot later). Wait for exit.
  5. Start the FC VM (using systemd) and wait for envd to signal ready.
  6. Build the template steps/layers: run user-defined commands (.runCmd(["apt-get update", "pip install transformers"])). Each command runs in a shell inside the VM via envd.
  7. Restart the sandbox and run two additional commands:
    • Configuration script (enable swap, create user, change folder permissions, etc.)
    • Start command (if defined), together with the ready command (always with default value if not defined)
  8. Snapshot: call Firecracker's CreateSnapshot. This captures guest memory (memory file) and device state (state file JSON).
  9. Upload template (and all not-yet-uploaded layers) to object storage (S3/GCS). The template snapshot is now ready for sandboxes to resume from.

Filesystem-Only vs Full Snapshots

From ARCHITECTURE.md:

"A template can also be filesystem-only (rootfs, no memfile), taken by a filesystem-only pause or checkpoint; sandboxes created from it cold-boot from disk instead of resuming."
  • Full snapshot (default): Captures memory + device state. Sandboxes resume from the snapshot (fast: ~1s vendor claim, ~28ms measured independently with 256MB working set).
  • Filesystem-only snapshot: Captures only the rootfs (ext4 image), no memory. Sandboxes cold-boot from the rootfs (~125ms for minimal kernel + init, slower for full systemd boot). Use case: When you want a clean boot every time (e.g., testing init scripts), or when the memory footprint is too large for practical snapshot/restore.

Template Caching and Layers

From E2B docs: Caching:

"Templates are built in layers (similar to Docker layers). Each .runCmd() is a layer. Layers are cached: if you rebuild a template and only the last layer changed, E2B reuses the earlier layers' snapshots and only rebuilds the changed layer and subsequent layers."

How layer caching works: Each layer's snapshot is content-addressed by a hash of its inputs (base layer + commands). When you rebuild, E2B checks if a layer with the same hash already exists in object storage. If yes, it skips that layer. If no, it resumes the previous layer's snapshot, runs the new commands, and snapshots again.

Pause, Resume, and Lazy Memory

From ARCHITECTURE.md:

"Fresh creates, resumes after a pause, and forks all take the same path."

In E2B's architecture, create = resume. There is no "cold boot" for sandboxes in the normal runtime path. Every sandbox starts from a template snapshot, which was itself created by booting once and snapshotting.

The Resume Path (userfaultfd + NBD CoW)

From ARCHITECTURE.md (pkg/sandbox/):

  1. API receives create request: POST /sandboxes with template_id.
  2. Placement: API picks a node via best-of-K.
  3. Orchestrator resume: API sends gRPC Create to the orchestrator, which calls ResumeSandbox:
    • Memory: Fetch template snapshot header from object storage (contains memory file location and page list). Register guest memory range with userfaultfd. The orchestrator's userfaultfd handler thread is now waiting for page faults. Optional prefetch: If the template has a prefetch page list (recorded during template build), fetch those pages from object storage and map them before starting the VM.
    • Rootfs: Start the in-process NBD server. The server exposes a copy-on-write view of the template rootfs. Reads come from the template rootfs (read-only, in object storage or cached locally). Writes go to a per-sandbox cache file (sandboxFiles.SandboxCacheRootfsPath). Firecracker mounts this NBD device as its virtio-blk drive.
    • Networking: Create a network namespace, TAP device, and veth pair. Configure nftables egress rules (allow/deny domains based on team settings). The Firecracker process joins this netns via the jailer (Lesson 04's --netns).
    • Firecracker: Call LoadSnapshot API with the memory file and state file paths. Firecracker mmaps the memory file (which is backed by userfaultfd), restores device state, and calls KVM_RUN. The guest kernel resumes execution exactly where the snapshot was taken.
    • envd init: The orchestrator calls envd's POST /init endpoint to set environment variables, volume mounts, and the initial user. envd responds when ready.
  4. Routing record: The orchestrator writes sandbox:routing:{id} to Redis with the node ID and proxy URL.
  5. API response: Returns 201 Created with the sandbox ID and URL to the SDK.

The Pause Path (Diff Export)

From ARCHITECTURE.md:

"Pause diffs memory and disk against the template and ships the diff to object storage."
  1. API receives pause request: POST /sandboxes/{id}/pause.
  2. Orchestrator pause: API sends gRPC Pause to the orchestrator:
    • Freeze cgroups: Call envd's POST /freeze to freeze user/PTY cgroups. This ensures no processes are writing during snapshot capture.
    • Snapshot: Call Firecracker's CreateSnapshot. Firecracker writes the memory file (full guest RAM) and state file (device state JSON) to local disk.
    • Diff memory: Compare the memory file to the template's memory file. Only modified pages are uploaded to object storage. (Implementation: not detailed in public docs; likely compares page hashes or uses mincore(2) to find dirty pages.)
    • Diff rootfs: The NBD server has tracked all writes to the CoW cache. Export the dirty blocks as a diff file and upload to object storage.
    • Metadata: Write a snapshot header to object storage that references the template ID and the diff files (memory + rootfs).
  3. Stop Firecracker: Kill the Firecracker process. The sandbox is now paused (no CPU/memory cost on the host).
  4. Orchestrator writes state: Update Redis to mark the sandbox as paused. Write the snapshot metadata to Postgres.

Resume from Paused Snapshot

When the SDK calls POST /sandboxes/{id}/resume (or the client proxy auto-resumes on incoming traffic), the orchestrator:

  1. Fetch diff: Download the memory diff and rootfs diff from object storage.
  2. Apply diff: Merge the memory diff with the template's memory file (in-memory or on-disk, depending on cache). The NBD server merges the rootfs diff with the template rootfs.
  3. Resume: Follow the same resume path as a fresh create, but with the merged snapshot instead of the template snapshot.

Latency Breakdown (Vendor Claim)

From E2B persistence docs:

  • Pause: "approximately 4 seconds per 1 GiB of RAM" (vendor claim, includes memory snapshot capture + diff export + upload to object storage)
  • Resume: "approximately 1 second" (vendor claim, includes diff download + apply + Firecracker LoadSnapshot + userfaultfd lazy page-in for hot pages)

Independent measurement: A published benchmark reports ~28ms median restore latency for a 256MB working set on NVMe (Firecracker snapshot restore, not E2B's full stack). E2B's 1s figure includes network round-trips to object storage, so it's reasonable for a multi-GiB sandbox.

Fork: One Sandbox to N Children

From E2B fork docs:

"With the SDKs and the CLI you can request up to 20 forks at once."

Fork is the feature you learned about in Lesson 05: run an agent to step k, snapshot, then spawn N clones from that snapshot. Each child resumes from the same state, but with different RNG seeds, sampling parameters, or policies.

How Fork Works in E2B

From ARCHITECTURE.md:

"Fork checkpoints the original in place and spreads children across nodes."

The workflow:

  1. Parent sandbox running: Your agent code has executed to step k. The sandbox is in state S.
  2. SDK calls fork: POST /sandboxes/{id}/fork with count=N (up to 20).
  3. Checkpoint parent: The orchestrator pauses the parent sandbox (same as Pause: freeze cgroups, snapshot memory + rootfs, export diff, upload to object storage). The parent can optionally resume after checkpoint (controlled by API request flag).
  4. Spread children: The API picks N nodes (can be the same node if capacity allows, or spread across nodes via placement). For each child:
    • Send gRPC Create to the target orchestrator with the checkpoint snapshot ID (not the template ID).
    • The orchestrator resumes the checkpoint snapshot (which is a diff against the template) the same way it resumes a paused sandbox.
    • Reseed RNG: The orchestrator (or envd during init) writes unique entropy to each child's /dev/urandom to fix the RNG clone hazard (Lesson 05). (Implementation detail not specified in public docs; likely done via envd's POST /init with unique environment variables or a seed file.)
    • Unique MAC: Each child gets a unique MAC address (configured in Firecracker's network-interfaces config). The network namespace is also unique per child (each has its own TAP device).
  5. Return child IDs: The API returns a list of N sandbox IDs to the SDK. Each child is now an independent sandbox that the SDK can control separately.

Use Cases for Fork

  • GRPO-style rollouts: Run agent to decision point, fork N children, sample with different temperatures/seeds, compare outcomes for policy gradient update.
  • Tree search: At each branch point, fork N children to explore N different actions. Prune low-value branches, continue high-value ones.
  • A/B testing: Run setup once (install dependencies, clone repo), fork N children, run different versions of the code in each child.
  • Parallel eval: Run expensive setup (load model, warm cache), fork N children, run N eval instances in parallel.

Key Production Concerns You Didn't Build

  • Multi-tenancy: Per-team auth, rate limiting, quotas, separate object storage prefixes
  • Autoscaling: Nomad nodepool autoscaler (adds/removes nodes based on queue depth)
  • Graceful degradation: Orchestrator health checks, drain/shutdown, placement retries with backoff
  • Storage efficiency: Diff-based snapshots (only modified pages/blocks uploaded), layer caching for templates
  • Security: Seccomp filters (Lesson 02), nftables egress rules, secrets management (markers resolved at egress, not stored in VM)
  • Live upgrade: envd can be upgraded inside running sandboxes without reboot

Build It Yourself: Deploy E2B Embed Locally

In this exercise, you'll deploy E2B Embed (the single-node deployment bundle) locally, create a sandbox, execute commands, pause it, resume it, and measure the latency of each step. You'll also try forking a sandbox.

⚠️ Prerequisites

  • Linux with KVM: E2B uses Firecracker, which requires KVM (/dev/kvm). Check ls -l /dev/kvm.
  • Docker and Docker Compose: E2B Embed runs all services in containers.
  • 8GB+ RAM: The full stack (Postgres, Redis, ClickHouse, API, orchestrator, Firecracker VM) needs ~4-6GB RAM. Your host needs more to run comfortably.
  • Root access: The orchestrator runs as root (for Firecracker/KVM/networking).
  • Go 1.21+, Node.js 18+, or Python 3.10+: For the SDK example (pick one language).

If you don't have KVM: You can read the exercise and understand the workflow, but you won't be able to run Firecracker. The E2B team recommends an AWS EC2 .metal instance or a GCP VM with nested virtualization enabled.

#!/usr/bin/env python3

    Template()

    .run_cmd([
        "apt-get update",
        "apt-get install -y python3 python3-pip"
    ])
)

# Build the template locally
Template.build(
    template,
    "python-sandbox",
    on_build_logs=default_build_logger(),
    api_url="http://localhost:3000"  # Point to local Embed API

Expected output: The template builder boots a Firecracker VM, runs the commands, snapshots the VM, and uploads the snapshot to local storage. This takes ~30-60 seconds (first boot is slow because layers must be built).

Step 5: Create, Exec, Pause, Resume, Measure Latency

Create sandbox_lifecycle.py: 

#!/usr/bin/env python3
"""
E2B sandbox lifecycle: create, exec, pause, resume, measure latency.
"""
import time
from e2b import Sandbox

def measure(label, fn):
    start = time.time()
    result = fn()
    elapsed = (time.time() - start) * 1000  # milliseconds
    print(f"{label}: {elapsed:.1f}ms")
    return result

# Configure for local Embed
api_url = "http://localhost:3000"

print("=== Create Sandbox ===")
sandbox = measure(
    "Create from template",
    lambda: Sandbox(
        template="python-sandbox",
        api_url=api_url
    )
)
print(f"Sandbox ID: {sandbox.id}")

print("\n=== Execute Commands ===")
def exec_hello():
    result = sandbox.commands.run("echo 'Hello from E2B'")
    return result.stdout

output = measure("Exec echo", exec_hello)
print(f"Output: {output}")

def exec_python():
    result = sandbox.commands.run("python3 -c 'print(sum(range(100)))'")
    return result.stdout

output = measure("Exec python", exec_python)
print(f"Output: {output}")

print("\n=== Pause Sandbox ===")
measure("Pause", lambda: sandbox.pause())

print("\n=== Resume Sandbox ===")
measure("Resume", lambda: sandbox.connect())

print("\n=== Post-Resume Exec ===")
output = measure("Exec after resume", exec_hello)
print(f"Output: {output}")

print("\n=== Kill Sandbox ===")
measure("Kill", lambda: sandbox.kill())

print("\nDone!")

Run it: 

python3 sandbox_lifecycle.py

What to observe: The script prints timing measurements for each operation. Latency varies based on your hardware (CPU, disk speed, RAM), the size of the sandbox's working set, and whether the node has cached the template's snapshot. Print and compare your own measurements rather than expecting specific numbers.

Context: E2B Cloud (with distributed object storage and optimized networking) reports pause takes approximately 4 seconds per 1 GiB of RAM and resume takes approximately 1 second (vendor claims from E2B persistence docs). Independent benchmarks report ~28ms median restore latency for Firecracker snapshot restore alone (256MB working set, NVMe, from DOI 10.63721/26jsea0149). Your local Embed deployment will have different characteristics.

Step 6 (Optional): Fork a Sandbox

Create fork_test.py: 

#!/usr/bin/env python3
"""
E2B fork test: create sandbox, run prefix, fork N children, sample differently.
"""
import time
from e2b import Sandbox

api_url = "http://localhost:3000"

print("=== Create Parent Sandbox ===")
parent = Sandbox(template="python-sandbox", api_url=api_url)
print(f"Parent ID: {parent.id}")

print("\n=== Run Prefix (Setup) ===")
parent.commands.run("echo 'Setup complete' > /tmp/prefix_done")
result = parent.commands.run("cat /tmp/prefix_done")
print(f"Prefix output: {result.stdout}")

print("\n=== Fork 3 Children ===")
start = time.time()
children = parent.fork(count=3)  # Fork up to 20 at once
elapsed = (time.time() - start) * 1000
print(f"Fork 3 children took: {elapsed:.1f}ms")

print(f"Child IDs: {[c.id for c in children]}")

print("\n=== Sample Differently in Each Child ===")
for i, child in enumerate(children):
    # Each child sees the prefix output
    result = child.commands.run("cat /tmp/prefix_done")
    print(f"Child {i}: prefix output: {result.stdout}")
    
    # Run different sampling (simulate GRPO-style rollout)
    seed = 42 + i  # Unique seed per child
    result = child.commands.run(f"python3 -c 'import random; random.seed({seed}); print(random.randint(0, 100))'")
    print(f"Child {i}: sampled value: {result.stdout}")

print("\n=== Kill All ===")
parent.kill()
for child in children:
    child.kill()

print("Done!")

Run it: 

python3 fork_test.py

Expected output: Each child resumes from the parent's state (sees /tmp/prefix_done) and samples a different random value (unique seed per child). Fork latency depends on whether the children are placed on the same node (fast: local snapshot copy) or spread across nodes (slower: network transfer of checkpoint diff).

Going Further: Production Deployment

E2B Embed is for single-node development and testing. For production, you'll want:

  • Multi-node orchestrator: Deploy orchestrators on multiple nodes (Nomad, Kubernetes, or Terraform). The API's placement algorithm distributes sandboxes across nodes.
  • Distributed object storage: Use S3, GCS, or Azure Blob instead of local storage. This lets any orchestrator node fetch any template/snapshot.
  • Monitoring: OpenTelemetry tracing, ClickHouse metrics, Grafana dashboards.
  • Autoscaling: Nomad nodepool autoscaler or Kubernetes HPA to add/remove nodes based on queue depth.

See runtime/self-host.md for Terraform deployment guides (GCP, AWS, Azure).
