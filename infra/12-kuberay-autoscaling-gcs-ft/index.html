From Single-Cluster Ray to Production Kubernetes Deployment

In Lessons 10 and 11, you learned Ray's execution model (tasks, actors, object store, GCS) and resource-aware scheduling (placement groups, gang scheduling). You ran Ray on a local cluster (ray.init()) or manually started clusters (ray start --head). But when you need to run 1,000-node eval clusters in production, you need:

  • Declarative cluster management: Define desired state (cluster size, resources, autoscaling policy) in YAML; let an operator reconcile actual state to match it.
  • Autoscaling: Add worker nodes when demand exceeds supply; remove idle nodes to save cost.
  • Fault tolerance: Survive head node restarts, GCS crashes, worker failures.
  • Integration with Kubernetes ecosystem: Use existing auth (RBAC), networking (services, ingress), monitoring (Prometheus), logging (Fluentd).

KubeRay (github.com/ray-project/kuberay, Apache-2.0) is the official Kubernetes operator for Ray. It provides three custom resource definitions (CRDs): RayCluster (long-lived clusters), RayJob (ephemeral clusters for batch jobs), and RayService (Ray Serve deployments with zero-downtime upgrades). The operator watches these CRDs, creates/deletes Pods, configures services, and coordinates the Ray autoscaler (runs as a sidecar container in the head Pod).

What You'll Learn

  • KubeRay operator architecture: CRD controllers, reconcile loops, and how it manages Pod lifecycle
  • RayCluster CRD spec: head/worker group specs, autoscaling config, enableInTreeAutoscaling, rayStartParams
  • Ray autoscaler v1 (legacy, deprecated) vs v2 (current): how autoscaler v2 runs as a sidecar, uses GCS to read resource demand, and scales worker groups via the KubeRay operator's RayCluster status
  • Autoscaler decision logic: resource demand (pending tasks/actors/placement groups), idle timeout (default 60s), min/max replicas, upscaling speed (per-worker-group quotas)
  • GCS fault tolerance with external Redis: --external-storage-namespace, RAY_REDIS_ADDRESS, what GCS stores in Redis, recovery behavior
  • Head node sizing: GCS + autoscaler + dashboard CPU/memory overhead, when the head becomes a bottleneck
  • Three production failure modes: (1) head node bottleneck (GCS overload, autoscaler thrashing), (2) object store full / spilling, (3) actor/worker death and restart semantics
  • How this applies to untrusted eval sandboxes and RL rollouts at scale
  • Hands-on: Deploy Ray on kind with KubeRay operator, create a RayCluster with autoscaling enabled, submit demand and observe worker Pods scale up/down, simulate GCS failure and recovery

KubeRay Operator: Architecture and Reconcile Loops

KubeRay is a Kubernetes operator: a control loop that watches custom resources (CRs) and reconciles actual cluster state to match the desired state defined in those CRs. From the KubeRay v1.2.2 README:

"KubeRay is a powerful, open-source Kubernetes operator that simplifies the deployment and management of Ray applications on Kubernetes."

Three Custom Resource Definitions

KubeRay defines three CRDs (from the README):

  • RayCluster: "KubeRay fully manages the lifecycle of RayCluster, including cluster creation/deletion, autoscaling, and ensuring fault tolerance."
  • RayJob: "With RayJob, KubeRay automatically creates a RayCluster and submits a job when the cluster is ready. You can also configure RayJob to automatically delete the RayCluster once the job finishes."
  • RayService: "RayService is made up of two parts: a RayCluster and a Ray Serve deployment graph. RayService offers zero-downtime upgrades for RayCluster and high availability."

This lesson focuses on RayCluster (long-lived clusters for eval/RL orchestration). RayJob and RayService are variants built on top of RayCluster.

Operator Components

The KubeRay operator runs as a Deployment in your Kubernetes cluster. From the source code at ray-operator/controllers/ray/raycluster_controller.go (the RayCluster controller), the operator:

  1. Watches RayCluster CRs: Uses Kubernetes watch API to get notified when a RayCluster is created, updated, or deleted.
  2. Reconciles head Pod: Creates a head Pod (if missing), configures it with ray start --head command, exposes services (dashboard, GCS, client ports).
  3. Reconciles worker Pods: For each worker group in the RayCluster spec, creates Pods with ray start --address=... command to join the cluster.
  4. Handles autoscaling: If enableInTreeAutoscaling: true, the operator injects a Ray autoscaler sidecar into the head Pod. The autoscaler reads resource demand from GCS and updates the RayCluster status with desired replica counts; the operator reconciles worker Pods to match.
  5. Monitors health: Watches Pod status (Ready, Running, Failed), updates RayCluster status conditions, recreates failed Pods.

Reconcile Loop: From CR to Running Cluster

From raycluster_controller.go lines 174-180: 

// Reconcile reads that state of the cluster for a RayCluster object and makes changes based on it
// and what is in the RayCluster.Spec
// Automatically generate RBAC rules to allow the Controller to read and write workloads

// +kubebuilder:rbac:groups=ray.io,resources=rayclusters/status,verbs=get;update;patch
// +kubebuilder:rbac:groups=ray.io,resources=rayclusters/finalizers,verbs=update
// +kubebuilder:rbac:groups=core,resources=events,verbs=get;list;watch;create;update;patch;delete

The reconcile loop (simplified; lines 182-400):

  1. Fetch the RayCluster CR from the API server
  2. If the CR is being deleted (has deletionTimestamp), clean up Pods and services, then remove finalizer
  3. Reconcile the head Pod: check if it exists; if not, create it with spec.headGroupSpec template
  4. Reconcile worker groups: for each spec.workerGroupSpecs[i], create/update/delete Pods to match desired replicas
  5. If autoscaling is enabled, read status.desiredWorkerReplicas (written by autoscaler sidecar) and adjust worker Pods
  6. Update RayCluster status.state (ready, unhealthy, failed) and status.availableWorkerReplicas

RayCluster CRD: Anatomy of a Cluster Definition

A RayCluster CR defines a Ray cluster's desired state. From Ray 2.40.0 Docs: RayCluster Quick Start, a minimal RayCluster YAML: 

apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: raycluster-example
spec:
  rayVersion: '2.40.0'
  headGroupSpec:
    rayStartParams:
      dashboard-host: '0.0.0.0'
    template:
      spec:
        containers:
        - name: ray-head
          image: rayproject/ray:2.40.0
          resources:
            limits:
              cpu: "2"
              memory: "4Gi"
            requests:
              cpu: "2"
              memory: "4Gi"
          ports:
          - containerPort: 6379  # GCS
            name: gcs-server
          - containerPort: 8265  # Dashboard
            name: dashboard
          - containerPort: 10001 # Ray client
            name: client
  workerGroupSpecs:
  - replicas: 2
    minReplicas: 1
    maxReplicas: 10
    groupName: small-group
    rayStartParams: {}
    template:
      spec:
        containers:
        - name: ray-worker
          image: rayproject/ray:2.40.0
          resources:
            limits:
              cpu: "1"
              memory: "2Gi"
            requests:
              cpu: "1"
              memory: "2Gi"

Key Fields

  • rayVersion: Ray version. Must match the image tag (e.g., rayproject/ray:2.40.0).
  • headGroupSpec: Head Pod template. Contains rayStartParams (flags for ray start --head) and template (Pod spec: containers, resources, volumes).
  • workerGroupSpecs: Array of worker groups. Each group has:
    • groupName: Unique name (e.g., "cpu-group", "gpu-group")
    • replicas: Desired replica count (static, if autoscaling disabled)
    • minReplicas / maxReplicas: Autoscaling bounds (if enabled)
    • rayStartParams: Flags for ray start on workers
    • template: Pod spec

rayStartParams: Ray CLI Flags

rayStartParams is a map of flags passed to ray start. From Ray 2.40.0 Docs: Configure RayCluster:

"rayStartParams are the parameters used in the ray start command to start the Ray cluster. [...] For the head node, you must include --port=6379, --dashboard-host=0.0.0.0 if you want to expose dashboard to external traffic."

Common rayStartParams (from Ray 2.40.0 Docs: ray start CLI):

  • --num-cpus: Override logical CPU count (default: auto-detected)
  • --num-gpus: Override GPU count (default: auto-detected via CUDA_VISIBLE_DEVICES)
  • --resources: Custom resources, JSON format (e.g., "{\"tpu\": 4}")
  • --object-store-memory: Plasma object store size in bytes (default: 30% of RAM)
  • --dashboard-host: Dashboard bind host (default localhost; set to 0.0.0.0 to expose on all interfaces)
  • --dashboard-port: Dashboard port (default 8265)
  • --metrics-export-port: Prometheus metrics port (default: random)

Autoscaling Config: enableInTreeAutoscaling and Worker Group Bounds

To enable autoscaling, add enableInTreeAutoscaling: true to the RayCluster spec, and set minReplicas / maxReplicas on worker groups. From Ray 2.40.0 Docs: RayCluster Configuration — Autoscaling:

"To enable autoscaling, set enableInTreeAutoscaling: true in the RayCluster spec. Then the KubeRay operator will inject an autoscaler container into the Ray head pod, which will create and delete Ray worker pods based on resource demands." 
spec:
  enableInTreeAutoscaling: true
  workerGroupSpecs:
  - groupName: worker-group
    replicas: 1          # Initial replicas (ignored after first scale event)
    minReplicas: 0       # Scale down to 0 if idle
    maxReplicas: 100     # Scale up to 100 workers max
    rayStartParams:
      num-cpus: "4"
    template:
      spec:
        containers:
        - name: ray-worker
          image: rayproject/ray:2.40.0
          resources:
            requests:
              cpu: "4"
              memory: "8Gi"

Key points:

  • replicas sets the initial count when the cluster is created. After the first autoscaler decision, the autoscaler overrides this value by writing to status.desiredWorkerReplicas.
  • minReplicas: 0 allows scaling to zero (workers removed when idle). Use minReplicas: 1 to keep at least one worker always running (lower startup latency for new work).
  • maxReplicas caps the number of workers. The autoscaler will never request more than maxReplicas per group.

Ray Autoscaler: v1 vs v2, Decision Logic, and Sidecar Integration

The Ray autoscaler adds/removes nodes (or in KubeRay, worker Pods) based on resource demand. Ray has two autoscaler versions:

  • Autoscaler v1 (legacy): Python script that runs on the head node, reads cluster state via SSH/cloud APIs, launches/terminates nodes with cloud provider APIs (EC2, GCE, Azure). Deprecated as of Ray 2.0.
  • Autoscaler v2 (current): Go/Python component that reads demand from Ray GCS, writes desired node counts to a backend (KubeRay operator for Kubernetes, cloud APIs for VMs). In KubeRay, runs as a sidecar container in the head Pod.

Autoscaler v2 in KubeRay: Sidecar Architecture

From Ray 2.40.0 Docs:

"the KubeRay operator will inject an autoscaler container into the Ray head pod"

The autoscaler sidecar runs ray kuberay-autoscaler (source: python/ray/autoscaler/v2/sdk.py). It:

  1. Connects to GCS (via ray._private.gcs_utils.GcsClient) to read:
    • Pending tasks/actors (resource requests not yet fulfilled)
    • Placement groups (PENDING placement groups that need resources)
    • Cluster resource availability (total resources, used resources per node)
  2. Runs a control loop every autoscaler_update_interval_s (default 5 seconds; from python/ray/autoscaler/v2/_private/constants.py line 15: AUTOSCALER_UPDATE_INTERVAL_S = 5).
  3. For each worker group, calculates desired replicas based on:
    • Resource demand: Sum of pending resource requests
    • Idle timeout: Nodes idle for more than idle_timeout_minutes (default 5 minutes; from Ray 2.40.0 Docs: Configuring Autoscaling, the default is "a node will be idle-terminated after 5 minutes") are marked for scale-down
    • Min/max bounds: Clamp to minReplicas and maxReplicas
  4. Writes desired replica counts to the RayCluster CR's status.desiredWorkerReplicas field via Kubernetes API
  5. The KubeRay operator watches status.desiredWorkerReplicas, reconciles actual worker Pods to match

Upscaling Speed: How Fast Can the Autoscaler Scale Up?

The autoscaler scales up gradually to avoid resource exhaustion and API rate limits. From Ray 2.40.0 Docs: Configuring Autoscaling:

"upscaling_speed: A number from [0, 1] which controls the aggressiveness of upscaling. The default is 1.0, which immediately adds nodes to the cluster if resources are unavailable."

In KubeRay, this translates to per-worker-group quotas. From the autoscaler source code at python/ray/autoscaler/_private/autoscaler.py lines 350-360: 

# Simplified excerpt (actual code is more complex)
def _get_node_launch_quota(self, node_type, current_count, target_count):
    """Calculate how many nodes of node_type to launch this iteration."""
    upscaling_speed = self.config.get("upscaling_speed", 1.0)
    # Default: launch all at once if upscaling_speed=1.0
    # Lower values throttle: upscaling_speed=0.5 → launch 50% of delta per iteration
    max_launch_batch = max(5, int(upscaling_speed * (target_count - current_count)))
    return min(max_launch_batch, target_count - current_count)

Example: If upscaling_speed: 1.0 (default), the autoscaler launches all needed workers at once. If upscaling_speed: 0.2, it launches 20% of the delta per iteration (every 5 seconds), taking several iterations to reach target count.

Why throttle? Prevent Pod scheduler churn in large clusters. If you request 1,000 new Pods instantly, Kubernetes scheduler may struggle to place them, and some may fail to schedule (Pending due to resource fragmentation). Throttling to upscaling_speed: 0.5 launches 500, waits 5 seconds for them to register, then launches the next 500.

Downscaling: Idle Timeout and Scale-to-Zero

Workers are removed if they are idle (no tasks running) for more than idle_timeout_minutes. From Ray docs:

"idle_timeout_minutes: The number of minutes that need to pass before an idle node is removed by the Autoscaler. Defaults to 5."

This is implemented as an idle timeout per worker. From the autoscaler source at python/ray/autoscaler/_private/autoscaler.py lines 600-620: 

# Simplified excerpt
def _node_is_idle(self, node_id):
    """Check if node has no running tasks/actors and has been idle > idle_timeout."""
    idle_timeout_s = self.config.get("idle_timeout_minutes", 5) * 60
    node_idle_duration = time.time() - self.node_tracker[node_id].last_used_time_s
    return node_idle_duration > idle_timeout_s and not self._node_has_active_tasks(node_id)

Scale-to-zero: If minReplicas: 0, all workers in a group can be removed when idle. The next task submission will trigger scale-up, but there will be a cold-start delay (Pod creation + Ray worker initialization, typically 20-60 seconds depending on cluster/image size).

Trade-off: minReplicas: 0 saves cost (no idle workers running), but adds latency for bursty workloads. minReplicas: 1 or higher keeps a warm pool.

Autoscaler Metrics and Observability

The autoscaler exposes Prometheus metrics at :8080/metrics on the head Pod's autoscaler container (from python/ray/autoscaler/v2/metrics.py):

  • autoscaler_cluster_resources: Total/used/available resources per resource type (CPU, GPU, memory)
  • autoscaler_pending_nodes: Number of nodes pending creation
  • autoscaler_running_nodes: Current node count per node type
  • autoscaler_failed_create_nodes: Count of nodes that failed to create
  • autoscaler_pending_resources: Pending resource requests (tasks/actors waiting for resources)

You can scrape these metrics with Prometheus and visualize in Grafana. See Ray 2.40.0 Docs: Using Prometheus and Grafana for setup instructions.

GCS Fault Tolerance with External Redis

In Lesson 10, you learned that the GCS (Global Control Service) is Ray's control plane: it stores actor locations, node membership, placement groups, and jobs. By default, GCS stores this metadata in-memory. If the head node crashes, the cluster is unrecoverable. From Ray 2.40.0 Docs: GCS Fault Tolerance:

"By default, the GCS is not fault tolerant ... its failure means that the entire Ray cluster fails. [...] To make the GCS fault tolerant, you need to use an external Redis instance."

How GCS Fault Tolerance Works

GCS FT (fault tolerance) uses Redis as an external metadata store. From the docs:

"When GCS FT is enabled, all cluster-level data will be persisted in an external Redis instance. When the GCS restarts (either on the same node or a different node), it will reload the data from Redis and continue serving as if it never crashed."

What GCS stores in Redis:

  • Actor metadata: ActorID → node address, state (ALIVE, DEAD, RESTARTING)
  • Placement group metadata: PlacementGroupID → bundle specs, node assignments, state (PENDING, CREATED)
  • Node membership: NodeID → raylet address, resources, heartbeat timestamp
  • Job metadata: JobID → driver address, config

What GCS does NOT store: Task metadata (stored by task owners), object data (stored in Plasma on worker nodes), worker process states. GCS FT ensures control plane continuity, not data plane state.

Enabling GCS FT in KubeRay

From Ray 2.40.0 Docs: GCS Fault Tolerance (KubeRay):

"To enable GCS FT with KubeRay, you need to: (Step 1) Set up an external Redis instance. (Step 2) Configure the RayCluster CR to use the external Redis."

Step 1: Deploy Redis (example with Bitnami Helm chart): 

helm repo add bitnami https://charts.bitnami.com/bitnami
helm install redis bitnami/redis --set auth.enabled=true --set auth.password=mypassword

Redis will be accessible at redis-master.default.svc.cluster.local:6379 (assuming default namespace).

Step 2: Add RAY_REDIS_ADDRESS and Redis password to RayCluster CR. From the docs, modify headGroupSpec.template.spec.containers[0].env: 

spec:
  headGroupSpec:
    template:
      spec:
        containers:
        - name: ray-head
          image: rayproject/ray:2.40.0
          env:
          - name: RAY_REDIS_ADDRESS
            value: "redis-master.default.svc.cluster.local:6379"
          - name: RAY_REDIS_PASSWORD
            valueFrom:
              secretKeyRef:
                name: redis
                key: redis-password
        rayStartParams:
          external-storage-namespace: "ray-gcs-ft"  # Namespace for Redis keys
          dashboard-host: '0.0.0.0'

external-storage-namespace: A Redis key prefix (e.g., "ray-gcs-ft"). GCS writes keys like ray-gcs-ft:ActorTable:<ActorID>. Use different namespaces for different Ray clusters sharing the same Redis instance.

What Happens During GCS Recovery

From Ray 2.40.0 Docs:

"During the GCS recovery, the following Ray operations are available: Running Ray tasks and actors will continue to run. [...] Any existing objects will continue to be available. [...] The following operations are unavailable: Actor creation/deletion/reconstruction. [...] Placement group operations. [...] Submitting new tasks, which require new worker processes to be created. [...] Resource management."

Recovery time: From the docs: "The recovery time is proportional to the amount of data stored in Redis and the network latency between GCS and Redis. In practice, recovery takes a few seconds for typical cluster sizes (<100 nodes)."

Head Node Restart in KubeRay with GCS FT

In KubeRay, if the head Pod crashes:

  1. Kubernetes restarts the Pod (if restartPolicy: Always)
  2. GCS process starts, connects to external Redis, reloads metadata
  3. Workers detect head node IP change (via service), reconnect to GCS
  4. GCS resumes serving: actor directory lookups, node membership, placement group scheduling

Caveat: If the head Pod moves to a different node (e.g., node failure), the head's Plasma object store is lost (objects stored on the old head node). Tasks/actors that depended on those objects may fail. Use lineage reconstruction (Lesson 10) or store critical data in an external store (S3, database).

Three Production Failure Modes

Even with KubeRay and GCS FT, Ray clusters fail in predictable ways. Understanding these failure modes helps you design robust eval/RL systems.

Failure Mode 1: Head Node Bottleneck (GCS Overload)

Symptom: Tasks take seconds to schedule, even though workers have free resources. Dashboard shows high head Pod CPU usage (>80%). Autoscaler thrashes (adds workers, then removes them immediately).

Root cause: GCS runs on the head node and coordinates:

  • Actor registration/lookups (every actor creation + method call)
  • Node heartbeats (every worker sends heartbeat every 1 second by default)
  • Autoscaler queries (every 5 seconds, reads pending tasks + cluster resources)
  • Dashboard queries (frequent UI refreshes)

In a 1,000-worker cluster with 10,000 actors and 100,000 tasks/second, GCS can become CPU-bound. From Ray 2.0 Architecture Whitepaper:

"the GCS manages metadata that is less frequently accessed but likely to be used by most or all workers in the cluster"

but at large scale (1,000+ nodes), "less frequently" still means millions of requests per minute.

Solutions:

  • Increase head node CPU: Use 8-16 CPUs for the head Pod. From Ray docs: Configure RayCluster — Head Node: "For large clusters (>100 nodes), consider using a larger head node (8+ CPUs, 32+ GB memory)."
  • Reduce GCS load: Batch actor operations (create 100 actors at once, not 100 sequential .remote() calls). Use fewer, long-lived actors instead of many short-lived ones.
  • Tune heartbeat interval: Increase raylet_heartbeat_period_milliseconds from default 1000ms to 5000ms (trade-off: slower failure detection). Set via rayStartParams with _system_config={"raylet_heartbeat_period_milliseconds":5000}.

Failure Mode 2: Object Store Full / Spilling Overhead

Symptom: Tasks slow down dramatically after initial fast progress. Logs show "Spilling objects to disk" or "Object store full" warnings. Worker Pods have high disk I/O (if spilling to local disk).

Root cause: Plasma object store (30% of worker RAM by default) is full. Ray spills objects to disk. From Lesson 10:

"when memory pressure is detected, pinned objects are automatically spilled from shared memory to external storage (local disk or S3). [...] Object spilling is fully abstracted away to user applications."

but spilling is slow: disk I/O latency is 100× slower than RAM access. If your workload creates many large objects (e.g., 1 GB per task), and you have 100 concurrent tasks per worker, you need 100 GB of object store per worker — far more than the default 30% of RAM.

Solutions:

  • Increase object store size: Set --object-store-memory in rayStartParams. Example: for a worker with 64 GB RAM, allocate 40 GB to object store: 
    rayStartParams:
  object-store-memory: "42949672960"  # 40 GB in bytes
  • Reduce working set: Process results in smaller batches. Call del on ObjectRefs when done, or use ray.get immediately after task completion (retrieves value and deletes ObjectRef).
  • Stream results to external store: Instead of returning large results to the driver (which stores them in driver's object store), write directly to S3/database from workers.
  • Use NVMe for spilling: If spilling is unavoidable, use fast NVMe disks. Configure spill directory via _system_config: object_spilling_config="{\"type\":\"filesystem\",\"params\":{\"directory_path\":\"/mnt/nvme/spill\"}}".

Failure Mode 3: Actor/Worker Death and Restart Semantics

Symptom: Actors crash mid-execution, and tasks that depend on them fail with RayActorError: The actor died unexpectedly. Some actors restart, others don't.

Root cause: Worker Pods can die for many reasons:

  • OOM kill: Pod exceeds memory limit, Kubernetes kills it
  • Node failure: Node crashes, all Pods on it are lost
  • Autoscaler scale-down: Idle worker removed by autoscaler (if running actors on it, they die)
  • User code crash: Uncaught exception in actor __init__ or method

Ray's restart semantics: From Ray 2.40.0 Docs: Task Fault Tolerance:

"By default, Ray will not retry failed tasks. You can change this behavior by setting max_retries."

For actors, from Ray 2.40.0 Docs: Actor Fault Tolerance:

"By default, Ray will not restart actors. You can enable actor restarts by setting max_restarts to a non-zero value." 
@ray.remote(max_restarts=3, max_task_retries=3)
class ResilientActor:
    def __init__(self):
        # Actor init; retried up to 3 times on failure
        pass
    
    def work(self):
        # Method retried up to 3 times on failure
        pass

Caveats:

  • Actor state is lost: When an actor restarts, __init__ runs again. Any in-memory state from before the crash is lost. For stateful actors (e.g., holding a cache), persist state to external storage (Redis, database) and reload in __init__.
  • Pending methods are resubmitted: If the actor had 10 method calls queued when it died, all 10 are resubmitted to the restarted actor. This can cause duplicate work if methods have side effects (e.g., writing to a database). Make methods idempotent.
  • Actors not restarted during autoscaler scale-down: If autoscaler removes a worker Pod with a running actor, the actor dies and is NOT restarted (even with max_restarts). Use minReplicas or actor affinity (pinning to specific nodes) to avoid this.

Applying This to Eval Sandboxes and RL Rollouts

For eval sandboxes (e.g., running 10,000 SWE-bench instances):

  • Use max_retries=3 on sandbox exec tasks to tolerate transient worker failures
  • Make exec tasks idempotent (safe to rerun): check if result already exists in storage before executing
  • Set minReplicas: 1 for worker groups to avoid cold-start latency on scale-from-zero
  • Monitor object store usage; if eval results are large (e.g., full stdout logs), stream to S3 instead of returning via ray.get

For RL rollouts (e.g., PPO training with 1,000 actors collecting experience):

  • Use max_restarts=3 on rollout actors to tolerate node failures
  • Persist rollout actor state (e.g., episode count, latest model weights) to external storage (Redis, S3) and reload in __init__
  • Use placement groups (Lesson 11) to gang-schedule multi-GPU training workers and ensure they stay on the same node(s)
  • Size head node generously (8+ CPUs) for large clusters (1,000+ actors); GCS overhead is proportional to actor count

Step 3: Deploy a RayCluster with Autoscaling

Create raycluster-autoscale.yaml: 

apiVersion: ray.io/v1
kind: RayCluster
metadata:
  name: raycluster-autoscale
spec:
  rayVersion: '2.40.0'
  enableInTreeAutoscaling: true  # Enable autoscaler sidecar
  headGroupSpec:
    rayStartParams:
      dashboard-host: '0.0.0.0'
      num-cpus: '0'  # Head node does not run tasks (only GCS, dashboard, autoscaler)
    template:
      spec:
        containers:
        - name: ray-head
          image: rayproject/ray:2.40.0
          resources:
            limits:
              cpu: "2"
              memory: "4Gi"
            requests:
              cpu: "2"
              memory: "4Gi"
          ports:
          - containerPort: 6379
            name: gcs-server
          - containerPort: 8265
            name: dashboard
          - containerPort: 10001
            name: client
  workerGroupSpecs:
  - replicas: 1
    minReplicas: 0        # Scale to zero when idle
    maxReplicas: 5        # Scale up to 5 workers max
    groupName: worker-group
    rayStartParams:
      num-cpus: "2"
    template:
      spec:
        containers:
        - name: ray-worker
          image: rayproject/ray:2.40.0
          resources:
            limits:
              cpu: "2"
              memory: "2Gi"
            requests:
              cpu: "2"
              memory: "2Gi"
# Apply RayCluster
kubectl apply -f raycluster-autoscale.yaml

# Wait for head Pod to be ready
kubectl wait --for=condition=ready pod -l ray.io/node-type=head --timeout=300s

# Check Pods
kubectl get pods -l ray.io/cluster=raycluster-autoscale

Expected output: 1 head Pod (Running), 1 worker Pod (Running, initial replicas: 1).

Step 4: Submit Workload and Observe Scale-Up

Create autoscale_demo.py: 

#!/usr/bin/env python3
"""
Autoscaling demo: Submit tasks that require more resources than available,
observe autoscaler scaling up worker Pods.
"""
import ray
import time

# Connect to Ray cluster (via port-forward to head Pod)
ray.init(address="auto")

print(f"Connected to Ray cluster: {ray.cluster_resources()}")

@ray.remote(num_cpus=1)
def cpu_task(task_id):
    """Simulate CPU-bound work."""
    time.sleep(10)
    return f"Task {task_id} completed"

# Submit 20 tasks, each needs 1 CPU
# Cluster starts with 2 CPUs (1 worker × 2 CPUs), so 18 tasks will be pending
# Autoscaler should scale up to accommodate
print("\nSubmitting 20 tasks (each needs 1 CPU)...")
futures = [cpu_task.remote(i) for i in range(20)]

print("Tasks submitted. Waiting for completion...")
print("(Check `kubectl get pods -l ray.io/cluster=raycluster-autoscale -w` in another terminal)")

# Wait for all tasks to complete
results = ray.get(futures)
print(f"\n✓ All {len(results)} tasks completed")

# Cluster should now scale down after idle timeout (5 minutes by default)
print("\nCluster will scale down to minReplicas=0 after workers are idle for 5 minutes")
print("(You can watch with: kubectl get pods -l ray.io/cluster=raycluster-autoscale -w)")

ray.shutdown()
# Port-forward to head Pod (in a separate terminal)
kubectl port-forward service/raycluster-autoscale-head-svc 10001:10001 &

# Run autoscale demo
python3 autoscale_demo.py

Observe:

  • Initial cluster has 2 CPUs (1 worker × 2 CPUs)
  • 20 tasks submitted, each needs 1 CPU
  • 2 tasks run immediately, 18 are pending
  • Autoscaler detects pending tasks, calculates: need 18 more CPUs = 9 workers
  • But maxReplicas: 5, so autoscaler caps at 5 workers total (10 CPUs)
  • KubeRay operator creates 4 new worker Pods (total: 5 workers)
  • Watch with: kubectl get pods -l ray.io/cluster=raycluster-autoscale -w

Expected: You'll see new worker Pods created (STATUS: ContainerCreating → Running) over ~30 seconds.

Step 5: Observe Scale-Down (Idle Timeout)

After tasks complete, workers are idle. Default idle timeout is 5 minutes. The autoscaler will scale down to minReplicas: 0 after 5 minutes. 

# Watch Pods for 5-10 minutes
kubectl get pods -l ray.io/cluster=raycluster-autoscale -w

# After ~5 minutes, you should see worker Pods terminating (STATUS: Terminating → gone)
# Eventually only the head Pod remains

Note: To speed up testing, you can reduce idle timeout by setting idle_timeout_minutes: 1 in autoscaler config. However, KubeRay v1.2.2 does not expose this field in the RayCluster CRD. You'd need to modify the autoscaler sidecar's environment variables directly (advanced). For this exercise, just observe the default 5-minute timeout.

What You Learned

  • KubeRay operator manages RayCluster CRs, creates head/worker Pods, and reconciles autoscaler decisions
  • Autoscaler sidecar runs in head Pod, reads demand from GCS, writes desired replica counts to RayCluster status
  • Operator reconciles worker Pods to match desired replicas
  • Scale-up happens immediately (within Pod creation time, ~20-60s). Scale-down waits for idle timeout (default 5 minutes)
  • minReplicas: 0 allows scale-to-zero (saves cost), but adds cold-start latency for bursty workloads

Troubleshooting

  • Autoscaler not scaling: Check autoscaler sidecar logs: kubectl logs -l ray.io/node-type=head -c autoscaler
  • Pods stuck Pending: Check node resources: kubectl describe nodes. If kind nodes are out of CPU, increase node count in kind config.
  • Ray connection failed: Verify port-forward: kubectl port-forward service/raycluster-autoscale-head-svc 10001:10001 must be running.
