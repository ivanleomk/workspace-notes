Why Namespaces and cgroups Aren't Enough

In Lesson 01, you learned that namespaces and cgroups wrap a process in isolation and resource limits. But every containerized process still makes the same syscalls to the same host kernel as every other process.

Linux has over 300 syscalls. Many are essential (read, write, mmap), but some are dangerous for untrusted code:

  • ptrace — attach to and control another process
  • kexec_load — load a new kernel (requires privileges, but still scary)
  • perf_event_open — read performance counters across the system
  • bpf — load arbitrary BPF programs into the kernel
  • mount, umount — modify the filesystem hierarchy

Even with namespaces, a container that can call ptrace or perf_event_open might leak information about other containers or the host. This is where seccomp-bpf comes in: it lets you filter which syscalls a process can make.

seccomp-bpf: Syscall Filtering with BPF

seccomp (secure computing mode) is a Linux kernel feature that restricts which syscalls a process can make. From seccomp(2):

"seccomp allows a process to make a one-way transition into a 'secure' state where it cannot make any system calls except exit(), sigreturn(), read(), and write() to already-open file descriptors."

The original SECCOMP_MODE_STRICT (2005) was too restrictive: only 4 syscalls allowed. In 2012, seccomp-bpf (SECCOMP_MODE_FILTER) was added, allowing you to write a BPF (Berkeley Packet Filter) program that decides which syscalls to allow.

How It Works

When a process with a seccomp filter makes a syscall, the kernel runs the BPF program before executing the syscall. The BPF program inspects the syscall number and arguments, then returns one of six actions:

SECCOMP_RET_* Return Actions

From seccomp(2):

  • SECCOMP_RET_ALLOW — Execute the syscall normally.
  • SECCOMP_RET_ERRNO — Block the syscall and return a specified errno (e.g., EPERM, ENOSYS).
  • SECCOMP_RET_KILL_PROCESS — Kill the entire process (all threads).
  • SECCOMP_RET_KILL_THREAD — Kill only the calling thread.
  • SECCOMP_RET_TRAP — Send SIGSYS to the process. A signal handler can inspect the syscall and decide what to do. This is how gVisor intercepts syscalls.
  • SECCOMP_RET_TRACE — Notify a ptrace tracer (if attached). The tracer can allow, block, or modify the syscall. gVisor's older ptrace platform used this.
  • SECCOMP_RET_LOG — Allow the syscall but log it to the audit subsystem (useful for policy development).

The BPF Filter

The filter is a BPF program—originally designed for packet filtering, now repurposed for syscalls. From the kernel docs (seccomp_filter.html):

"A seccomp filter is expressed as a Berkeley Packet Filter (BPF) program. The BPF program is evaluated for each system call the task makes."

You typically don't write raw BPF bytecode by hand. Instead, you use a library like libseccomp (C) or seccomp-tools (Ruby) to generate it. For containers, runc applies the filter via prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, ...) before executing the container's entrypoint.

Docker's Default seccomp Profile

Docker (via runc) applies a default seccomp profile to every container unless you run with --security-opt seccomp=unconfined. The Docker seccomp docs explain that seccomp profiles filter system calls to prevent containers from exploiting vulnerabilities in the Linux kernel. Docker's default profile blocks a subset of Linux's 300+ syscalls—the dangerous ones that pose security risks in containerized environments.

Which Syscalls Are Blocked?

The canonical profile is in the Moby repo: profiles/seccomp/default.json. Key blocked syscalls include:

  • Kernel module loading: init_module, finit_module, delete_module — prevents loading kernel modules (requires CAP_SYS_MODULE, but defense in depth).
  • Debugging: ptrace — prevents attaching to other processes (important for multi-tenant isolation).
  • Kernel replacement: kexec_load, kexec_file_load — prevents loading a new kernel.
  • Time manipulation: clock_settime, settimeofday — prevents setting the system clock (which could break other containers).
  • BPF programs: bpf — prevents loading arbitrary BPF programs (requires CAP_SYS_ADMIN for most operations).
  • Performance counters: perf_event_open — prevents reading system-wide performance counters (potential side-channel).
  • Reboot: reboot — prevents rebooting the host.
  • Personality: personality with certain flags — blocks execution domain changes that could bypass security.

Example: Blocked Syscall Behavior

If a containerized process tries to call ptrace, the seccomp filter returns SECCOMP_RET_ERRNO with errno=EPERM or errno=ENOSYS. The process sees the syscall fail immediately, without ever reaching the kernel's ptrace handler. 

import ctypes
import errno

libc = ctypes.CDLL(None, use_errno=True)

# Try to ptrace ourselves (should fail with EPERM in Docker default profile)
result = libc.ptrace(0, 0, 0, 0)  # PTRACE_TRACEME
if result == -1:
    err = ctypes.get_errno()
    print(f"ptrace failed: {errno.errorcode.get(err, err)}")
    # Output in Docker: ptrace failed: EPERM

Why Not Block More Syscalls?

The default profile is a balance: it blocks dangerous syscalls but allows enough for general-purpose workloads (databases, web servers, build tools). For tighter sandboxing, you can:

  • Use a custom seccomp profile with a whitelist of only the syscalls your workload needs (requires profiling).
  • Use gVisor, which blocks syscalls at a higher level (in the Sentry) and intercepts the rest.

gVisor's Syscall Interception: SECCOMP_RET_TRAP and systrap

gVisor is a userspace kernel written in Go. Instead of letting application syscalls go directly to the host kernel, gVisor interposes a component called the Sentry that implements a large subset of the Linux syscall API. From the gVisor platforms docs:

"The Sentry implements the Linux system call interface. When the application makes a system call, the call is intercepted and handled by the Sentry, not the host kernel. The Sentry then makes a limited set of host system calls to provide the requested functionality."

Platform: systrap (Default Since Mid-2023)

gVisor's systrap platform (introduced as the default in gVisor v20230717.0) uses SECCOMP_RET_TRAP to intercept syscalls. From the platforms docs:

"systrap uses seccomp to trap into the Sentry for system calls. When the application makes a system call, the seccomp filter returns SECCOMP_RET_TRAP, which delivers a SIGSYS signal to a Sentry thread. The Sentry handles the signal, emulates the system call, and resumes the application."

This is faster than the older ptrace platform (which used SECCOMP_RET_TRACE and ptrace(PTRACE_SYSEMU)) because it avoids context switches to a separate tracer process.

Why Use gVisor for Evals?

From the gVisor homepage:

"gVisor provides a substantial layer of isolation between running applications and the host operating system. It limits the host kernel surface accessible to applications."

In production eval systems:

  • Modal uses gVisor as the default runtime for sandboxes. From Modal sandbox docs: "GPU Sandboxes are only supported with runtime=gvisor."
  • UK AISI's Inspect k8s provider uses gVisor as the RuntimeClass. From inspect_k8s_sandbox README: "gVisor provides an additional layer of isolation."
  • Kubernetes can use runsc (gVisor's OCI runtime) via RuntimeClass. From RuntimeClass docs: select per-pod with runtimeClassName: gvisor.

⚠️ Performance Trade-Off

gVisor's syscall interception adds overhead. From the gVisor performance guide, gVisor imposes runtime costs that come in two forms: additional overhead for application system calls, and a fixed memory overhead. The overhead depends on the workload and is highest for syscall-heavy and file I/O-heavy applications, while CPU-bound workloads with few syscalls see minimal impact.

But this is the tax for stronger isolation. The Sentry is a smaller attack surface than the full Linux kernel. A vulnerability in the Sentry is less catastrophic than a kernel vuln, and the Sentry's attack surface is auditable.

overlayfs: Union Filesystems for Container Layers

overlayfs is a union filesystem: it combines multiple directories (called layers) into one unified view. From the kernel docs (overlayfs.html):

"An overlay filesystem combines an 'upper' filesystem (read-write) with one or more 'lower' filesystems (read-only). When a file is accessed, overlayfs first checks the upper; if not found, it searches the lowers."

This is how Docker shares one base image across thousands of containers. Each container gets its own writable layer on top of shared read-only layers.

The Four Directories

An overlayfs mount requires four directories:

1. Lower Directories (Read-Only)

These are the base layers—typically Docker image layers. Multiple lowers can be stacked. When a file exists in multiple lowers, the uppermost (most recent) wins.

Example: lowerdir=/var/lib/docker/overlay2/base1:/var/lib/docker/overlay2/base2

2. Upper Directory (Read-Write)

This is the container's writable layer. All writes go here. When you modify a file from a lower layer, overlayfs copies it to the upper (copy-on-write). When you delete a file, overlayfs creates a whiteout marker in the upper.

Example: upperdir=/var/lib/docker/overlay2/container_abc/diff

3. Work Directory

An internal directory used by overlayfs for atomic copy-up operations. Must be on the same filesystem as the upper. Not directly visible to applications.

Example: workdir=/var/lib/docker/overlay2/container_abc/work

4. Merged Directory (The Unified View)

This is the mount point—the unified filesystem that the container sees. Reads check upper first, then lowers. Writes go to upper.

Example: /var/lib/docker/overlay2/container_abc/merged (this becomes the container's / after pivot_root).

Copy-on-Write and Whiteouts

From the kernel docs:

"When a file in a lower layer is modified, the entire file is copied to the upper layer (copy-up) before the modification is applied. When a file is deleted, a whiteout (a character device with device number 0/0) is created in the upper layer."

Why this matters for evals:

  • Image sharing: Thousands of containers can share one base image (e.g., python:3.11) without copying it. Each container's writes stay in its own upper.
  • Storage efficiency: From SWE-bench Docker setup, with cache_level=instance, cached images require ~2,000GB. With cache_level=env (caching base and environment layers only), storage drops to ~100GB. Without layering, each instance would need its own full copy of all dependencies, multiplying storage requirements substantially.
  • Startup speed: No need to copy the base image—mount is instant. The container starts as soon as overlayfs is mounted.

How Docker Uses overlayfs

When you run docker run ubuntu, Docker:

  1. Pulls (or reuses) the ubuntu image layers (each layer is a tar archive).
  2. Extracts each layer into /var/lib/docker/overlay2/<id>/diff.
  3. Creates a new upper+work pair for the container.
  4. Mounts overlayfs: mount -t overlay overlay -o lowerdir=layer1:layer2:layer3,upperdir=container_upper,workdir=container_work merged.
  5. The container's root filesystem is merged. All reads are from layers or upper; all writes go to upper.

Inspect a running container's overlayfs mount: 

# Find the container ID
docker ps

# Inspect its mount
docker inspect <container_id> | grep -A 20 '"GraphDriver"'

# Or check /proc/mounts on the host
grep overlay /proc/mounts

How Real Systems Combine seccomp and overlayfs

Docker (runc)

seccomp: Applies default.json profile (blocks ~44 syscalls) via prctl(PR_SET_SECCOMP) before container entrypoint. From runc's seccomp_linux.go: "Load the seccomp filter into the kernel."

overlayfs: Default storage driver on modern Linux. From Docker storage driver docs: "OverlayFS is the default and recommended driver."

gVisor (runsc)

seccomp: The Sentry itself runs with a tight seccomp filter that only allows the host syscalls it needs (e.g., mmap, futex, epoll_wait). The application's syscalls are intercepted via SECCOMP_RET_TRAP. From gVisor's filter/config.go: "The Sentry's seccomp policy."

Filesystem: gVisor emulates filesystems in the Sentry. For the root filesystem, it can use gofer (a 9P proxy) or direct overlayfs access. From gVisor filesystem docs: "The default is gofer for maximum compatibility."

Kubernetes (with runc or gVisor)

seccomp: You can set a per-pod seccomp profile via securityContext.seccompProfile in the pod spec. From Kubernetes seccomp tutorial: "Restrict a Container's Syscalls with seccomp."

overlayfs: Depends on the container runtime (containerd or CRI-O) and the configured storage driver. On most modern setups, it's overlayfs.

SWE-bench

seccomp: Uses Docker defaults (not explicitly overridden in the public code).

overlayfs: Essential for the three-layer image model (base → environment → instance). From SWE-bench Docker setup, the harness builds images in three layers to reduce duplication. With cache_level=instance, cached images require ~2,000GB; with cache_level=env, only ~100GB. Without overlayfs layering, storage would multiply as each instance needed full copies of all dependencies.

Modal Sandboxes

seccomp: Managed by the gVisor runtime (default). From Modal sandbox docs: "gVisor runtime for stronger isolation."

Filesystem: Modal uses gVisor's gofer for the root filesystem, plus support for filesystem and memory snapshots. From the same docs: "Filesystem snapshots save setup time."

Exercise 1: Minimal seccomp Filter

This Python script installs a seccomp filter that blocks getpid (just for demonstration). It uses the libseccomp library via ctypes (you can also use the seccomp package from PyPI for a higher-level interface, but we'll use ctypes to show the raw syscall interface). 

#!/usr/bin/env python3
"""
Minimal seccomp filter demo: block getpid() syscall.

Requirements:
- Python 3.7+
- No special privileges needed (seccomp filters are per-process)

Usage:
    python3 seccomp_demo.py

What it does:
1. Calls getpid() successfully
2. Installs a seccomp filter that blocks getpid
3. Tries to call getpid() again (will fail with EPERM)
"""

import os
import sys
import ctypes
import ctypes.util

# Linux syscall numbers (x86-64)
__NR_seccomp = 317
__NR_getpid = 39

# seccomp constants
SECCOMP_SET_MODE_FILTER = 1
SECCOMP_FILTER_FLAG_TSYNC = 1

# SECCOMP_RET_* values
SECCOMP_RET_KILL = 0x00000000
SECCOMP_RET_ERRNO = 0x00050000
SECCOMP_RET_ALLOW = 0x7fff0000

# BPF instruction structure
class sock_filter(ctypes.Structure):
    _fields_ = [
        ("code", ctypes.c_uint16),
        ("jt", ctypes.c_uint8),
        ("jf", ctypes.c_uint8),
        ("k", ctypes.c_uint32),
    ]

class sock_fprog(ctypes.Structure):
    _fields_ = [
        ("len", ctypes.c_uint16),
        ("filter", ctypes.POINTER(sock_filter)),
    ]

# BPF instruction macros
def BPF_STMT(code, k):
    return sock_filter(code, 0, 0, k)

def BPF_JUMP(code, k, jt, jf):
    return sock_filter(code, jt, jf, k)

# BPF opcodes
BPF_LD = 0x00
BPF_W = 0x00
BPF_ABS = 0x20
BPF_JMP = 0x05
BPF_JEQ = 0x10
BPF_RET = 0x06
BPF_K = 0x00

# Load libc
libc = ctypes.CDLL(ctypes.util.find_library('c'), use_errno=True)

def install_seccomp_filter():
    """
    Install a seccomp filter that:
    - Blocks getpid() with EPERM
    - Allows all other syscalls
    """
    # BPF program:
    # 1. Load syscall number (at offset 0 in seccomp_data)
    # 2. If syscall == getpid, return ERRNO(EPERM)
    # 3. Else, return ALLOW
    
    # seccomp_data offsets (from kernel headers)
    offsetof_nr = 0  # syscall number is at offset 0
    
    filter_prog = (sock_filter * 5)(
        # Load syscall number
        BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof_nr),
        
        # If syscall == __NR_getpid, jump to return ERRNO
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_getpid, 0, 1),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | 1),  # errno=EPERM (1)
        
        # Default: allow
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),  # padding
    )
    
    prog = sock_fprog(len(filter_prog), filter_prog)
    
    # Call seccomp(SECCOMP_SET_MODE_FILTER, 0, &prog)
    ret = libc.syscall(__NR_seccomp, SECCOMP_SET_MODE_FILTER, 0, ctypes.byref(prog))
    if ret != 0:
        errno = ctypes.get_errno()
        raise OSError(errno, os.strerror(errno), "seccomp")
    
    print("[seccomp] Filter installed: getpid() is now blocked")

def main():
    print("=== seccomp Filter Demo ===\n")
    
    # Step 1: Call getpid() normally
    pid = os.getpid()
    print(f"[before filter] os.getpid() = {pid}")
    
    # Step 2: Install the filter
    try:
        install_seccomp_filter()
    except OSError as e:
        print(f"❌ Failed to install seccomp filter: {e}")
        print("   (This should not happen—seccomp filters don't need special privileges)")
        sys.exit(1)
    
    # Step 3: Try to call getpid() again (should fail)
    print("\n[after filter] Attempting os.getpid()...")
    try:
        # os.getpid() is cached in Python, so we call the raw syscall
        pid = libc.syscall(__NR_getpid)
        if pid == -1:
            errno = ctypes.get_errno()
            print(f"✓ getpid() blocked! errno={errno} ({os.strerror(errno)})")
        else:
            print(f"✗ Unexpected: getpid() returned {pid} (should have been blocked)")
    except Exception as e:
        print(f"✓ getpid() blocked with exception: {e}")
    
    print("\n✅ Demo complete!")
    print("   Note: The seccomp filter is now active for this process and cannot be removed.")
    print("   All child processes inherit it. To reset, exit this process.")

if __name__ == "__main__":
    main()

Exercise 2: Mount overlayfs

This script demonstrates a minimal overlayfs mount. It creates lower, upper, work, and merged directories, mounts overlayfs, and shows copy-on-write behavior. 

#!/usr/bin/env python3
"""
overlayfs mount demo: stack read-only lower layers under one writable upper.

Requirements:
- Linux kernel with overlayfs support (merged into mainline in 3.18, 2014)
- Python 3.7+
- Root or CAP_SYS_ADMIN (e.g., run with sudo)

Usage:
    sudo python3 overlayfs_demo.py

What it does:
1. Creates lower1/ (read-only layer), lower2/ (another read-only layer), upper/ (writable), work/, and merged/
2. Mounts overlayfs: merged/ shows the union of lower1, lower2, and upper
3. Demonstrates copy-on-write: modifying a file from lower copies it to upper
4. Demonstrates whiteouts: deleting a file from lower creates a whiteout in upper
"""

import os
import sys
import subprocess
import tempfile
import shutil

def run_command(cmd, check=True):
    """Run a shell command and return output."""
    result = subprocess.run(cmd, shell=True, capture_output=True, text=True)
    if check and result.returncode != 0:
        print(f"❌ Command failed: {cmd}")
        print(f"   stdout: {result.stdout}")
        print(f"   stderr: {result.stderr}")
        sys.exit(1)
    return result

def main():
    if os.geteuid() != 0:
        print("⚠️  This script needs root to mount overlayfs. Run with sudo.")
        sys.exit(1)
    
    print("=== overlayfs Mount Demo ===\n")
    
    # Create a temporary directory for our demo
    demo_dir = tempfile.mkdtemp(prefix="overlayfs_demo_")
    print(f"[setup] Working directory: {demo_dir}\n")
    
    try:
        # Create the four required directories
        lower1_dir = os.path.join(demo_dir, "lower1")
        lower2_dir = os.path.join(demo_dir, "lower2")
        upper_dir = os.path.join(demo_dir, "upper")
        work_dir = os.path.join(demo_dir, "work")
        merged_dir = os.path.join(demo_dir, "merged")
        
        for d in [lower1_dir, lower2_dir, upper_dir, work_dir, merged_dir]:
            os.makedirs(d, exist_ok=True)
        
        # Populate lower layers
        with open(os.path.join(lower2_dir, "base.txt"), "w") as f:
            f.write("This file is in lower2 (the bottom layer).\n")
        
        with open(os.path.join(lower1_dir, "app.txt"), "w") as f:
            f.write("This file is in lower1 (middle layer).\n")
        
        with open(os.path.join(lower1_dir, "shared.txt"), "w") as f:
            f.write("This file exists in lower1.\n")
        
        with open(os.path.join(lower2_dir, "shared.txt"), "w") as f:
            f.write("This file also exists in lower2, but lower1 takes precedence.\n")
        
        print("[setup] Created lower layers:")
        print(f"  lower2/base.txt")
        print(f"  lower1/app.txt")
        print(f"  lower1/shared.txt (shadows lower2/shared.txt)\n")
        
        # Mount overlayfs
        # Syntax: mount -t overlay overlay -o lowerdir=lower1:lower2,upperdir=upper,workdir=work merged
        mount_opts = f"lowerdir={lower1_dir}:{lower2_dir},upperdir={upper_dir},workdir={work_dir}"
        mount_cmd = f"mount -t overlay overlay -o {mount_opts} {merged_dir}"
        
        print(f"[mount] Mounting overlayfs...")
        print(f"  Command: {mount_cmd}\n")
        run_command(mount_cmd)
        print(f"✓ Mounted overlayfs at {merged_dir}\n")
        
        # Show merged view
        print("[merged view] Contents of merged/:")
        result = run_command(f"ls -la {merged_dir}", check=False)
        print(result.stdout)
        
        print("[merged view] Contents of merged/base.txt:")
        with open(os.path.join(merged_dir, "base.txt"), "r") as f:
            print(f"  {f.read().strip()}")
        
        print("\n[merged view] Contents of merged/shared.txt (from lower1, not lower2):")
        with open(os.path.join(merged_dir, "shared.txt"), "r") as f:
            print(f"  {f.read().strip()}")
        
        # Demonstrate copy-on-write
        print("\n[copy-on-write] Modifying merged/app.txt (from lower1)...")
        with open(os.path.join(merged_dir, "app.txt"), "a") as f:
            f.write("This line was added via the merged view.\n")
        
        print("  ✓ File modified. Checking upper/:")
        result = run_command(f"ls -la {upper_dir}", check=False)
        print(result.stdout)
        
        print("  Contents of upper/app.txt (copy-up happened):")
        with open(os.path.join(upper_dir, "app.txt"), "r") as f:
            print(f"    {f.read()}")
        
        # Demonstrate whiteout (deletion)
        print("[whiteout] Deleting merged/base.txt (from lower2)...")
        os.remove(os.path.join(merged_dir, "base.txt"))
        
        print("  ✓ File deleted. Checking upper/:")
        result = run_command(f"ls -la {upper_dir}", check=False)
        print(result.stdout)
        
        print("  Note: A whiteout marker (char device 0/0) was created in upper/")
        
        # Unmount
        print(f"\n[cleanup] Unmounting {merged_dir}...")
        run_command(f"umount {merged_dir}")
        print("  ✓ Unmounted")
        
    finally:
        # Clean up
        print(f"\n[cleanup] Removing {demo_dir}...")
        shutil.rmtree(demo_dir, ignore_errors=True)
        print("  ✓ Cleaned up")
    
    print("\n✅ Demo complete!")
    print("\nKey takeaways:")
    print("  - overlayfs stacks multiple lower layers under one writable upper")
    print("  - Reads check upper first, then lowers in order")
    print("  - Writes trigger copy-on-write: files are copied from lower to upper")
    print("  - Deletions create whiteout markers in upper (char device 0/0)")
    print("  - This is how Docker shares one image across thousands of containers")

if __name__ == "__main__":
    main()
