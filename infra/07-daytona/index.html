From E2B's Single Path to Daytona's Multi-Tier Approach

In Lesson 06, you saw E2B's architecture: every sandbox is a Firecracker microVM that resumes from a snapshot. One isolation model, one runtime, one code path.

Daytona ( daytona.io) takes a different approach: it offers three isolation classes within one platform. You choose the boundary that fits your workload:

  • Container sandboxes: Shared kernel, fast startup (<90ms vendor claim from cached OCI image), no pause/resume/fork. Built on Docker with Linux namespaces and cgroups.
  • VM sandboxes: Dedicated kernel (Firecracker microVM when nested virtualization is available, or sysbox otherwise), hardware virtualization, pause/resume/fork/memory snapshots. Resume time: "in under a second" (vendor claim from VMs announcement).
  • GPU sandboxes: Exclusive GPU allocation (NVIDIA/AMD), container-based (shared kernel), no pause/resume/fork, one GPU device per sandbox.

What You'll Learn

  • Why Daytona separates control plane (API, job queue) from compute plane (runners, sandbox daemon)
  • When to choose containers (speed, Docker compatibility) vs VMs (isolation, pause/resume/fork) vs GPU (exclusive hardware)
  • How Daytona's architecture differs from E2B: job-based runner polling (no synchronous gRPC from API), Rust daemon (not Go), container default (not VM-only)
  • How VM sandboxes implement pause/resume/fork on Firecracker, and why fork creates deterministic branches
  • How GPU sandboxes schedule onto GPU runners with exclusive allocation
  • Hands-on: create container, VM, and GPU sandboxes via SDK, measure startup latency, test pause/resume/fork

Daytona Architecture: Control Plane vs Compute Plane

From Daytona Architecture docs:

"The control plane receives all client requests, authenticates them, records the desired state, and publishes jobs that runners pick up. Runners report progress back as events, so no sandbox operation requires a synchronous round trip between the API and a runner."

Why Job-Based Architecture?

Async by default: The API doesn't make synchronous gRPC calls to runners (contrast E2B, where the API calls orchestrator gRPC endpoints directly). Instead, the API writes a job to a queue (backed by Postgres + Redis), the runner polls the queue, executes the job, and reports events back. This decouples API availability from runner availability: if the API restarts, runners keep running and reconnect to the queue.

Runner pull, not push: Runners poll the control plane for jobs. No inbound connections from the API to runners. This simplifies networking (runners can sit behind NAT or firewalls) and reduces blast radius: a compromised API can write malicious jobs, but it can't directly exec commands on runner nodes.

Container Sandboxes: Shared Kernel, Fast Startup

Default runtime. Container sandboxes use Docker with Linux namespaces and cgroups to provide isolation without hardware virtualization. Each sandbox has:

  • Dedicated Linux namespaces (PID, mount, network, UTS, IPC, user, cgroup)
  • Hard resource limits (vCPU, RAM, disk) enforced via cgroups v2
  • Root inside the sandbox, unprivileged on the host (user namespace mapping)
  • No shared network with other sandboxes (each gets its own network namespace)

When to use: You need fast startup (<90ms vendor claim), Docker compatibility (mount Docker images, run apt-get, pip install), and high concurrency. You don't need pause/resume/fork or hardware-level isolation.

Trade-offs: Kernel is shared. If a guest kernel vulnerability exists, container sandboxes could potentially exploit it to escape to the host or observe other sandboxes (mitigated by seccomp-bpf filters, user namespaces, and AppArmor/SELinux). No pause/resume/fork: you can't checkpoint agent state and resume later, or branch into N copies.

VM Sandboxes: Dedicated Kernel, Pause/Resume/Fork

Hardware-virtualized microVMs. From Daytona VMs announcement:

"Every Daytona sandbox can now run as a true microVM with full OS-level isolation. Pause freezes the entire machine state and resumes it in under a second. Fork clones a running VM into any number of identical copies from a single point in time."

Each VM sandbox boots its own Linux kernel (or Windows kernel for Windows VMs) inside a microVM. According to Daytona's 2024 ELC presentation, "In scenarios with nested virtualization, Firecracker is used for enhanced isolation. In environments like Amazon, where nested virtualization isn't available, it falls back to sysbox." Isolation is enforced by hardware virtualization (KVM) or enhanced container isolation, not basic Linux namespaces. Guest kernel vulnerabilities cannot escape to the host or observe other VMs.

When to use: You need hardware-level isolation (untrusted or AI-generated code), pause/resume (long-running agents that sit idle between steps), fork (branch-and-select workflows, GRPO-style RL, tree search), or nested virtualization (run Docker/KVM inside the sandbox).

Trade-offs: Customer case studies report sandbox creation times of "<100ms" to "under 200ms" depending on configuration. Cannot create VM sandboxes from arbitrary Dockerfiles (must create from existing VM snapshots). Higher memory overhead (guest kernel + user space).

GPU Sandboxes: Exclusive GPU Allocation

Container-based with exclusive GPU devices. From Daytona Isolation docs:

"Isolated container with exclusive GPU allocation: assigned GPU devices belong to one sandbox at a time and are never shared."

GPU sandboxes are containers (shared kernel) that run on GPU runners. Each sandbox is allocated one or more GPU devices (NVIDIA or AMD), and those devices are never shared with other sandboxes. The runner schedules sandboxes with --gpus (Docker runtime) or equivalent device passthrough.

When to use: Model inference, fine-tuning, GPU-accelerated compute (CUDA, ROCm). You need dedicated GPU hardware and can tolerate container-level isolation (no pause/resume/fork).

Trade-offs: No pause/resume/fork (GPU state cannot be checkpointed; Firecracker + GPU is unsupported in most setups). Must schedule onto GPU runners (limited availability, higher cost). Container-based (shared kernel), not VM isolation.

VM Sandboxes: Pause, Resume, and Fork on Firecracker

How Pause Works

When you call sandbox.pause() on a VM sandbox:

  1. Runner receives pause job: API writes pause job to queue, runner polls and picks it up.
  2. Firecracker CreateSnapshot: Runner calls Firecracker's CreateSnapshot API. Firecracker writes:
    • Memory file: Full guest RAM (mmap-backed file)
    • State file: Device state JSON (vCPU registers, virtio device state, timers, interrupt state)
    • Rootfs diff (optional): Modified disk blocks (if using diff snapshots)
  3. Upload to S3: Runner uploads memory file and state file to object storage (S3/GCS). Optionally uploads only the diff (changed pages) if configured.
  4. Stop Firecracker: Kill the Firecracker process. The sandbox is now paused (no CPU/memory cost on the runner).
  5. Report event: Runner reports sandbox=paused to API.

Latency: Daytona does not publish official pause latency numbers. Firecracker snapshot creation is typically <1 second for small VMs (256MB–1GB RAM), but upload to S3 depends on object storage latency and snapshot size.

How Resume Works

When you call sandbox.connect() (Python SDK) or sandbox.resume() on a paused VM sandbox:

  1. Runner receives resume job: API writes resume job to queue, runner polls.
  2. Download snapshot: Runner downloads memory file and state file from S3. May use userfaultfd lazy memory (load pages on-demand) or full download, depending on runner config.
  3. Firecracker LoadSnapshot: Runner calls Firecracker's LoadSnapshot API with the memory file and state file paths. Firecracker mmaps the memory file, restores device state, and calls KVM_RUN. The guest resumes execution exactly where it was paused.
  4. Sandbox daemon reconnects: The sandbox daemon (Rust init) was frozen when the snapshot was taken. It resumes and re-exposes the Toolbox API on port 49983.
  5. Report event: Runner reports sandbox=running to API.

Latency: From the VMs announcement: "Resume restores the exact state in under a second" (vendor claim). This includes S3 download and Firecracker LoadSnapshot. Independent Firecracker benchmarks (Lesson 06, E2B) report ~28ms median restore for a 256MB working set on NVMe (LoadSnapshot API only, not including S3 download).

How Fork Works: Checkpoint Parent, Resume N Children

From the VMs announcement:

"Fork clones a running VM into N identical copies. Each fork starts from the same machine state, including memory and running processes, and then diverges independently."

The workflow:

  1. Parent sandbox running: Your agent code has executed to step k. The sandbox is in state S (memory, processes, open files).
  2. SDK calls fork: parent.fork(count=N) (Python) or equivalent.
  3. Checkpoint parent: API writes checkpoint job. Runner pauses the parent (same as pause: CreateSnapshot, upload to S3). The parent can optionally continue running after checkpoint (controlled by API request flag).
  4. Spread children: Sandbox manager (in API) schedules N new sandboxes with the checkpoint snapshot ID. For each child:
    • API picks a runner (may be the same runner or different runners, depending on capacity).
    • API writes create from checkpoint job for that runner.
    • Runner downloads the checkpoint snapshot from S3.
    • Runner calls LoadSnapshot to resume the child from the checkpoint.
    • Fix clone hazards: Runner (or sandbox daemon) must reseed RNG (/dev/urandom, /dev/random) to ensure each child generates different random values. The runner assigns each child a unique MAC address (configured in Firecracker network-interfaces JSON). Time synchronization: Firecracker does not provide VMGenID, so child VMs may see clock drift; applications should resync time if needed.
  5. Return child IDs: API returns a list of N sandbox IDs to the SDK.

Why Fork Creates Deterministic Branches

Because each child resumes from the exact same memory and device state as the parent, the initial state is bitwise-identical (modulo RNG reseed and MAC change). This makes fork ideal for:

  • GRPO-style RL: Run agent to decision point, fork N children, sample with different temperatures/seeds, compare outcomes for policy gradient update. The setup is identical, so differences in outcomes are purely from sampling variance.
  • Tree search: Fork at each branch point to explore N actions. Prune low-value branches, continue high-value ones. Each branch starts from the same known state.
  • A/B testing: Run expensive setup (install dependencies, load model), fork N children, run different code versions in each child. Setup cost is paid once.

GPU Sandboxes: Exclusive Allocation and Scheduling

How GPU Sandboxes Work

GPU sandboxes are container-based (shared kernel, Linux namespaces + cgroups), but with exclusive GPU device allocation. From the Isolation docs:

"Isolated container with exclusive GPU allocation: assigned GPU devices belong to one sandbox at a time and are never shared."

When you create a GPU sandbox:

  1. API receives create request: POST /api/sandbox with class=gpu, gpu_count=1 (or more).
  2. Sandbox manager schedules onto GPU runner: The manager queries available runners, filters for GPU runners with sufficient free GPU devices, and picks one (placement algorithm not documented; likely round-robin or load-based).
  3. Runner allocates GPU devices: The runner (Go agent) calls Docker create with --gpus device=0 (or equivalent for multiple GPUs). This passes the GPU device(s) into the container. The runner marks those GPU devices as in-use, so no other sandbox can claim them.
  4. Container starts: Docker starts the container with the allocated GPU device(s). The sandbox can now use CUDA, ROCm, or other GPU frameworks.
  5. Exclusive allocation: While the sandbox is running, those GPU devices are unavailable to other sandboxes. When the sandbox is deleted, the runner marks the devices as free.

Why Container, Not VM?

GPU sandboxes are containers, not Firecracker microVMs, for two reasons:

  • Firecracker + GPU = unsupported in most setups: Firecracker does not natively support GPU passthrough (PCIe device passthrough requires VFIO, which Firecracker doesn't expose). Cloud Hypervisor (an alternative VMM) supports GPU passthrough, but Daytona uses Firecracker for VMs.
  • Container GPU passthrough is mature: Docker + nvidia-container-runtime or --gpus is the standard way to run GPU workloads. It works reliably, has good tooling (NVIDIA Docker, nvidia-smi), and avoids the complexity of VFIO PCIe passthrough.

Trade-off: No pause/resume/fork for GPU sandboxes. GPU state (CUDA contexts, kernel memory, model weights) cannot be checkpointed by Firecracker. CUDA checkpoint/restore (CRIU + cuda-checkpoint, gVisor's experimental feature) is not supported in Daytona's container runtime.

GPU Runner Scheduling and Capacity

GPU runners report their GPU device list and availability to the API. The API's sandbox manager tracks which devices are in-use. When capacity is exhausted (all GPU devices allocated), new GPU sandbox requests queue or fail (behavior depends on API configuration). GPU runners typically have 1–8 GPUs per node (NVIDIA A100, H100, or AMD MI250X in production).

When to Choose E2B vs Daytona

  • Choose E2B if: You need VM-only isolation (every sandbox is a microVM), open-source backend (Apache-2.0), or you're self-hosting and want a simpler single-path architecture.
  • Choose Daytona if: You need multi-class isolation (container for speed, VM for fork, GPU for ML), or you want a managed service with GPU support (Daytona Cloud).

Step 2: Create and Measure Container Sandbox

Python example: 

#!/usr/bin/env python3
"""
Daytona container sandbox: fast startup, no pause/resume.
"""
import time
from daytona import Daytona, DaytonaConfig

def measure(label, fn):
    start = time.time()
    result = fn()
    elapsed = (time.time() - start) * 1000  # milliseconds
    print(f"{label}: {elapsed:.1f}ms")
    return result

# Configure
config = DaytonaConfig(api_key="YOUR_API_KEY")
daytona = Daytona(config)

print("=== Container Sandbox ===")
container = measure(
    "Create container",
    lambda: daytona.create()  # Default class is container
)
print(f"Container ID: {container.id}")

# Execute a command
result = container.process.exec("echo 'Hello from container'")
print(f"Output: {result.result}")

# Try to pause (should fail)
try:
    container.pause()
    print("Paused (unexpected!)")
except Exception as e:
    print(f"Pause failed (expected): {e}")

# Clean up
container.kill()
print("Container killed")

Step 3: Create and Test VM Sandbox with Pause/Resume/Fork

Python example: 

#!/usr/bin/env python3
"""
Daytona VM sandbox: pause/resume/fork.
"""
import time
from daytona import Daytona, DaytonaConfig, CreateSandboxFromSnapshotParams

def measure(label, fn):
    start = time.time()
    result = fn()
    elapsed = (time.time() - start) * 1000  # milliseconds
    print(f"{label}: {elapsed:.1f}ms")
    return result

config = DaytonaConfig(api_key="YOUR_API_KEY")
daytona = Daytona(config)

print("\n=== VM Sandbox ===")
vm = measure(
    "Create VM",
    lambda: daytona.create(CreateSandboxFromSnapshotParams(
        snapshot_id="daytona-vm-small"  # Pre-built Linux VM snapshot (1 vCPU, 1GB RAM)
    ))
)
print(f"VM ID: {vm.id}")

# Execute a command
result = vm.process.exec("echo 'Hello from VM'")
print(f"Output: {result.result}")

# Write state
vm.process.exec("echo 'state before pause' > /tmp/state.txt")

# Pause
measure("Pause VM", lambda: vm.pause())

# Resume
measure("Resume VM", lambda: vm.start())

# Verify state persisted
result = vm.process.exec("cat /tmp/state.txt")
print(f"State after resume: {result.result}")

# Fork (call fork() individually for each child)
print("\n=== Fork VM ===")
children = []
for i in range(3):
    child = measure(f"Fork child {i}", lambda i=i: vm.fork(name=f"child-{i}"))
    children.append(child)
print(f"Child IDs: {[c.id for c in children]}")

# Sample differently in each child
for i, child in enumerate(children):
    result = child.process.exec("cat /tmp/state.txt")
    print(f"Child {i}: state: {result.result}")
    
    # Sample with unique seed
    seed = 42 + i
    result = child.process.exec(f"python3 -c 'import random; random.seed({seed}); print(random.randint(0, 100))'")
    print(f"Child {i}: sampled value: {result.result}")

# Clean up
vm.kill()
for child in children:
    child.kill()
print("All VMs killed")

await vm.kill();
for (const child of children) {
  await child.kill();
}
console.log('All VMs killed');

Step 4 (Optional): Create GPU Sandbox

Python example: 

#!/usr/bin/env python3
"""
Daytona GPU sandbox: exclusive GPU allocation (requires Tier 3+).
"""
import time
from daytona import Daytona, DaytonaConfig, CreateSandboxFromSnapshotParams

def measure(label, fn):
    start = time.time()
    result = fn()
    elapsed = (time.time() - start) * 1000
    print(f"{label}: {elapsed:.1f}ms")
    return result

config = DaytonaConfig(api_key="YOUR_API_KEY")
daytona = Daytona(config)

print("\n=== GPU Sandbox ===")
try:
    gpu = measure(
        "Create GPU",
        lambda: daytona.create(CreateSandboxFromSnapshotParams(
            # GPU sandboxes require specifying a GPU-compatible snapshot
            # Check Daytona docs for available GPU snapshot IDs
        ))
    )
    print(f"GPU ID: {gpu.id}")

    # Check GPU availability
    result = gpu.process.exec("nvidia-smi")
    print(f"nvidia-smi output:\n{result.result}")

    # Try to pause (should fail)
    try:
        gpu.pause()
        print("Paused (unexpected!)")
    except Exception as e:
        print(f"Pause failed (expected for GPU): {e}")

    gpu.kill()
    print("GPU killed")
except Exception as e:
    print(f"GPU sandbox creation failed (expected if no GPU quota): {e}")
