Why This Matters for Eval Infrastructure

Every eval sandbox you've used—Docker containers for SWE-bench, Modal sandboxes for HumanEval, E2B microVMs for agent rollouts—is built on the primitives you'll learn in this lesson. Before you can choose between runc, gVisor, and Firecracker, you need to understand what they're isolating and how.

The core insight: A "container" is not a special kernel object. It's just a regular Linux process wrapped in namespaces and cgroups. Every sandbox—whether it shares the host kernel (Docker, gVisor) or runs in a VM (Firecracker, Kata)—uses these primitives somewhere in its isolation stack.

What You'll Learn

  • The 8 types of Linux namespaces and what each isolates (and doesn't)
  • cgroups v2 controllers: cpu, memory, io, pids, plus the freezer and PSI
  • Why shared-kernel isolation is not sufficient for untrusted code
  • How runc, Docker, Kubernetes, and eval harnesses use these primitives
  • Hands-on: build a minimal Python sandbox with unshare(2) and cgroup v2

What Containers Really Are

From the gVisor README:

"Containers are not a sandbox. While containers have revolutionized how we develop, package, and deploy applications, using them to run untrusted or potentially malicious code without additional isolation is not a good idea. While using a single, shared kernel allows for efficiency and performance gains, it also means that container escape is possible with a single vulnerability."

A container runtime like runc (or its lighter C implementation crun) combines several Linux primitives:

  • Namespaces: Give the process its own view of system resources
  • cgroups v2: Limit and account for resource usage (CPU, memory, I/O, PIDs)
  • seccomp-bpf: Filter which syscalls the process can make
  • overlayfs: Union mount for copy-on-write filesystem layers
  • capabilities, AppArmor/SELinux: Drop privileges and enforce MAC policies

But at the end of the day, every containerized process calls the same host kernel as every other process. This is fundamentally different from hardware virtualization, where each guest runs its own kernel.

⚠️ Security Implication for Evals

If you're running RL policies that explore for reward hacks, or evaluating potentially malicious code submissions, plain containers are not sufficient. A kernel vulnerability can lead to container escape. This is why production eval systems either:

  • Use gVisor (userspace kernel that intercepts syscalls)
  • Use microVMs (Firecracker, Kata) with hardware isolation
  • Run containers on single-tenant nodes with network isolation

Linux Namespaces: Hiding Things

Namespaces give a process its own view of a global resource. The process "thinks" it's alone, but it's actually sharing the kernel with everyone else.

From namespaces(7), there are 8 types:

1. Mount Namespace (CLONE_NEWNS)

What it isolates: The filesystem mount table. Each namespace has its own set of mount points.

What it does NOT isolate: The underlying filesystems themselves. If two containers mount the same host path, they see the same data.

Why it matters: Lets you give a container its own root filesystem (pivot_root) without affecting the host. Combined with overlayfs, this is how thousands of containers share one base image.

2. PID Namespace (CLONE_NEWPID)

What it isolates: Process IDs. The first process in a new PID namespace becomes PID 1 inside that namespace (but has a different PID on the host).

What it does NOT isolate: Process resources, scheduling, or signals from outside the namespace.

Why it matters: Inside the sandbox, ps only shows processes in that namespace. The sandbox can't see or signal host processes. But the host can see (and kill) all sandbox processes.

3. Network Namespace (CLONE_NEWNET)

What it isolates: Network stack—interfaces, routing tables, firewall rules (iptables/nftables), sockets.

What it does NOT isolate: Physical network hardware (that stays on the host).

Why it matters: Each sandbox gets its own lo interface and can't see the host's network. Connect it via veth pairs (virtual ethernet) to a bridge on the host. For Firecracker, each VM gets its own netns with a tap device.

Eval use case: Per-sandbox egress firewalls. E2B uses nftables rules in each netns to allow/deny domains. Inspect AI defaults to network_mode: none.

4. UTS Namespace (CLONE_NEWUTS)

What it isolates: Hostname and NIS domain name.

Why it matters: Lets each container have its own hostname without changing the host's. Minor, but prevents hostname collisions.

5. IPC Namespace (CLONE_NEWIPC)

What it isolates: System V IPC objects (message queues, semaphores, shared memory) and POSIX message queues.

Why it matters: Prevents containers from interfering with each other's IPC primitives. Less critical for modern sandboxes (most code uses sockets, not SysV IPC).

6. User Namespace (CLONE_NEWUSER)

What it isolates: User and group IDs. You can map UID 0 (root) inside the namespace to an unprivileged UID on the host.

What it does NOT isolate: Capabilities still apply. Even if you're "root" inside, you don't have host root powers unless you have the capabilities.

Why it matters: This is the most important namespace for unprivileged containers. With user namespaces, you can run Docker without sudo (rootless Docker). Inside the sandbox, the process thinks it's root, but on the host it's UID 100000 or similar.

See user_namespaces(7) for the full mapping rules.

7. Cgroup Namespace (CLONE_NEWCGROUP)

What it isolates: View of the cgroup hierarchy. Processes see a virtualized /proc/self/cgroup.

Why it matters: Prevents containers from seeing or modifying the host's cgroup tree. Less about resource isolation (that's cgroups themselves) and more about information hiding.

8. Time Namespace (CLONE_NEWTIME, Linux 5.6+)

What it isolates: CLOCK_MONOTONIC and CLOCK_BOOTTIME offsets.

Why it matters: Lets you restore a checkpoint with the clock adjusted. Useful for migration and checkpoint/restore (CRIU, gVisor checkpoint/restore).

Key Takeaway: Namespaces Only Hide

Namespaces do not prevent resource exhaustion. A process in a PID namespace can still fork-bomb the host. A process in a net namespace can still saturate the NIC. That's where cgroups come in.

cgroups v2: Resource Limits and Accounting

From cgroup-v2.html:

"Control Groups version 2 provide a unified hierarchy for resource control and accounting."

cgroups v2 is the current standard (cgroups v1 is deprecated but still widely deployed). Key difference: v2 has one unified hierarchy, while v1 had separate hierarchies per controller (cpu, memory, etc.).

Controllers

A controller is a subsystem that manages one type of resource. The main controllers:

1. CPU Controller

Files: cpu.max, cpu.weight, cpu.stat

What it does:

  • cpu.max: Hard limit. Format: $MAX $PERIOD in microseconds. Example: 50000 100000 = 50% of one CPU (50ms per 100ms).
  • cpu.weight: Proportional share (100–10000, default 100). If cgroup A has weight 100 and B has 200, B gets 2× the CPU when both are busy.

Eval use case: Prevent one sandbox from starving others. E2B sets cpu.max before the guest runs a single instruction (from ARCHITECTURE.md).

2. Memory Controller

Files: memory.max, memory.current, memory.high, memory.swap.max

What it does:

  • memory.max: Hard limit. If the cgroup tries to allocate more, allocations fail or the OOM killer runs.
  • memory.current: Current usage (read-only).
  • memory.high: Soft limit. The kernel throttles the cgroup when it crosses this threshold.

Why it matters: Without memory.max, a sandbox can OOM the host. Set it based on your eval workload. For SWE-bench, typical containers need 2–8 GB.

Gotcha: Inside the sandbox, free and nproc report host values, not cgroup limits. Daytona documents this in isolation docs. Your code must read /sys/fs/cgroup/memory.max to see the actual limit.

3. I/O Controller

Files: io.max, io.weight, io.stat

What it does: Limits IOPS and throughput (bytes/sec) per block device.

Eval use case: Prevent one sandbox's pip install or git clone from saturating the disk and slowing everyone else. Less critical for RAM-backed /tmp or NVMe.

4. PIDs Controller

Files: pids.max, pids.current

What it does: Limits the number of processes/threads in the cgroup.

Why it matters: Stops fork bombs. Set pids.max to something reasonable for your workload (e.g., 512 or 1024). Without this, a malicious :(){ :|:& };: can exhaust the PID space and DoS the host.

5. Freezer

File: cgroup.freeze

What it does: Write 1 to freeze all processes in the cgroup (like SIGSTOP, but atomic). Write 0 to thaw.

Eval use case: Pause a sandbox instantly. E2B and Daytona use this (plus VM-level pause for memory) to implement pause/resume.

6. Pressure Stall Information (PSI)

Files: cpu.pressure, memory.pressure, io.pressure

What it does: Reports how much time processes spent stalled waiting for CPU, memory, or I/O.

Why it matters: Observability. If memory.pressure is high, your sandbox is thrashing. If io.pressure is high, you're I/O-bound. Use this to right-size limits or detect runaway workloads.

Key Takeaway: cgroups Enforce, Namespaces Hide

Namespaces give the process an isolated view. cgroups give the kernel a way to limit and account for what that process can do. You need both for a secure sandbox.

But even with both, you're still calling the same host kernel. That's why systems like gVisor and Firecracker exist.

How Real Systems Use These Primitives

Now that you understand the building blocks, let's see how production systems combine them.

runc (Docker, containerd, CRI-O)

Source: github.com/opencontainers/runc

runc is the reference OCI (Open Container Initiative) runtime. It:

  • Creates all 8 namespaces (or a subset, based on config)
  • Sets up cgroup v2 limits (cpu.max, memory.max, pids.max, io.max)
  • Applies a seccomp profile (Docker's default disables "around 44 out of 300+" syscalls, per docs.docker.com/engine/security/seccomp)
  • Uses overlayfs to layer the image (read-only lowers) and a writable upper
  • Drops capabilities and sets AppArmor/SELinux policies
  • pivot_root to the container's rootfs
  • Execs the entrypoint

Where the syscalls go: Directly to the host kernel. This is the highest performance (no interception), but also the largest attack surface.

Kubernetes

Documentation: RuntimeClass

Kubernetes is a container orchestrator. It doesn't implement namespaces/cgroups itself; it delegates to a container runtime via CRI (Container Runtime Interface). Common runtimes:

  • containerd + runc: Standard shared-kernel containers
  • containerd + runsc (gVisor): Userspace kernel
  • Kata Containers: Each pod in a lightweight VM

You select the runtime per pod via runtimeClassName in the pod spec. For example, UK AISI's Inspect k8s provider uses gVisor.

cgroups: The kubelet creates a cgroup hierarchy. Each pod gets a cgroup; QoS classes (Guaranteed, Burstable, BestEffort) map to cgroup settings.

SWE-bench Harness

Source: github.com/SWE-bench/SWE-bench

SWE-bench runs each test instance in a Docker container (runc by default). From the Docker setup guide:

  • Images are layered: base → environment (~60 images) → instance
  • Recommended max_workers < min(0.75*cpu_count, 24)
  • The harness doesn't set explicit cgroup limits in the public code (relies on Docker defaults)

What's isolated: Each instance gets its own mount, PID, net (usually no network), UTS, IPC, user namespaces. cgroups are Docker's defaults (which depend on your daemon config).

What's NOT isolated: They all share the host kernel. If a test exploits a kernel vulnerability, it can escape. For SWE-bench this is acceptable (tests are from known repos), but for adversarial evals you'd want gVisor or VMs.

OpenHands Remote Runtime

Source: OpenHands API Sandbox docs

The OpenHands agent server runs inside a container. The architecture splits:

  • Agent loop (driver): Runs on the orchestrator
  • Tool executor (sandbox): Runs inside a container, connected via WebSocket

For large-scale evaluation (like SWE-bench), they run the container on a remote server (the APIRemoteWorkspace). The container itself is a plain Docker container (runc + namespaces + cgroups).

Inspect AI

Documentation: inspect.aisi.org.uk/sandboxing.html

Inspect's Docker provider generates a compose file with:

  • network_mode: none (no network by default)
  • Exec output capped at 10 MB (tail kept)
  • max_sandboxes defaults to 2× CPUs

The k8s provider (from UK AISI) uses gVisor as the RuntimeClass, plus Cilium network policies for egress control.

Build It Yourself: A Minimal Python Sandbox

Now let's build a simple sandbox that demonstrates namespaces and cgroups. This script:

  • Creates new user, mount, PID, and net namespaces
  • Sets up a cgroup v2 with memory and PID limits
  • Runs a child process that prints its PID and UID
  • Demonstrates isolation: the child has PID 1 inside, but a different PID on the host

⚠️ Privilege Requirements

User namespaces can be created unprivileged on most Linux distros (check /proc/sys/kernel/unprivileged_userns_clone). But creating a cgroup v2 typically requires:

  • A delegated cgroup (systemd's user.slice for unprivileged), or
  • Root (via sudo), or
  • Running inside Docker with --privileged or appropriate capabilities

The script below requires sudo or a delegated cgroup. If you don't have that, the namespace parts will work, but cgroup setup will fail.

Alternative: Run this inside a Docker container with docker run --privileged -it python:3.11.

The Code: exercise.py

#!/usr/bin/env python3
"""
Minimal sandbox demonstrating Linux namespaces and cgroups v2.

Requirements:
- Linux kernel 5.6+ (for all 8 namespaces including time; older kernels work without CLONE_NEWTIME)
- Python 3.7+
- sudo (or a delegated cgroup)

Usage:
    sudo python3 exercise.py

What it does:
1. Creates a new cgroup v2 with memory.max=100M and pids.max=10
2. Unshares into new user, mount, PID, and net namespaces
3. Runs a child that demonstrates isolation
"""

import os
import sys
import subprocess
import ctypes
import ctypes.util

# Linux namespace flags (from sched.h)
CLONE_NEWNS = 0x00020000    # mount
CLONE_NEWPID = 0x20000000   # PID
CLONE_NEWNET = 0x40000000   # network
CLONE_NEWUSER = 0x10000000  # user
CLONE_NEWUTS = 0x04000000   # UTS (hostname)
CLONE_NEWIPC = 0x08000000   # IPC
CLONE_NEWCGROUP = 0x02000000  # cgroup

# Load libc
libc = ctypes.CDLL(ctypes.util.find_library('c'), use_errno=True)

def unshare(flags):
    """
    Call unshare(2) to create new namespaces.
    Returns 0 on success, raises OSError on failure.
    """
    if libc.unshare(flags) != 0:
        errno = ctypes.get_errno()
        raise OSError(errno, os.strerror(errno), "unshare")
    return 0

def setup_cgroup(cgroup_name, memory_limit_bytes, pid_limit):
    """
    Create a cgroup v2 under /sys/fs/cgroup/{cgroup_name} with limits.
    Requires root or a delegated cgroup.
    """
    cgroup_path = f"/sys/fs/cgroup/{cgroup_name}"
    
    # Create the cgroup directory
    os.makedirs(cgroup_path, exist_ok=True)
    print(f"[cgroup] Created {cgroup_path}")
    
    # Set memory limit
    with open(f"{cgroup_path}/memory.max", "w") as f:
        f.write(str(memory_limit_bytes))
    print(f"[cgroup] Set memory.max = {memory_limit_bytes} bytes ({memory_limit_bytes // 1024 // 1024} MB)")
    
    # Set PID limit
    with open(f"{cgroup_path}/pids.max", "w") as f:
        f.write(str(pid_limit))
    print(f"[cgroup] Set pids.max = {pid_limit}")
    
    # Move current process into the cgroup
    with open(f"{cgroup_path}/cgroup.procs", "w") as f:
        f.write(str(os.getpid()))
    print(f"[cgroup] Moved PID {os.getpid()} into cgroup")
    
    return cgroup_path

def child_process():
    """
    This runs inside the new namespaces.
    """
    print("\n=== Inside the Sandbox ===")
    print(f"My PID (from os.getpid()): {os.getpid()}")
    print(f"My UID (from os.getuid()): {os.getuid()}")
    print(f"My GID (from os.getgid()): {os.getgid()}")
    
    # Read cgroup limits (these are visible from /proc or /sys/fs/cgroup)
    try:
        with open("/sys/fs/cgroup/memory.max", "r") as f:
            mem_max = f.read().strip()
        with open("/sys/fs/cgroup/pids.max", "r") as f:
            pids_max = f.read().strip()
        print(f"cgroup memory.max: {mem_max}")
        print(f"cgroup pids.max: {pids_max}")
    except FileNotFoundError:
        print("(cgroup files not visible in this namespace)")
    
    # Show network interfaces (should only see lo, and it's down)
    print("\nNetwork interfaces:")
    result = subprocess.run(["ip", "link", "show"], capture_output=True, text=True)
    print(result.stdout)
    
    print("=== Exiting sandbox ===\n")

def main():
    if os.geteuid() != 0:
        print("⚠️  This script needs root (or a delegated cgroup). Run with sudo.")
        print("   Namespace creation may work unprivileged, but cgroup setup will fail.")
        sys.exit(1)
    
    print("=== Sandbox Demo: Namespaces + cgroups v2 ===\n")
    
    # Step 1: Create a cgroup and set limits
    cgroup_name = f"sandbox_demo_{os.getpid()}"
    memory_limit = 100 * 1024 * 1024  # 100 MB
    pid_limit = 10
    
    try:
        cgroup_path = setup_cgroup(cgroup_name, memory_limit, pid_limit)
    except PermissionError as e:
        print(f"❌ Failed to create cgroup: {e}")
        print("   Make sure you're running with sudo or inside a delegated cgroup.")
        sys.exit(1)
    
    # Step 2: Unshare into new namespaces
    # We'll create: user, mount, PID, net
    # (UTS, IPC, cgroup are optional; time requires kernel 5.6+)
    flags = CLONE_NEWUSER | CLONE_NEWNS | CLONE_NEWPID | CLONE_NEWNET
    
    print("\n[namespace] Creating new user, mount, PID, and net namespaces...")
    
    # For user namespace, we need to set up UID/GID maps before we can do much else.
    # Since we're root, we'll map root inside to root outside (not recommended for prod!).
    # In production, you'd map to an unprivileged UID.
    
    try:
        unshare(flags)
    except OSError as e:
        print(f"❌ unshare() failed: {e}")
        print("   Your kernel may not support all these namespaces.")
        sys.exit(1)
    
    print("[namespace] Unshare successful. We are now in new namespaces.")
    
    # Write UID and GID maps for the user namespace
    # Map UID 0 inside to UID 0 outside (this requires CAP_SETUID, which we have as root)
    with open("/proc/self/uid_map", "w") as f:
        f.write("0 0 1\n")
    # Disable setgroups (required before writing gid_map)
    with open("/proc/self/setgroups", "w") as f:
        f.write("deny\n")
    with open("/proc/self/gid_map", "w") as f:
        f.write("0 0 1\n")
    
    print("[namespace] UID/GID maps configured.")
    
    # Step 3: Fork a child to demonstrate PID namespace
    # The child will be PID 1 inside the new PID namespace
    print("\n[fork] Forking a child to demonstrate PID namespace isolation...\n")
    
    pid = os.fork()
    if pid == 0:
        # Child process
        child_process()
        sys.exit(0)
    else:
        # Parent: wait for child
        _, status = os.waitpid(pid, 0)
        print(f"[parent] Child exited with status {status}")
    
    # Step 4: Clean up cgroup
    print(f"\n[cleanup] Removing cgroup {cgroup_path}...")
    try:
        os.rmdir(cgroup_path)
        print("[cleanup] Cgroup removed.")
    except OSError as e:
        print(f"[cleanup] Failed to remove cgroup: {e}")
        print("         (This is fine; it may have children or be in use.)")
    
    print("\n✅ Demo complete!")

if __name__ == "__main__":
    main()

What This Demonstrates

  • PID namespace: The child has PID 1 inside, but a different PID on the host.
  • User namespace: UID/GID mapping (we mapped 0→0, but you'd normally map to unprivileged).
  • Net namespace: Only lo interface, and it's down (no connectivity).
  • cgroup limits: memory.max=100MB, pids.max=10. Try spawning more than 10 processes or allocating >100MB to see the limits enforced.

Exercises to Try

  1. Modify the script to allocate 200MB inside the child (should hit the cgroup limit and OOM).
  2. Fork 11 processes inside the child (should hit pids.max=10 and fail).
  3. Add a mount namespace: pivot_root to a new rootfs (requires more setup).
  4. Measure how long unshare() and cgroup creation take (hint: nanoseconds for unshare, milliseconds for cgroup setup).
