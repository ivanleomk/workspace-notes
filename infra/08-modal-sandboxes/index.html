From Firecracker VMs to gVisor: Modal's Dual-Runtime Model

In Lessons 06 and 07, you saw two approaches to sandbox isolation: E2B's VM-only path (every sandbox is a Firecracker microVM) and Daytona's multi-tier choice (container, VM, or GPU). Modal (modal.com) takes yet another path: gVisor by default for userspace syscall interception, with VM runtime opt-in for Docker-in-sandbox and full Linux kernel features.

Where E2B gives you pause/resume/fork on VMs and Daytona separates container (fast) from VM (fork-capable), Modal gives you a single unified API — modal.Sandbox.create(runtime="gvisor") or runtime="vm" — backed by a serverless platform that elastically autoscales sandboxes from zero on demand.

What You'll Learn

  • Why Modal defaults to gVisor (userspace kernel, GPU-compatible, lesson 03 comparison) instead of Firecracker VMs
  • How Modal's Image definitions layer and cache (similar to Docker layers, but with OCI + function hashing)
  • How filesystem snapshots (snapshot_filesystem) share expensive setup across sandboxes and avoid pip-install waits
  • How memory snapshots (mechanism undocumented, checkpoint/restore) work for Modal Functions (not Sandboxes) and their limitations (GPU snapshots are alpha, randomness caveats)
  • How SWE-bench's Modal harness creates per-instance images and runs evaluations in Sandboxes
  • When your eval orchestrator should choose Modal (elastic, serverless, gVisor-compatible) vs E2B (VM-only, Apache-2.0 OSS) vs Daytona (self-hosted, job-based) vs self-managed Firecracker/gVisor
  • Hands-on: Create gVisor and VM sandboxes, build/cache images, snapshot filesystem, measure startup latency, and run a mini async eval pool with timeouts and retries

Modal Architecture: Serverless Sandboxes on Demand

Modal is a serverless compute platform: you define functions and sandboxes, Modal schedules them onto a fleet of workers, and you pay per-second for CPU/memory/GPU usage. Unlike E2B (control plane + orchestrator nodes you manage) or Daytona (job queue + runners you deploy), Modal is fully managed. You call modal.Sandbox.create(...) and Modal provisions the container, runs it, and tears it down when idle.

The Modal Execution Model

From Modal Sandboxes documentation:

"A Sandbox is a secure container for executing untrusted user or agent code on Modal. Each individual job is called a Sandbox and can be created using the Sandbox.create constructor. Sandboxes support nearly all configuration options found in regular modal.Functions."

Sandboxes vs Functions:

  • Functions: Defined in Python, deployed with modal deploy, invoked via fn.remote(...). Modal auto-scales them (0 to N containers), handles retries, queues, and distributed coordination.
  • Sandboxes: Created at runtime (modal.Sandbox.create), you control exec calls (sb.exec("python", "-c", "...")), and you decide when to terminate (sb.terminate()). No auto-scaling of a single sandbox; instead, you create N sandboxes in parallel.

Lifecycle and Timeouts

From Modal Sandboxes docs, a sandbox moves through these events:

  1. Created: Registered with Modal, ID assigned, no resources allocated yet.
  2. Scheduled: Assigned to a worker, provisioning resources (CPU, memory, GPU, volumes).
  3. Started: Container launched, entrypoint running (if specified), ready for sb.exec(...).
  4. Ready (optional): Readiness probe succeeded (e.g., HTTP health check). Skipped if no probe configured.
  5. Finished: Entrypoint exited, terminated manually, timeout reached, or OOM. No further commands accepted.

Default timeout: 5 minutes (300 seconds). Max: 24 hours (Sandbox.create). For longer runs, use filesystem snapshots to preserve state and resume later. Idle timeout: Auto-terminate after N seconds of no activity (no running exec, no stdin writes, no open tunnel connections). Set via idle_timeout parameter.

Runtimes: gVisor (Default) vs VM

From Modal Sandboxes docs:

"Sandboxes run on one of two runtimes:
gVisor, a container runtime developed by Google, provides strong isolation and is suitable for most workloads.
VMs run the Sandbox in a virtual machine with its own Linux kernel. Use the VM runtime for workloads that expect a full Linux environment, such as running Docker inside the Sandbox, mounting FUSE filesystems, or managing resources with nested cgroups."

gVisor: Userspace Kernel (Default)

Recall Lesson 03: gVisor implements the Linux syscall interface in userspace. Applications make syscalls, but instead of going to the host kernel, they trap into the gVisor Sentry (userspace kernel). The Sentry validates, logs, and either handles the syscall itself or passes safe operations to the host kernel.

Modal's gVisor implementation: Modal uses gVisor's systrap platform (not KVM platform). Systrap uses SECCOMP_RET_TRAP to intercept syscalls (lesson 02 seccomp-bpf) and redirect them to the Sentry. Systrap is gVisor's current default platform because it works everywhere (no /dev/kvm needed) and has lower syscall overhead than the older ptrace platform.

Why gVisor for most workloads?

  • GPU-compatible: Unlike Firecracker (lesson 04), gVisor supports GPU passthrough. Modal GPU sandboxes require runtime="gvisor" (Sandboxes docs). gVisor's nvproxy forwards NVIDIA GPU ioctl calls to the host without running a full guest kernel.
  • Fast cold starts: gVisor containers start faster than microVMs (no kernel boot). Modal reports sub-second cold starts with image caching (vendor claim).
  • Lower memory overhead: No guest kernel RAM. The Sentry (userspace kernel) adds modest per-sandbox memory overhead, but avoids the cost of a full guest OS.
  • Good syscall performance: Systrap has lower syscall overhead than gVisor's older ptrace platform. File I/O and network I/O go through the Gofer (lesson 03), which adds latency for small I/O but is optimized for bulk transfers.

Trade-offs: No pause/resume/fork (gVisor Sentry doesn't expose snapshot APIs to Modal). No nested virtualization (no /dev/kvm inside gVisor). Docker-in-gVisor works for some cases but can hit limits (runsc doesn't implement every Docker feature); use VM runtime for full Docker compatibility.

VM Runtime: Full Linux Kernel

When to use: Docker-in-sandbox, FUSE filesystems (lesson 03 overlayfs was kernel module; FUSE is userspace), nested cgroups (advanced resource control), or any workload that expects /dev/kvm or kernel modules.

From Sandboxes docs, example: 

image = (
    modal.Image.from_registry("ubuntu:24.04")
    .env({"DEBIAN_FRONTEND": "noninteractive"})
    .apt_install("docker.io")
)

sb = modal.Sandbox.create(
    "dockerd",  # Entrypoint: start Docker daemon
    app=sb_app,
    image=image,
    runtime="vm",
    readiness_probe=modal.Probe.with_exec("docker", "info", interval_ms=500),
)
sb.wait_until_ready()

p = sb.exec("docker", "run", "--rm", "alpine", "echo", "hello from Docker")
p.wait()
print(p.stdout.read())  # "hello from Docker"

sb.terminate()

How it works (VMM not documented by Modal): Modal does not publish which hypervisor backs VM runtime. Candidates include KVM (Linux), Firecracker, or Cloud Hypervisor. Based on feature set (512 GiB root filesystem, no pause/resume/fork mentioned for Sandboxes), the specific hypervisor is undocumented.

Trade-offs: VM sandboxes have higher memory overhead (guest kernel + init), slightly slower cold starts (kernel boot), and fixed 512 GiB root filesystem (Sandbox resources docs). /var/lib/docker is included in filesystem snapshots, so you can snapshot a VM with Docker images pre-pulled and resume later.

Image Building and Caching: Avoid Rebuild Waits

Problem: Running pip install torch or apt-get install gcc inside a fresh sandbox takes seconds to minutes. When you're running 1,000 eval instances, that's hours of wasted time. Solution: pre-build images with dependencies baked in, and cache layers so unchanged steps don't rebuild.

Modal Image Definitions

From Modal Images docs:

"Images are cached per layer (i.e., per Image method call), and breaking the cache on a single layer will cause cascading rebuilds for all subsequent layers. You can shorten iteration cycles by defining frequently-changing layers last so that the cached version of all other layers can be used."

Example: 

image = (
    modal.Image.debian_slim()  # Layer 0: base (Debian + Python 3.11)
    .apt_install("git")        # Layer 1: apt packages
    .pip_install("pytest", "requests")  # Layer 2: Python packages
    .run_commands("echo 'setup complete' > /setup.txt")  # Layer 3: custom script
)

Each method call is a layer. If you change pip_install (e.g., add "numpy"), Modal rebuilds layer 2 and layer 3 (because layer 3 depends on layer 2's filesystem). Layer 0 and layer 1 are reused from cache. This is similar to Docker's layer cache but uses function hashing: Modal hashes the method name, arguments, and base image ID to decide if a layer can be reused.

Layer Caching Rules

  • Cache hit: If the base image and method call (name + args) match a previous build, Modal pulls the cached layer from the OCI registry.
  • Cache miss: If the base or method changes, Modal rebuilds that layer and all subsequent layers.
  • Force rebuild: Add force_build=True to any method to rebuild that layer and subsequent layers, even if the definition hasn't changed. Remove it after the rebuild to avoid rebuilding every time.
  • Environment variable: MODAL_FORCE_BUILD=1 modal run ... rebuilds all images attached to your App. MODAL_IGNORE_CACHE=1 rebuilds from the top without breaking the shared cache (useful for debugging).

Named Images and Pre-Built Images

Problem: If every sandbox builds the same image on-demand, you waste time and money. Solution: Deploy a named image once, then reference it by name. 

# Build once, deploy to registry
app = modal.App("my-eval-harness")

image = modal.Image.debian_slim().pip_install("pytest", "requests")

@app.function(image=image)
def dummy():
    pass  # Trigger image build on deploy

# Deploy (builds image, pushes to Modal registry)
# modal deploy my_app.py

# Later, reference by name (no rebuild)
app_lookup = modal.App.lookup("my-eval-harness", create_if_missing=False)
sb = modal.Sandbox.create(image=image, app=app_lookup)
# Image pulled from cache, no rebuild

Why this matters for SWE-bench: SWE-bench has 2,294 instances (SWE-bench full), each needing its own Python environment. If each instance rebuilt from scratch, total time would be days. Instead, SWE-bench builds a small set of base images per repo (e.g., django-base, flask-base), caches them, then forks per-instance sandboxes from those bases. We'll see the actual implementation in the "Real System" section.

Image Builder Version Updates

From Images docs:

"Modal provides a separate mechanism for keeping base images up-to-date without causing unpredictable rebuilds: the 'Image Builder Version'. This is a workspace-level configuration that will be used for every Image built in your workspace. We release a new Image Builder Version every few months but allow you to update your workspace's configuration when convenient."

What this means: Modal's debian_slim(), from_registry(...), and other base definitions pin specific OS versions, Python versions, and Modal client versions. When Modal releases a new builder version (e.g., to patch a CVE), your images don't automatically rebuild. You opt in via workspace settings, then the next deploy rebuilds all images. This gives you control over when breaking changes land (e.g., Python 3.11 → 3.12, or glibc updates).

Filesystem and Memory Snapshots: Fast Restore and Warm Pools

Filesystem Snapshots: Share Setup Across Sandboxes

Use case: You've run pip install numpy pandas torch (takes 60 seconds), cloned a repo, and set up config files. Now you want to run 100 test variations. Instead of repeating that 60-second setup 100 times, snapshot the filesystem and create 100 sandboxes from the snapshot.

From Modal Sandbox Snapshots docs:

"Filesystem Snapshots are copies of the Sandbox's filesystem at a given point in time. These Snapshots are Images and can be used to create new Sandboxes. Filesystem Snapshots are optimized for performance: they are calculated as the difference from your base image, so only modified files are stored."

How it works: 

import modal

app = modal.App.lookup("sandbox-snapshot-test", create_if_missing=True)

# Create sandbox, do expensive setup
sb = modal.Sandbox.create(app=app)
sb.exec("pip", "install", "torch").wait()  # 60 seconds
sb.exec("git", "clone", "https://github.com/myrepo/myproject").wait()  # 5 seconds
sb.exec("bash", "-c", "echo 'config=value' > /config.txt").wait()

# Snapshot filesystem (only modified files stored)
image = sb.snapshot_filesystem(timeout=55, ttl=None)  # ttl=None: retain indefinitely
sb.terminate()

# Create 100 sandboxes from snapshot (no pip install, no git clone)
for i in range(100):
    sb_child = modal.Sandbox.create(image=image, app=app)
    # Filesystem already has torch, myproject, config.txt
    sb_child.exec("pytest", f"myproject/tests/test_{i}.py").wait()
    sb_child.terminate()

Diff-based storage: Modal computes the diff between the snapshot and the base image. If the base image is 500 MB and you added 100 MB of files, the snapshot stores ~100 MB (plus metadata). This is similar to Docker's layer model and overlayfs (lesson 02).

Retention: Default TTL is 30 days (Snapshots docs). Pass ttl=None to retain indefinitely. Expired snapshots raise NotFoundError when you try to mount them.

Forking via Filesystem Snapshots

From Snapshots docs:

"Since Filesystem Snapshots are Images, you can create multiple Sandboxes from the same snapshot. Each Sandbox starts with an identical copy of the snapshotted filesystem, so you can use this to run parallel workloads or test different changes independently."

Compare to E2B/Daytona fork (lessons 06-07): E2B and Daytona fork entire VMs (memory + devices). Modal's filesystem snapshot only forks the filesystem, not running processes. Each child sandbox starts fresh (no running Python interpreter cloned). Trade-off: no memory state preserved, but also no clone hazards (RNG seeds, open file descriptors are fresh).

Memory Snapshots: For Modal Functions Only

Important: Memory snapshots work for Modal Functions, not Sandboxes. From Memory Snapshots docs:

"Modal Memory Snapshots can dramatically reduce the cold start latency of Modal Functions by skipping initialization work on most container boots. You can enable Memory Snapshots for your Function with the enable_memory_snapshot=True parameter."

How it works (mechanism undocumented): Modal checkpoints a Function container after global initialization (imports, model loading) but before the first request, then restores new containers from that checkpoint. The underlying checkpoint/restore mechanism is not documented by Modal.

Vendor performance claim: From Modal Memory Snapshots docs: "In our experience, practical initialization-heavy Functions often start up 3-10x faster from Memory Snapshots." This is a vendor-reported range, not independently verified.

Example: 

import modal

image = modal.Image.debian_slim().pip_install("torch")

with image.imports():
    import torch
    model = torch.load("model.pt")

app = modal.App("mem-snapshot-demo")

@app.function(enable_memory_snapshot=True, image=image)
def infer(x):
    return model(x)

# Deploy: modal deploy my_app.py
# First call: slow (imports + model load + snapshot creation)
# Subsequent calls: fast (restore from snapshot, skip imports/load)

Limitations:

  • GPU Memory Snapshots (alpha): GPU Memory Snapshots are available as an alpha feature via experimental_options={"enable_gpu_snapshot": True}. CPU-only memory snapshots block GPU access during @modal.enter(snap=True) methods. See Memory Snapshots docs for GPU snapshotting limitations and workarounds.
  • Randomness: From the docs: "if a variable is randomly initialized and that value included in a Memory Snapshot, that variable will be identical after every restore." If your application depends on uniqueness of state, verify your code is resilient to snapshotting.
  • Volume deletions: Deleting files in a Modal Volume that were read during checkpoint will cause restore failures (Memory Snapshots docs).
  • Snapshot counts: CPU-only Functions need around 6 snapshots for full coverage. GPU Functions need 2-3 snapshots per GPU type (Memory Snapshots docs FAQ).

Why not Sandboxes? Modal's memory snapshots are tied to the Function deployment lifecycle (snapshot created once per Function version, reused for all subsequent calls). Sandboxes are ephemeral: you create, exec, terminate. Modal doesn't expose checkpoint/restore APIs for Sandboxes because the implementation is optimized for the Function model (one checkpoint per code version, many restores). If you need pause/resume/fork for eval orchestration, use E2B or Daytona (lessons 06-07).

Networking and Security: Block, Allow, Tunnel

From Modal Networking docs:

"Sandboxes are built to be secure-by-default, meaning that a default Sandbox has no ability to accept incoming network connections or access your Modal resources."

Security Model: Isolated by Default

gVisor isolation: gVisor's Sentry intercepts network syscalls. Outbound connections go through the Sentry's netstack (userspace TCP/IP implementation). Inbound connections are blocked unless you explicitly expose ports via tunnels.

VM isolation: VM sandboxes run a full guest kernel with iptables rules configured by Modal. Outbound/inbound policies are enforced at the hypervisor or guest firewall.

Default policy: Sandboxes can make outbound connections to the internet (HTTP, HTTPS, arbitrary TCP/UDP). They cannot receive inbound connections (no listening sockets exposed to the internet) and they cannot access other Modal resources (Functions, Volumes, Dicts) unless you explicitly pass them via the SDK.

Network Controls

From Modal Networking docs, sandboxes support network controls (verify exact parameter names and syntax in current documentation):

  • block_network=True: Block all outbound network access. The sandbox can only talk to itself (localhost).
  • CIDR allowlists: Allowlist specific IP ranges. All other IPs are blocked.
  • Domain allowlists: Allowlist domain names (wildcard prefixes may be supported). All other domains are blocked.
  • Inbound allowlists: Allowlist inbound connections for tunnels. All other IPs are blocked.

Use case: Running untrusted LLM-generated code. Set block_network=True to prevent the code from exfiltrating data or downloading malware. 

sb = modal.Sandbox.create(
    app=app,
    block_network=True,  # No outbound connections
)
sb.exec("python", "-c", "import requests; requests.get('https://evil.com')")  # Fails
# ConnectionError: network blocked

Tunnels: Expose Ports to the Internet

Use case: Your sandbox runs a web server (e.g., Jupyter notebook, VS Code server, web UI for an agent). You want to access it from your browser.

From Sandboxes docs, expose ports: 

sb = modal.Sandbox.create(
    app=app,
    encrypted_ports=[8888],  # TLS-encrypted tunnel
)
# Modal creates a public URL: https://<sandbox-id>.modal.run:8888
# Requests to that URL are forwarded to localhost:8888 inside the sandbox

sb.exec("jupyter", "notebook", "--port=8888", "--no-browser").wait_in_background()
print(f"Jupyter: {sb.tunnels()[8888].url}")  # Print public URL

Tunnel types:

  • Encrypted ports (encrypted_ports): TLS-encrypted, no custom domain.
  • HTTP/2 ports (h2_ports): TLS + HTTP/2, useful for gRPC.
  • Unencrypted ports (unencrypted_ports): Plain TCP, no TLS (not recommended for untrusted sandboxes).

GPU Sandboxes: gVisor nvproxy, No Pause/Resume

From Sandbox Resources docs:

"You can also run Sandboxes with GPUs. GPU Sandboxes are only supported with runtime="gvisor"."

Why gVisor for GPUs?

gVisor nvproxy: gVisor's nvproxy forwards NVIDIA GPU ioctl calls from the guest to the host NVIDIA driver without running a guest kernel. This works because:

  • CUDA applications make ioctl calls to /dev/nvidia0 (the GPU device).
  • gVisor Sentry intercepts those ioctls and forwards them to the host driver.
  • The host driver allocates GPU memory, launches kernels, etc., on behalf of the guest.

Why not VMs? Hardware-virtualized VMs (KVM) need PCIe passthrough (VFIO) to expose GPUs to guests. Firecracker doesn't support PCIe passthrough. Cloud Hypervisor does, but Modal's VM runtime doesn't expose GPU passthrough (no gpu=... parameter for runtime="vm").

GPU Preemption

From Sandbox Resources docs:

"Unlike CPU Sandboxes, GPU Sandboxes are subject to preemption. Design your GPU workloads to handle interruptions gracefully."

What this means: If Modal's cluster is at capacity and a higher-priority workload needs a GPU, your sandbox may be preempted (killed). Your code should checkpoint progress regularly (e.g., save model checkpoints to a Volume after every N steps) so you can resume from the last checkpoint if preempted.

Elasticity and Pricing: Pay-Per-Second Serverless

Serverless Economics

Pay for what you use: Modal bills by the second for CPU, memory, and GPU. No idle charges. From Sandbox Resources docs:

"Modal Sandboxes are billed by the second based on whichever is higher: your resource request or your actual usage. Sandboxes can burst beyond their CPU and memory requests when additional resources are available on the underlying host."

Example: You request cpu=0.5 (0.5 physical cores) and memory=512 (512 MiB). Your sandbox uses 0.3 cores and 400 MiB. You pay for 0.5 cores (your request) and 512 MiB (your request), because max(request, actual). If your sandbox bursts to 0.7 cores and 600 MiB, you pay for 0.7 cores and 600 MiB.

Sandbox Pricing

From Modal Pricing (October 18, 2026):

  • CPU: $0.00003942 per physical core per second (0.125 core minimum). 1 physical core = 2 vCPUs.
  • Memory: $0.00000667 per GiB per second.

Example cost: A sandbox with 1 core and 2 GiB RAM running for 100 seconds costs:
CPU: 1 core × $0.00003942/sec × 100 sec = $0.003942
Memory: 2 GiB × $0.00000667/sec × 100 sec = $0.001334
Total: $0.005276 (~0.5 cents)

Compare to traditional cloud: AWS c7g.xlarge (4 vCPU, 8 GiB) costs $0.1512/hour on-demand in US East (N. Virginia) as of October 18, 2026 (AWS EC2 Pricing) = $0.000042/sec. Modal's 2 vCPU + 8 GiB = 1 core × $0.00003942 + 8 GiB × $0.00000667 = $0.00009278/sec (~2.2x AWS on-demand per-second). For spiky workloads (e.g., 10% utilization), Modal's pay-per-second model saves costs because you don't pay for idle time (2.2x higher per-second rate × 10% utilization ≈ 0.22x total cost vs. 24/7 on-demand). Modal's value prop: no idle charges, instant autoscale.

Cost = 300,000 × (1 core × $0.00003942/core/sec + 2 GiB × $0.00000667/GiB/sec) = 300,000 × $0.00005276 = $15.83. This excludes image build costs (depends on repo count and build time; measure your own). Total cost will vary based on actual CPU/memory requests and build overhead.

Real System: SWE-bench Modal Backend

SWE-bench (github.com/SWE-bench/SWE-bench) is a benchmark for evaluating LLM agents on software engineering tasks: given a GitHub issue and repo, can the agent generate a patch that fixes the issue and passes the test suite? It includes 2,294 instances across 12 Python repositories.

Why SWE-bench Needs Sandboxes

Problem: Each instance requires repo setup, dependencies installation, patch application, and test execution. Running thousands of instances sequentially or on limited local resources would take substantial time. Solution: Cloud sandboxes with elastic parallelism.

SWE-bench Modal Integration

Implementation: SWE-bench's Modal harness is in swebench/harness/modal_eval/run_evaluation_modal.py (SWE-bench repository).

Actual implementation (from source):

  1. Modal Function wrapper: @app.function decorator on run_instance_modal with 120-minute timeout to account for image build time.
  2. Per-instance image building: ModalSandboxRuntime.get_instance_image(test_spec) builds a unique Modal Image for each test instance from Ubuntu 22.04 + Python 3.11 + Miniconda, runs setup_env.sh and setup_repo.sh from the test spec, installs repo at /testbed/. Modal automatically caches images.
  3. Sandbox creation: modal.Sandbox.create() with the instance image, 4 CPUs, default 30-minute timeout (configurable).
  4. Patch application: Write patch to /tmp/patch.diff, apply via git apply or patch --batch --fuzz=5.
  5. Test execution: Run eval.sh script from test spec.
  6. Parallelization: run_instance_modal.starmap() runs instances in parallel. Errors set errored=True in TestOutput.
  7. Results: Logs saved to RUN_EVALUATION_LOG_DIR/run_id/model/instance_id/ with run_instance.log, test_output.txt, patch.diff, report.json.

Illustrative Code Example

Note: The following is a simplified, illustrative example showing Modal's evaluation pattern, not actual SWE-bench source code. Consult the SWE-bench repository for the real implementation. 

# Illustrative example showing Modal's evaluation pattern
import modal

app = modal.App("swebench-eval")

# Build base image (one per repo)
base_image = (
    modal.Image.from_registry("ubuntu:22.04")
    .apt_install("git", "python3.11", "python3-pip")
    .pip_install("pytest", "tox")
    .run_commands("git clone https://github.com/django/django /repo")
    .run_commands("cd /repo && pip install -e .")
)

@app.function(image=base_image, timeout=1800)
def run_instance_modal(instance_id, prediction, test_spec, run_id, timeout):
    """
    Run one SWE-bench instance in a Modal sandbox.
    
    Args:
        instance_id: e.g. "django__django-12345"
        prediction: agent's patch as string
        test_spec: dict with repo, python_version, test_command
        run_id: unique ID for this eval run
        timeout: max seconds for test execution
    
    Returns:
        dict with test_output, exit_code, logs
    """
    import subprocess
    import os
    
    # Write patch to file
    with open("/tmp/patch.diff", "w") as f:
        f.write(prediction)
    
    # Apply patch
    result = subprocess.run(
        ["git", "apply", "/tmp/patch.diff"],
        cwd="/repo",
        capture_output=True,
        timeout=60
    )
    if result.returncode != 0:
        return {"error": "patch_failed", "stderr": result.stderr.decode()}
    
    # Run tests
    result = subprocess.run(
        test_spec["test_command"],
        cwd="/repo",
        capture_output=True,
        timeout=timeout,
        shell=True
    )
    
    return {
        "instance_id": instance_id,
        "exit_code": result.returncode,
        "stdout": result.stdout.decode(),
        "stderr": result.stderr.decode(),
    }

Key observations:

  • Image caching: Modal automatically caches images. The source builds a unique image per instance but Modal's caching minimizes rebuild overhead.
  • Timeout handling: ModalSandboxRuntime uses modal.Sandbox.create() inside the Function with configurable timeout (default 30 minutes). The Function itself has a 120-minute timeout.
  • Error handling: If patch application fails or exceptions occur, the function returns TestOutput with errored=True. The source uses EvaluationError exceptions, not "infra_failure" strings.
  • Hybrid approach: SWE-bench wraps modal.Sandbox.create() calls inside a @app.function decorator to leverage Modal's parallelization via .starmap().

Lessons for Your Orchestrator

  • Build once, run many: Pre-build base images with common dependencies. Don't pip install inside each sandbox.
  • Timeout nesting: Set a per-exec timeout (kill the test process) and a per-sandbox timeout (kill the container). The sandbox timeout should be slightly longer (e.g., exec timeout + 60 seconds buffer for cleanup).
  • Error classification: Distinguish infra failures (patch didn't apply, image build failed) from model failures (tests failed). Only retry infra failures.
  • Log shipping: Write logs to object storage (S3, GCS) or a durable queue, not just local disk. If your orchestrator crashes, you can still retrieve results.

When to Use Modal vs E2B vs Daytona vs Self-Hosted

You're building an eval orchestrator. You've learned about E2B (lesson 06), Daytona (lesson 07), and Modal (lesson 08). Which should you choose? Here's a decision framework:

Decision Tree

  1. Do you need pause/resume/fork for GRPO-style RL or branch-and-select?
    • Yes → E2B (lesson 06) or Daytona VM class (lesson 07). Modal does not support pause/resume/fork for Sandboxes.
    • No → Continue.
  2. Do you need GPU sandboxes?
    • Yes → Modal (gVisor nvproxy) or Daytona GPU class (container + exclusive GPU). E2B does not support GPUs.
    • No → Continue.
  3. Do you need elastic serverless scale without provisioning nodes?
    • Yes → Modal (serverless autoscaling, pay-per-second).
    • No → Continue.
  4. Do you need open-source backend for audit / compliance / customization?
    • Yes → E2B (Apache-2.0, active OSS) or Daytona (AGPL-3.0, v0.190.0 frozen).
    • No → Continue.
  5. Do you need multi-tier isolation (container for speed, VM for fork, GPU for ML)?
    • Yes → Daytona (lesson 07).
    • No → Continue.
  6. Do you want to avoid managing infra (K8s, PG, Redis, S3)?
    • Yes → Modal (fully managed).
    • No → Self-host E2B, Daytona, or build your own (lessons 04-05).

Cost Comparison Example

Illustrative scenario: Run 1,000 eval instances, each takes 5 minutes (300 seconds), 1 CPU core, 2 GB RAM, no GPU. Assume 1,000 instances run in parallel (5-minute burst), then idle for the rest of the month.

  • Modal: 1,000 sandboxes × 300 sec × ($0.00003942/core/sec + 2 GiB × $0.00000667/GiB/sec) = 1,000 × 300 × $0.00005276 = $15.83 (pricing from modal.com/pricing). No idle charges. Modal's per-second rate is ~2.2x AWS c7g.xlarge per-second on-demand, but Modal charges only for active time (5 minutes), while maintaining an always-on instance would incur 24/7 charges (2.2x × 5 minutes / 24 hours ≈ 0.8% of the always-on monthly cost).
  • E2B Cloud: Not published (contact sales). Self-hosted E2B: To run 1,000 one-core instances concurrently, provision 250 c7g.xlarge instances (4 cores each = 1,000 cores). EC2 Linux on-demand bills per-second with a 60-second minimum (AWS EC2 Pricing), so 5 minutes = 250 × $0.1512/hr × (5/60 hr) = $31.50. To run in batches of 400 concurrently (100 instances), cost = 100 × $0.1512/hr × (5/60 hr) × 3 batches = $37.80. Spot instance costs vary by region and time.
  • Daytona Cloud: Not published (contact sales). Self-hosted Daytona: same arithmetic as E2B (provision EC2 instances).
  • Self-hosted (spot instances): Spot prices vary significantly by region, availability zone, and time. Check AWS Spot Pricing for current rates and plug in for your instance type and concurrency needs. Cheapest option, but requires infra management and spot interrupt handling.

Takeaway: Modal is cost-competitive for spiky workloads (pay only for active time). For sustained 24/7 workloads, self-hosted on spot instances is cheaper but requires more engineering. E2B and Daytona self-hosted fall in between (you manage nodes, but the orchestrator is pre-built).

p.wait()

p.wait()

# Snapshot filesystem (only modified files stored)
print("Creating filesystem snapshot...")
snapshot_image = sb.snapshot_filesystem(ttl=None)  # Retain indefinitely
print(f"Snapshot created: {snapshot_image}")

sb.terminate()

# Create 3 child sandboxes from snapshot (no git clone, no config write)
print("\n=== Fork from Filesystem Snapshot ===")
for i in range(3):
    sb_child = modal.Sandbox.create(image=snapshot_image, app=app)
    print(f"Child {i} sandbox ID: {sb_child.sandbox_id}")

    p = sb_child.exec("ls", "/repo")
    p.wait()
    assert "README" in p.stdout.read(), "Repo not found"
    
    p = sb_child.exec("cat", "/config.txt")
    p.wait()
    print(f"Child {i} config: {p.stdout.read()}")

Step 4: Async Eval Pool with Timeouts and Retries

Goal: Run N eval items concurrently, with per-exec timeouts and infra error retries. 

#!/usr/bin/env python3
"""
Mini async eval pool: concurrent sandboxes, timeouts, retries.
"""
import asyncio
import modal

app = modal.App.lookup("modal-lesson-08-async", create_if_missing=True)

# Simple image
image = modal.Image.debian_slim().pip_install("pytest")

async def run_eval_item(item_id: str, test_cmd: str, timeout_sec: int, max_retries: int = 2):
    """
    Run one eval item in a sandbox, with timeout and retry on infra errors.
    
    Returns:
        dict with item_id, exit_code, stdout, stderr, or error
    """
    for attempt in range(max_retries + 1):
        try:
            # Create sandbox
            sb = await modal.Sandbox.create.aio(image=image, app=app, timeout=timeout_sec + 30)
            
            try:
                # Execute test command with timeout
                p = await sb.exec.aio("bash", "-c", test_cmd, timeout=timeout_sec)
                await p.wait.aio()
                
                result = {
                    "item_id": item_id,
                    "exit_code": p.returncode,
                    "stdout": await p.stdout.read.aio(),
                    "stderr": await p.stderr.read.aio(),
                    "attempt": attempt,
                }
                
                await sb.terminate.aio()
                return result
            
            except asyncio.TimeoutError:
                await sb.terminate.aio()
                return {"item_id": item_id, "error": "timeout", "attempt": attempt}
        
        except Exception as e:
            # Infra error (sandbox creation failed, exec failed, etc.)
            print(f"[{item_id}] Attempt {attempt} failed: {e}")
            if attempt < max_retries:
                await asyncio.sleep(2 ** attempt)  # Exponential backoff
            else:
                return {"item_id": item_id, "error": f"infra_failure: {e}", "attempt": attempt}

async def run_eval_pool(items, concurrency=10, timeout_sec=30):
    """
    Run eval items with bounded concurrency.
    
    Args:
        items: list of (item_id, test_cmd) tuples
        concurrency: max concurrent sandboxes
        timeout_sec: per-exec timeout
    
    Returns:
        list of result dicts
    """
    semaphore = asyncio.Semaphore(concurrency)
    
    async def run_with_semaphore(item_id, test_cmd):
        async with semaphore:
            return await run_eval_item(item_id, test_cmd, timeout_sec)
    
    tasks = [run_with_semaphore(item_id, test_cmd) for item_id, test_cmd in items]
    results = await asyncio.gather(*tasks)
    return results

# Test
if __name__ == "__main__":
    items = [
        ("test-1", "echo 'test 1 pass' && exit 0"),
        ("test-2", "echo 'test 2 pass' && exit 0"),
        ("test-3", "sleep 5 && echo 'test 3 slow' && exit 0"),
        ("test-4", "exit 1"),  # Fail
        ("test-5", "sleep 100"),  # Timeout (if timeout_sec=30)
    ]
    
    results = asyncio.run(run_eval_pool(items, concurrency=3, timeout_sec=10))
    
    for result in results:
        print(f"{result['item_id']}: {result.get('exit_code', result.get('error'))}")
