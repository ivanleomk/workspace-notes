From Hosted Platforms to Self-Hosted Sandboxes

In Lessons 06-08, you studied three hosted sandbox platforms: E2B's Firecracker-based VM orchestrator (lesson 06), Daytona's multi-tier architecture (lesson 07), and Modal's serverless gVisor-first model (lesson 08). Each solved the orchestration problem: how to schedule, create, pause, resume, fork, and tear down thousands of isolated sandboxes for eval workloads.

But what if you need self-hosted control? Maybe you're running evals on bare metal for cost efficiency, or you need HIPAA compliance and can't send data to third-party clouds, or you're extending an existing Kubernetes cluster and want to reuse its networking and storage primitives.

This lesson surveys four sandbox systems that span the spectrum from embeddable libraries (microsandbox) to Kubernetes-native operators (agent-sandbox) to self-hostable serverless runtimes (beta9) to hosted-only platforms (Fly Machines). You'll learn which isolation mechanisms they use, how their lifecycles work, what warm-pool and snapshot capabilities they expose, and when to choose each for your eval orchestrator.

What You'll Learn

  • How microsandbox's embeddable libkrun SDK boots microVMs directly from your application (no daemon) with ~100ms cold starts (vendor claim) and fork/snapshot support
  • How kubernetes-sigs/agent-sandbox's CRDs (SandboxTemplate, SandboxWarmPool, SandboxClaim) provide pre-warmed pod pools on Kubernetes with sub-2-second allocation (vendor claim) and support for runc, gVisor, and Kata runtimes
  • How beta9 (Beam's AGPL-3.0 open-source engine) runs a self-hostable serverless platform with fast cold starts (<1 second vendor claim) and GPU support on Kubernetes
  • How Fly Machines runs Firecracker microVMs with sub-second start/stop (vendor claim), BGP Anycast routing, and individual VM lifecycle control, though Fly.io is a hosted platform (not OSS)
  • When your orchestrator should embed microsandbox (low-level control, no K8s), use agent-sandbox (K8s-native warm pools), self-host beta9 (serverless on your cluster), or adopt a hosted platform
  • Hands-on: Deploy agent-sandbox on a local kind cluster, create a SandboxTemplate and WarmPool, claim a sandbox, and measure allocation latency

⚠️ Licensing and Self-Hosting Context

microsandbox: Apache-2.0 (github.com/superradcompany/microsandbox). Permissive license, can be embedded in proprietary applications.

agent-sandbox: Apache-2.0 (github.com/kubernetes-sigs/agent-sandbox). Kubernetes SIG project, permissive license.

beta9: GNU AGPL-3.0 (github.com/beam-cloud/beta9). Copyleft license. If you run a modified beta9 as a network service (e.g., internal API for your team), you must offer the modified source to users. Review with legal counsel for compliance.

Fly Machines: Proprietary hosted platform, not open-source. Fly.io operates the infrastructure; you cannot self-host. Mentioned here because it's built on Firecracker (OSS) and relevant for eval orchestration design comparisons.

microsandbox: Embeddable libkrun MicroVMs

microsandbox (github.com/superradcompany/microsandbox) is an embeddable microVM runtime built on libkrun, a KVM-based VMM that runs on Linux (KVM), macOS (Hypervisor.framework), and Windows (Windows Hypervisor Platform). Unlike E2B (lesson 06) or Daytona (lesson 07), which require a server daemon and API, microsandbox is a library: you call Sandbox.builder("name").image("python:3.12").create().await? and it boots a microVM directly in your process. No long-running daemon, no network dependency, no gRPC coordination.

What Makes microsandbox Different

From the microsandbox README:

"Microsandbox runs untrusted workloads inside fast, local microVMs: AI agents, user code, plugins, CI jobs, dev environments, scrapers, and automation. [...] Embeddable: Spawn VMs right within your code. No setup server. No long-running daemon. [...] Instant Startup: Average boot times under 100 milliseconds."

Key claims (vendor-reported):

  • 100ms cold starts: From README "Average boot times under 100 milliseconds" (source). README footnote clarifies: "Boot time refers to guest boot on an M1 machine." Not independently verified; actual latency depends on image size, host CPU, and hypervisor.
  • Fork & snapshot: README states "Fork & Snapshot: Fork live sandboxes. Save running sandbox state and restore later" (source).
  • Cross-platform: Linux (KVM), macOS (Hypervisor.framework), Windows (WHP) (README).

Architecture: Single-Process Runtime

microsandbox's architecture changed significantly in a March 2026 rewrite (PR #455). The previous design had a two-process model (supervisor + VM process) and required a microsandbox-server daemon. The new design uses a single-process runtime:

From PR #455: "Single-process runtime — the supervisor is merged into the VM process. One process per sandbox, with an integrated agent relay over Unix domain sockets. [...] Embeddable Rust SDK — Sandbox::builder("name").image("python:3.12").create().await? boots a microVM directly from your application. No daemon, no server, no network dependency. Just a library call."

How It Works: libkrun, smoltcp, and Composable Filesystems

libkrun: A minimal KVM-based VMM forked from containers/libkrun. Per PR #455, microsandbox maintains a fork at github.com/zerocore-ai/libkrun with additional patches for smoltcp networking integration and single-process architecture. libkrun boots a Linux kernel and virtio devices (net, block, vsock). vendor/libkrunfw/ in the microsandbox repository packages the firmware and kernel images used by libkrun, not the VMM fork itself.

smoltcp networking: From PR #455: "smoltcp user-space networking — a pure-Rust in-process TCP/IP stack replaces TSI [the previous networking backend]. Enables packet-level network policy, DNS interception, TLS MITM for secret injection, and published ports — all without kernel network bridges."

Composable filesystems: Four pluggable backends (PR #455):

  • PassthroughFs: Host directory mapped to guest (virtio-fs passthrough).
  • MemFs: In-memory filesystem.
  • OverlayFs: N read-only layers + writable upper layer with copy-on-write and whiteout semantics (similar to Docker overlayfs, lesson 02).
  • DualFs: Policy-driven dispatch with lifecycle hooks for custom behavior (e.g., allow writes to /tmp, deny writes elsewhere).

Lifecycle and Snapshot/Fork

Create: Sandbox::builder("name").image("python:3.12").create().await? pulls the OCI image (if not cached), boots the VM via libkrun, and returns a Sandbox handle.

Exec: sandbox.exec("python", ["-c", "print('hello')"]) sends a command to the guest via the agent relay (Unix socket). The guest's init process spawns the command and streams stdout/stderr back.

Fork: From README: "Fork & Snapshot: Fork live sandboxes." Implementation details (memory snapshot mechanism, parent/child coordination) are not documented in the public README as of October 2026. The fork API is available in the SDK; consult the SDK documentation for usage.

Snapshot: README states "Save running sandbox state and restore later" (source). The snapshot mechanism (CRIU-like, or custom libkrun checkpoint) is not detailed in the public docs.

When to Use microsandbox

  • Low-level control: You want to embed microVM creation directly in your application without managing a server daemon.
  • Cross-platform: You need to run sandboxes on macOS or Windows (not just Linux).
  • Small-scale orchestration: You're running evals on a single node or a small cluster where you don't need Kubernetes-level orchestration.
  • Fork/snapshot: You need GRPO-style forking (lesson 05) but don't want to manage a separate orchestrator like E2B or Daytona.

Trade-offs: No built-in warm pools (you implement your own). No distributed scheduling (no API to allocate sandboxes across nodes). No GPU support documented (as of October 2026). If you need Kubernetes-native orchestration or GPU sandboxes, consider agent-sandbox or beta9.

kubernetes-sigs/agent-sandbox: CRDs for Warm Pools and Templates

agent-sandbox (github.com/kubernetes-sigs/agent-sandbox) is a Kubernetes-native platform for managing isolated, stateful, singleton workloads. It's purpose-built for AI agent runtimes, development environments, and any scenario that demands a long-running container with a stable identity. Instead of stitching together StatefulSets, Services, and PersistentVolumeClaims by hand, you describe the sandbox you want with Custom Resource Definitions (CRDs), and let the controller handle the rest.

Why agent-sandbox Exists

From agent-sandbox docs:

"Agent Sandbox is a Kubernetes-native platform for managing isolated, stateful, singleton workloads — purpose-built for AI agent runtimes, development environments, and any scenario that demands a long-running container with a stable identity. [...] The SandboxWarmPool extension pre-warms a pool of pods so that when a new sandbox is needed — for a code execution request or a fresh agent session — it can be assigned in milliseconds rather than waiting for a cold pod to schedule and start. This dramatically reduces latency for interactive workloads and high-throughput agent pipelines."

Key claim (vendor-reported): From quickstart README: "Performance comparison: With WarmPool: Sub-2 second allocation (pod already running). Without WarmPool: 10-30 seconds (image pull + container/VM startup)."

Architecture: Core CRDs and Extension CRDs

agent-sandbox defines two layers of CRDs:

  • Core CRD: Sandbox (under agents.x-k8s.io/v1beta1) — declarative API for a single, stateful pod with a stable hostname and optional persistent storage.
  • Extension CRDs: SandboxTemplate, SandboxClaim, SandboxWarmPool (under extensions.agents.x-k8s.io/v1beta1) — reusable templates, user-facing claims, and pre-warmed pod pools.

How It Works: Warm Pools and Claims

Step 1: Define a SandboxTemplate (admin-owned blueprint): 

# Save as python-template.yaml
apiVersion: extensions.agents.x-k8s.io/v1beta1
kind: SandboxTemplate
metadata:
  name: python-runtime-template
  namespace: agent-sandbox-demo
spec:
  podTemplate:
    spec:
      runtimeClassName: gvisor  # or kata, or omit for runc
      containers:
      - name: sandbox
        image: python:3.11
        resources:
          requests:
            cpu: "1"
            memory: "2Gi"

Step 2: Create a SandboxWarmPool (pre-warms N pods): 

apiVersion: extensions.agents.x-k8s.io/v1beta1
kind: SandboxWarmPool
metadata:
  name: python-warmpool
  namespace: agent-sandbox-demo
spec:
  replicas: 2  # Pre-warm 2 pods
  sandboxTemplateRef:
    name: python-runtime-template

The WarmPool controller creates 2 pods with label agents.x-k8s.io/warm-pool-sandbox. These pods are running and ready (image already pulled, container started).

Step 3: Create a SandboxClaim (user-facing request): 

apiVersion: extensions.agents.x-k8s.io/v1beta1
kind: SandboxClaim
metadata:
  name: quickstart-test
  namespace: agent-sandbox-demo
spec:
  warmPoolRef:
    name: python-warmpool

The controller claims one pod from the pool and creates a Sandbox resource. The WarmPool manager automatically creates a replacement pod to maintain replicas: 2.

Performance: From quickstart: "Sub-2 second allocation (pod already running)" vs "10-30 seconds (image pull + container/VM startup)" without a warm pool (vendor claim).

Runtime Flexibility: runc, gVisor, Kata

From docs: "Runtime flexibility: Works with standard containers, gVisor, Kata Containers, and other OCI-compatible runtimes."

Set spec.runtimeClassName: gvisor in the SandboxTemplate to use gVisor (lesson 03 userspace kernel). Set runtimeClassName: kata to use Kata Containers (lesson 03 hardware-virtualized VMs). Omit runtimeClassName to use the default runtime (runc).

Comparison to lessons 06-08: agent-sandbox doesn't manage VMs directly (like E2B or Daytona). Instead, it delegates to Kubernetes RuntimeClasses. If you want VM-level isolation, install Kata Containers on your cluster and reference it in the template. If you want gVisor isolation, install runsc (gVisor runtime) and reference it. agent-sandbox focuses on orchestration and warm pools, not the isolation mechanism itself.

When to Use agent-sandbox

  • Kubernetes-native: You're already running Kubernetes and want to reuse its networking, storage, and RBAC primitives.
  • Warm pools: You need pre-warmed sandboxes for low-latency allocation (sub-2 seconds vs 10-30 seconds cold start, vendor claim).
  • Runtime flexibility: You want to choose between runc (fast, shared kernel), gVisor (userspace kernel, lesson 03), or Kata (hardware VMs, lesson 03) via Kubernetes RuntimeClasses.
  • Multi-tenant orchestration: You're building a multi-tenant platform where users claim sandboxes from shared pools, with per-tenant quotas and RBAC.

Trade-offs: Requires Kubernetes (no standalone deployment). No fork built into the CRDs (not documented as a feature). The core README lists "pausing and resuming" as implemented; deep hibernation (saving state to persistent storage) and automatic resume on network activity are listed under Desired Sandbox Characteristics (aspirational). No GPU-specific scheduling documented (use Kubernetes device plugins for GPUs). For serverless autoscaling (0 to N pods), you'd layer Knative or KEDA on top of agent-sandbox, or use a platform like beta9 (next section).

beta9 (Beam): Self-Hostable Serverless Runtime (AGPL-3.0)

beta9 (github.com/beam-cloud/beta9) is the open-source engine powering Beam Cloud, a serverless platform for GPU inference, sandboxes, and background jobs. Unlike Modal (lesson 08, closed-source serverless), beta9 is self-hostable under the GNU AGPL-3.0 license. You can deploy it on your own Kubernetes cluster (EKS, GKE, or local k3d) with the provided Helm chart and run fast-starting containers (<1 second cold start, vendor claim) with GPU support, scale-to-zero, and distributed storage volumes.

License and Self-Hosting

From beta9 LICENSE:

"GNU AFFERO GENERAL PUBLIC LICENSE Version 3, 19 November 2007 [...] The GNU Affero General Public License is designed specifically to ensure that, in such cases, the modified source code becomes available to the community. It requires the operator of a network server to provide the source code of the modified version running there to the users of that server."

What this means: You can self-host beta9 for free, but if you modify it and run it as a network service (e.g., internal API for your team, or public SaaS), you must offer the modified source code to users. Review AGPL compliance with legal counsel if you're considering proprietary modifications. The AGPL does not restrict using beta9 as-is; it restricts distributing modified versions without sharing source.

Architecture: Gateway, Worker, and Runner

From beta9 README and self-hosting docs:

  • Gateway: REST API service (receives function invocations, schedules workloads, returns results). Written in Go.
  • Worker: Scheduler and container runtime manager. Pulls images, starts containers, manages lifecycle. Deployed as a DaemonSet or pool of pods on Kubernetes.
  • Runner: The actual container process running user code (sandbox). Workers spawn runners on-demand.

Fast Cold Starts and GPU Support

From beta9 README:

"Fast Cold Starts: Launch containers in under a second using a custom container runtime, scheduler, and embedded caching."

Vendor claim: "<1 second" cold starts (README). Not independently verified. Actual latency depends on image size, node CPU, and cache state. The "custom container runtime" and "embedded caching" refer to beta9's worker implementation (not documented in detail in public docs as of October 2026).

GPU support: README lists "GPU Support: Run on our cloud (4090s, H100s, and more) or bring your own GPUs" (source). Self-hosted beta9 can schedule workloads onto Kubernetes nodes with GPU device plugins (e.g., nvidia.com/gpu resources).

When to Use beta9

  • Serverless on your cluster: You want Modal-like serverless autoscaling (scale-to-zero, fast cold starts) but need to self-host for compliance, cost, or control.
  • GPU workloads: You're running GPU inference or training and want serverless scheduling onto your GPU nodes.
  • AGPL-compatible: You can comply with AGPL-3.0 (offer modified source to users if you modify beta9 and run it as a network service).
  • Kubernetes foundation: You're already on Kubernetes and want a serverless layer without vendor lock-in.

Trade-offs: AGPL license (less permissive than Apache-2.0). No pause/resume/fork built in (you'd implement that yourself if needed). Setup complexity higher than Modal (managed) but lower than building from scratch. For permissive licensing and lower-level control, consider agent-sandbox or microsandbox.

Fly Machines: Firecracker VMs on a Hosted Platform (Not OSS)

Fly Machines (fly.io/docs/machines/overview) are Firecracker microVMs on Fly.io's platform. Unlike microsandbox, agent-sandbox, and beta9 (all self-hostable OSS), Fly.io is a hosted platform: you cannot self-host Fly's infrastructure. However, Fly Machines are relevant for this lesson because:

  • They're built on Firecracker (lesson 04, Apache-2.0 OSS), so you can learn from Fly's architecture and apply those patterns to your own Firecracker-based orchestrator.
  • They demonstrate sub-second start/stop (vendor claim) and individual VM lifecycle control, which are design goals for eval orchestration.
  • They show how to integrate Firecracker VMs with BGP Anycast routing, WireGuard backhaul, and distributed proxy (fly-proxy), which are lessons for building a production VM fleet.

What Are Fly Machines?

From Fly Machines docs:

"Machines are fast-launching VMs with a simple REST API. They're the compute behind the Fly.io platform. [...] You can create and destroy Machines directly, and you have control over every Machine's lifecycle, resources, and region placement."

From Firecracker VM on Fly.io:

"Fly.io runs Firecracker in production. Application code on Fly.io runs inside Firecracker microVMs, on servers Fly.io operates itself, which is what makes it safe to run workloads from different customers on shared hardware. Fly Machines are those microVMs: hardware-virtualized, quick to boot, and addressable individually rather than as a fleet you scale in aggregate. [...] Machines start and stop at sub-second speeds, so a Machine that runs only when a request arrives is an ordinary deployment shape rather than an exotic one."

Architecture: Firecracker + BGP Anycast + WireGuard

From Fly.io Architecture:

  • Compute: Firecracker microVMs on dedicated servers. Each Firecracker process encapsulates one microVM (lesson 04 design).
  • BGP Anycast: Fly broadcasts IP ranges in all datacenters. Incoming connections are matched to a customer application and proxied to the closest available microVM.
  • fly-proxy: Rust-based proxy on every server. Accepts client connections, applies TLS termination, and forwards traffic to microVMs over WireGuard tunnels between datacenters.
  • WireGuard backhaul: If a user is in Dallas and your microVM is in Chicago, fly-proxy accepts traffic in Dallas, terminates TLS, and connects to the microVM over a WireGuard tunnel with low additional latency.

Lifecycle: Start, Stop, and Snapshot/Restore

From Firecracker VM on Fly.io:

"Machines start and stop at sub-second speeds, so a Machine that runs only when a request arrives is an ordinary deployment shape rather than an exotic one. Fly Proxy can stop and start Machines based on incoming traffic, and while a Machine sits stopped or suspended you aren't paying for its CPU and RAM. [...] Sprites are the same Firecracker substrate arranged for a different job. A Machine is the always-on production half. A Sprite is a persistent, reversible environment for running arbitrary or agent-generated code: a filesystem that survives on its own, checkpoints you can restore in place, and an opt-in egress allowlist. The snapshot and restore semantics described earlier are the mechanism underneath."

Vendor claim: "sub-second" start/stop (source). Not independently verified. Firecracker boot time (lesson 04) is ~125ms (AWS target), but Fly's "start" includes network setup, proxy configuration, and snapshot restore (if resuming), so actual user-visible latency varies.

Fly Init: Public Snapshot of Firecracker Guest Init

Fly published a snapshot of their init code at github.com/superfly/init-snapshot. From the README:

"This is a public snapshot of Fly's init code. It powers every Firecracker microvm we run for our users. It is Rust-based and we thought making it public (even in this very limited fashion) could help as a reference for people making Rust-based init programs. [...] our init is tailored for firecracker microvms. [...] Attach [the init device] as /dev/vda. Attach your rootfs as /dev/vdb. Attach a vsock virtio device."

Key details: The init reads /fly/run.json from /dev/vda (a separate ext2 device) for configuration, mounts the rootfs from /dev/vdb, and communicates over virtio-vsock for exec and lifecycle commands. This is a reference for building your own Firecracker guest init (lesson 04 covered host-side Firecracker setup; this is the guest-side counterpart).

Why Fly Machines Are Relevant (Despite Not Being OSS)

  • Firecracker best practices: Fly has run Firecracker in production at scale. Their architecture (BGP Anycast, WireGuard backhaul, individual VM lifecycle) is a proven design you can study for your own orchestrator.
  • Sub-second lifecycle: If your eval orchestrator needs fast sandbox allocation (like Fly's sub-second start), you can apply Firecracker's snapshot/resume (lesson 05) and pre-warmed VM pools (lesson 06 E2B's template snapshots).
  • Open init code: The init-snapshot repo is a rare public example of production Firecracker guest init in Rust. Compare it to E2B's Go-based orchestrator (lesson 06) and Daytona's Go runner (lesson 07) for alternative designs.

Trade-offs: You cannot self-host Fly.io. It's a hosted platform. If you need self-hosted Firecracker, use E2B's open-source runtime (lesson 06, Apache-2.0), build your own orchestrator (lessons 04-05), or layer Firecracker on Kubernetes with Kata Containers and agent-sandbox (this lesson).

Decision Guide for Your Orchestrator

  1. Do you need pause/resume/fork for GRPO-style RL or branch-and-select?
    • Yes, and you want self-hosted → E2B (lesson 06) or microsandbox (this lesson).
    • Yes, and you're okay with hosted → Fly Sprites (this lesson) or Modal Functions (lesson 08, memory snapshots).
    • No → Continue.
  2. Are you building on Kubernetes?
    • Yes, and you need warm pools → agent-sandbox (this lesson).
    • Yes, and you want serverless autoscaling → beta9 (this lesson).
    • No → Continue.
  3. Do you need GPU sandboxes?
    • Yes, self-hosted on K8s → beta9 or agent-sandbox (with K8s device plugins).
    • Yes, hosted → Modal (lesson 08, gVisor nvproxy) or Fly Machines (GPU Machines).
    • No → Continue.
  4. Do you want a permissive license (Apache-2.0)?
    • Yes → microsandbox, agent-sandbox, or E2B (lesson 06).
    • AGPL-3.0 is okay → beta9.
    • Proprietary hosted is okay → Modal (lesson 08) or Fly Machines.
  5. Do you need embeddable (library, no server)?
    • Yes → microsandbox (no daemon, call from your app).
    • No, server/orchestrator is fine → Any other option.

Build It Yourself: agent-sandbox on kind with Python SDK

You'll record your own timings to see warm-pool fast allocation vs cold-pod image pull and container start.

Step 3: Create a SandboxTemplate

Use the official Python runtime sandbox template from the agent-sandbox repository (clients/python/agentic-sandbox-client/python-sandbox-template.yaml). This template includes a runtime server on port 8888 that supports sandbox.commands.run() in Step 6: 

# Save as python-template.yaml
apiVersion: extensions.agents.x-k8s.io/v1beta1
kind: SandboxTemplate
metadata:
  name: python-runtime-template
  namespace: default
spec:
  podTemplate:
    spec:
      # runtimeClassName: gvisor  # Uncomment if gVisor is installed
      containers:
      - name: python-runtime
        image: us-central1-docker.pkg.dev/k8s-staging-images/agent-sandbox/python-runtime-sandbox:latest-main
        ports:
        - containerPort: 8888
        readinessProbe:
          httpGet:
            path: "/"
            port: 8888
          initialDelaySeconds: 0
          periodSeconds: 1
        resources:
          requests:
            cpu: "250m"
            memory: "512Mi"
      restartPolicy: "OnFailure"
kubectl apply -f python-template.yaml
kubectl get sandboxtemplate

Step 4: Create a SandboxWarmPool

Pre-warm 2 sandboxes:

apiVersion: extensions.agents.x-k8s.io/v1beta1

Step 6: Measure Warm-Pool Allocation Latency (Python SDK, Untested)

Create a Python script to claim a sandbox from the warm pool and measure allocation time through to Ready. Save as test_warmpool_timing.py: 

#!/usr/bin/env python3
"""Measure warm-pool allocation latency using k8s-agent-sandbox Python client."""
import time
from k8s_agent_sandbox import SandboxClient
from k8s_agent_sandbox.models import SandboxLocalTunnelConnectionConfig

# Connect to agent-sandbox via local tunnel (kubectl port-forward)
# SandboxLocalTunnelConnectionConfig has: port_forward_ready_timeout, server_port, router_namespace
# No kubeconfig_path field - it uses the default ~/.kube/config
with SandboxClient(
    connection_config=SandboxLocalTunnelConnectionConfig(
        router_namespace="agent-sandbox-system",  # Where sandbox-router is deployed
        port_forward_ready_timeout=30,
        server_port=8888
    )
) as client:
    print("=== Warm-Pool Allocation Test ===")
    print("Creating sandbox from warm pool...")

    start_time = time.time()

    # create_sandbox claims a pod from the warm pool
    # The SDK waits for the sandbox to be Ready before returning
    # Returns a Sandbox object with .claim_name and .sandbox_id attributes
    sandbox = client.create_sandbox(warmpool="python-warmpool", namespace="default")

    allocation_time = time.time() - start_time

    print(f"Sandbox claim name: {sandbox.claim_name}")
    print(f"Sandbox ID: {sandbox.sandbox_id}")
    print(f"Allocation time: {allocation_time:.2f} seconds")
    print(f"This includes: API call, warm pod claim, and SDK wait for Ready condition.")
    print("\nRecord your timing here: ___________ seconds\n")

    # Test the sandbox is working
    result = sandbox.commands.run("python3 -c 'print(\"Hello from warm pool\")'")
    print(f"Test output: {result.stdout.strip()}")

    # Clean up - sandbox.terminate() deletes the claim
    sandbox.terminate()

print("\n=== Test Complete ===")

python3 test_warmpool_timing.py

Record your timing: Write down the allocation time reported by the script. With a warm pool, the pod is already running (image pulled, container started), so allocation should be fast. Your results may vary based on local kind performance.

Step 7: Measure Cold-Pod Allocation Latency (kubectl, Not SDK)

The Python SDK's create_sandbox method only supports warmpool parameter, not template. To measure cold-pod allocation latency, use kubectl to create a bare Sandbox CR and time it with kubectl wait. This measures time to Ready only (no command execution): 

# Save as cold-sandbox.yaml
apiVersion: agents.x-k8s.io/v1beta1
kind: Sandbox
metadata:
  name: cold-test
  namespace: default
spec:
  podTemplate:
    spec:
      containers:
      - name: sandbox
        image: python:3.11-slim
        command: ["sleep", "infinity"]
        resources:
          requests:
            cpu: "1"
            memory: "2Gi"
# Measure cold-pod allocation latency
# time reports when the command completes, not when kubectl returns
# Use date to measure the full kubectl wait duration
START=$(date +%s)
kubectl apply -f cold-sandbox.yaml
kubectl wait --for=condition=Ready sandbox/cold-test --timeout=90s
END=$(date +%s)
ELAPSED=$((END - START))

echo "Cold-pod allocation time: ${ELAPSED} seconds"
echo "This includes: pod scheduling, image pull (if not cached), container start, and wait for Ready."
echo "Record your timing here: ___________ seconds"

# Verify the sandbox
kubectl get sandbox cold-test

Record your timing: Write down the cold-pod allocation time. On kind with a warm Docker image cache, you might see variable timings depending on node resource availability. Without cache (first pull of python:3.11-slim), expect longer times for image download.

kubectl delete sandboxwarmpool python-warmpool
kubectl delete sandboxtemplate python-runtime-template

kind delete cluster --name agent-sandbox-demo
